1. 회수율 57% — 못 짝지은 34건

1-1. 한 줄을 한 건으로 뭉친다

    골든                                실제
    KPI_NAME         "사업화 성공률"     KPI_NAME         "사업화 성공률: 목표값 30%, 기준연도 2025년"
    KPI_TARGET_VALUE "목표값 30%"        KPI_TARGET_VALUE "사업화 성공률: 목표값 30%, 기준연도 2025년"
    KPI_BASE_YEAR    "기준연도 2025년"

같은 줄이 두 축으로 중복 인용된다. 지표가 4개인데 목표값 인용이 2건뿐이라
"목표값 90건", "목표값 15%" 가 짝을 못 찾는다.

지원항목도 같다. 시제품 제작비 / 공인 시험인증비 / 판로개척 마케팅비 셋이
문장 하나의 SUPPORT_ACTIVITY 한 건으로 뭉친다. 보조율 80% 와 자부담률 20%
도 한 줄에 있어 SUBSIDY_RATE 한 건이 되고, 서로 다른 두 비율이 한 근거에
들어가 정규값이 하나만 남는다.

원인 — 프롬프트 문구 부족이 아니다. cpl-v0.9.txt 30행에 이미 있다.

    MINIMUM VERBATIM SPANS
    Quote the smallest complete phrase that proves one fact. Do not quote a
    whole paragraph, whole list, or whole KPI row when a shorter contiguous
    phrase proves the axis. In a comma-separated list, return each
    independently meaningful item.

"whole KPI row 를 인용하지 말라", "쉼표 목록은 항목별로 반환하라" 가
명시돼 있는데 지켜지지 않는다. 같은 문구를 덧붙이는 것은 의미가 없고
목업 과적합 위험만 키운다.

1-3. 필드 경계를 넘는다

근거 탈락 로그를 상세화한 뒤 실제 인용까지 확인했다.

    FIELD_NOT_ALLOWED:PURPOSE_PROBLEM_DOMAIN@body:4:cell:2:1
      인용 : "디지털 전환 수준이 전국 평균 대비 낮아 생산성 향상에 제약이…"
      소유 : BUSINESS_NEED

    FIELD_NOT_ALLOWED:ANNUAL_PLAN_CONTENT@body:4:cell:3:1
      인용 : "(사업기간) 2026. 01. 01. ~ 2028. 12. 31. (3년, 다년도 사업)"
      소유 : NEW_OR_CHANGED_CONTENT

둘 다 서버가 옳게 막았다. 코드 결함이 아니다. 프롬프트에도
"BUSINESS_NEED fragment is not PURPOSE_GOAL evidence merely because both
discuss the same policy domain" 이 있다.

참고로 로그 이름이 오해를 부른다. FIELD_NOT_ALLOWED 는 "허용 안 된 필드"
처럼 읽히지만 실제 뜻은 "인용 구간이 이 필드 소속이 아니다" 다.
EVIDENCE_FIELD_MISMATCH 쪽이 정확하다.


1-4. 해결 방향 — 요청 분리 (추론)

지금은 의미 필드 9개, 축 44개를 한 번의 호출로 요청한다. 여기에 원문 그대로,
최소 구간, 필드 경계, 커버리지 같은 제약이 겹친다. 프롬프트는 104줄이다.

추론: 지시가 부족한 게 아니라 한 번에 지켜야 할 제약이 너무 많다.
필드별로 나눠 요청하면

  - 해당 필드의 조각을 중심으로 주므로 1-3 의 필드 경계 위반이 크게 준다
  - 축 후보가 44개에서 4~10개로 줄어 1-2 의 오분류 여지가 준다

주의 1. "구조적으로 불가능해진다" 고 말할 수는 없다. _semantic_messages()
는 소유 필드가 없는 조각을 요청 필드와 무관하게 항상 포함한다.

    for fragment in semantic_fragments(document)
    if not fragment.field_codes
    or bool(fragment.field_codes & semantic_fields)

따라서 다른 칸에서 끌어올 여지가 크게 줄 뿐 사라지지는 않는다.

주의 2. 첫 실험은 한 변수만 바꾼다. 요청을 나누면서 프롬프트까지 필드별로
줄이면 개선이 어느 쪽 덕인지 구분할 수 없다.

  - 모델과 프롬프트 v0.9 는 그대로 둔다
  - 호출만 PURPOSE_GOAL / IMPLEMENTATION_PLAN / 나머지 7필드로 나눈다
  - 각 요청에 해당 필드 조각을 중심으로 전달한다
  - 8회 동안 필드별 recall, 탈락 사유, 토큰, 시간, 비용을 측정한다
  - 가능하면 기존 방식과 분리 방식을 번갈아 실행하는 A/B 로 돌린다

프롬프트 축소는 그다음 실험에서 따로 검증한다.

검증 방법: 위 조건으로 8회 실행하고 현재 기준선과 비교한다.

    기준선 (mockup_08, 8회)
      FIT 점수    21.4 / 35.7 / 50.0     폭 28.6
      CPL 확인율  10 ~ 11 / 13
      회수율      0.456 ~ 0.570          폭 11%p

측정 도구는 tmp/fit_variance_eval.py 가 이미 있다.

주의: 요청 분리는 호출 수를 늘린다. 마스터플랜의 비용·응답시간 항목과
충돌할 수 있으므로 회수율 개선 폭과 함께 봐야 한다.

2. 판정 변동성 — 원인 미확정
────────────────────────────────────────────────────────

확인된 사실. 같은 문서 8회에서 FIT 점수가 21.4 ~ 50.0 을 오간다.

    FIT-1  INSUFFICIENT:8                            안정
    FIT-2  FIT:6  INSUFFICIENT:2                     흔들림
    FIT-3  FIT:6  NEEDS_REVIEW:1  INSUFFICIENT:1     흔들림
    FIT-4  INSUFFICIENT:8                            계약상 고정
    FIT-5  NEEDS_REVIEW:6  FIT:2                     흔들림
    FIT-6  FIT:4  INSUFFICIENT:3  NEEDS_REVIEW:1     흔들림
    FIT-7  INSUFFICIENT:8                            양식상 단측

흔들리는 4개 중 3개는 등급이 아니라 판정 가능 여부 자체가 오간다.
순수한 등급 흔들림은 FIT-5 하나뿐이다.

이 결과로 판정 단계 세분화(0/50/100 을 더 나누는 것)는 보류했다.
3단계도 안정적으로 못 내는데 5단계를 요구하면 폭만 커진다. 그리고
흔들림의 대부분이 등급 문제가 아니라 판정 가능 여부 문제라 단계를
늘려도 해결되지 않는다. FitStatus 는 프론트 계약의 union type 이라
값 추가는 프론트 영향도 있다.

원인이 모델 성능인지 과제 설계인지는 아직 측정하지 않았다.
현재 CPL·FIT·SIM 모두 gpt-4o-mini 다.

판별 방법 (추론)

  1) 요청 분리로 개선되면 과제 설계 문제다
  2) 그래도 안 되면 같은 조건으로 더 큰 모델을 여러 회 돌려본다

     1회 비교로는 변동성과 우연을 구분할 수 없다. 지금 재는 대상이
     변동성 자체이므로 모델 비교도 같은 횟수로 반복해야 한다.

순서가 중요하다. 마스터플랜이 알파는 gpt-4o-mini, 후속은 로컬 sLLM 으로
정해놨으므로, 모델을 키우는 게 답이면 후속 계획과 충돌한다. 반대로 요청
분리로 해결되면 작은 모델로 간다는 근거가 되고 하이브리드 논지와도 맞는다.

3. IMPLEMENTATION_PLAN 이 MISSING 으로 떨어진다
────────────────────────────────────────────────────────

확인된 사실. 근거가 3건 남아 있는데 상태가 MISSING 이다.

이것은 상태 계약 위반이 아니다. AGENTS.md 225행이 정한 대로다.

    IMPLEMENTATION_PLAN 은 연차별 계획과 내역사업별 계획을 source_role 로
    따로 판정한 뒤 합친다. 하나라도 누락이면 MISSING …

연차 계획이 0건이므로 MISSING 이 맞다. 앞선 검토에서 "occurrence 가 있으면
MISSING 금지" 라는 상태 가드를 넣자는 안이 나왔으나 계약 위반이라
폐기했다. 실제로 연차 계획이 빠진 문서까지 약화시킨다.

원인은 1-2 의 축 오분류다. 1단계·2단계가 SUBPROGRAM 으로 태깅되고
정작 ANNUAL 로는 사업기간 줄이 들어온다. 두 축이 자리를 바꿔 들었다.
1-4 의 요청 분리로 함께 검증하면 된다.

목업 라벨을 "연차별 추진계획" / "내역사업별 추진계획" 둘로 나누자는 안도
나왔으나 폐기했다. 판별기준 제목 자체가 "연차별·내역사업별 추진계획" 이고
프롬프트도 합쳐진 구역을 명시적으로 허용한다. 라벨을 나누면 모델 오류를
고치는 게 아니라 스트레스 표본을 쉽게 만들어 실패를 숨기게 된다.


────────────────────────────────────────────────────────
4. occurrence 에 묶음 표현이 없다
────────────────────────────────────────────────────────

확인된 사실. CplOccurrence 는 평면이라 "목표값 30%" 가 어느 지표의 것인지
표현할 수 없다. 지표 4개의 이름·목표값·기준연도가 연결되지 않는다.
수행절차 7단계와 단계별 역할 3건도 짝지어지지 않아 FIT-6 이 단계별 역할을
제대로 대조하지 못한다.

해결 방향 (추론)

그룹은 LLM 에게 요구하지 않는다. 서버가 계산한다.
_evidence_context 가 이미 인용 구간의 위치를 찾고 있어 몇 번째 줄인지
바로 나온다. 다만 한 줄에 항목이 여러 개일 수 있으므로 줄 번호만으로는
부족하고 line_index + span_start/end 형태가 안전하다.

    - 사업화 성공률: 목표값 30%, 기준연도 2025년   ← line 3
    - 신규 고용창출: 목표값 240명                  ← line 4

    KPI_NAME         "사업화 성공률"    line 3 / span 2-8
    KPI_TARGET_VALUE "목표값 30%"       line 3 / span 10-17
    KPI_NAME         "신규 고용창출"     line 4 / span 2-9

줄 번호와 오프셋은 닫힌 사실이라 판단이 필요 없고 같은 문서면 항상 같은
값이 나온다. 축 하나도 안정적으로 못 붙이는 상태에서 LLM 에게 group_id 를
요구하면 실패 지점만 늘어난다.

프론트 영향은 additive 다. source_locator 에 이미 paragraph_index 가 있어
거기에 얹으면 새 최상위 필드도 필요 없다.

중요 1. 이것만으로는 회수율이 오르지 않는다. 지금처럼 줄 전체를 인용하면
두 축이 같은 그룹에 들어갈 뿐 "목표값 90건" 은 여전히 안 나온다.
1-4 가 회수율을 올리고 4 가 그것을 쓸모 있게 만드는 관계다.

중요 2. 좌표는 묶음의 재료이지 묶음 자체가 아니다. 좌표를 넣는다고 KPI
이름과 목표값의 관계가 저절로 표현되지 않는다. 다음을 따로 정해야 한다.

  - KPI 는 같은 줄을 같은 그룹으로 볼 것인가
  - 한 줄에 KPI 가 여러 개면 어떻게 나눌 것인가
  - 수행 역할은 쉼표로 나뉜 절을 각각 묶을 것인가
  - 같은 raw_text 가 같은 fragment 에 반복될 때 어느 span 을 고를 것인가

이 규칙은 실제 분리 추출 결과를 본 뒤에 정하는 것이 맞다. 지금 정하면
현재의 넓은 인용을 전제로 규칙을 만들게 된다.
따라서 순서는 1-4 → 재측정 → 좌표 보존 → 그룹 규칙 결정이다.


────────────────────────────────────────────────────────
5. FIT 점수 — 하나만 판정돼도 만점이 나온다
────────────────────────────────────────────────────────

확인된 사실. 현재 분모는 판정된 관계만 센다.

    denominator = sum(100 * weight for r in assessable)

7개 중 하나만 판정되고 그것이 FIT 이면 100 점이 나온다.
표기를 "100점(평가 가능 1/7)" 로 바꿔도 머리 숫자는 그대로 100 이다.

한 차례 분모를 7개 전체로 고정하는 변경을 넣었다가 되돌렸다. 이유는
계약 위반이다.

    AGENTS.md 245행
    FIT-7 단측 정보만 정정 계약에 따라 점수에서 제외한다.

    AGENTS.md 243행
    … INSUFFICIENT / SINGLE_SIDED_NO_CONFLICT, score=None 이다.

"점수에서 제외" 가 명시돼 있는데 고정 분모는 그것을 0점으로 포함시킨다.
FIT-4 도 계약상 항상 판정 불가라 균등 가중치 기준 14.3점이 영구히 빠진다.

해결 방향 (추론)

SIM 이 같은 문제를 CR-09 로 이미 해결했다. 핵심 축이 모두 평가 가능할
때만 점수를 내고, 아니면 weighted_score=None, review_grade=ON_HOLD 다.
FIT 도 같은 형태의 gate 계약이 필요하다.

핵심 관계 후보는 실제 양식을 따른 정상 문서라면 반드시 판정 가능해야
하는 것들이다.

    FIT-4  계약상 항상 판정 불가                → 핵심 제외
    FIT-6  양식이 수행절차를 필수로 요구 안 함    → 핵심 제외
    FIT-7  양식상 지원규모 구역이 없어 단측      → 핵심 제외
    FIT-5  조건 부재도 판정 불가로 처리됨        → 핵심 제외
    FIT-1  목적 ↔ 지원대상        ┐
    FIT-2  목적 ↔ 지원내용        │ 모두 양식의 필수 기재항목으로 구성
    FIT-3  목적 ↔ 기대효과·성과지표 ┘ → 핵심 후보

FIT-5 를 뺀 이유는 코드로 확인했다.

    fit_engine.py
    FitStatus.INSUFFICIENT,
    "별도로 명시된 지원조건이 없습니다.",
    ...
    "NO_CONDITIONS_SPECIFIED",

지원조건이 없는 정상 문서도 INSUFFICIENT 가 된다. 판별기준 11.3 도
"지원조건이 별도로 없다고 해서 자동으로 오류로 판단하지 않는다" 고 한다.
FIT-5 를 gate 에 넣으면 조건 없는 정상 문서는 영원히 전체 점수를 못 받는다.

그리고 gate 를 구현하기 전에 제품 표현부터 정해야 한다.

  - 점수를 계속 보여줄 것인가
  - "확인 가능 4/7" 중심으로 바꿀 것인가
  - gate 실패 시 score=None 만 둘 것인가, assessment_status=ON_HOLD 도 둘 것인가

이것은 report_json 계약이라 프론트와 함께 정해야 한다. 코드로 조용히
바꾸면 안 된다.

6. 남은 자잘한 것
────────────────────────────────────────────────────────

6-1. 라벨 포함 여부만 다른 중복 occurrence

    DELIVERY_METHOD_TYPE  "시 출연기관 위탁(보조)"
    DELIVERY_METHOD_TYPE  "수행방식: 시 출연기관 위탁(보조)"

같은 사실이 두 건이다. 동일 위치·축·role·정규값 비교는 이미 구현돼 있다.

    logic_validator.py
    def _same_contained_fact(rule, llm):
        return (rule.axis_code == llm.axis_code
            and rule.source_role == llm.source_role
            and rule.normalized_value == llm.normalized_value
            ... )

그런데 걸리지 않는다. 정규값이 원문 전체라 서로 다르기 때문이다.

    {"text": "시 출연기관 위탁(보조)"}
    {"text": "수행방식: 시 출연기관 위탁(보조)"}

따라서 조건을 다시 정의하는 것으로는 해결되지 않는다. 기존 라벨 파서를
재사용해 "수행방식:" 같은 라벨 접두를 떼어낸 결정적 비교값을 만든 뒤
Rule tie-break 를 적용해야 한다. 무조건 긴 쪽을 남기는 방식은 최소 충분
Evidence 원칙과 Rule 중복제거 우선순위에 어긋나므로 쓰지 않는다.

6-2. test_retrieval 격리

test_sync_versioning_embedding_profile_and_exact_top_five 는
embed_current_announcements 로 DB 의 모든 현행 공고를 임베딩하는데,
가짜 벡터 fixture 에는 자기가 넣은 7건만 등록돼 있다. E2E 를 돌린 적 있는
DB 에서는 반드시 실패한다. 현재 로컬 DB 에 공고가 1,590건 있다.

해결책은 테스트 전용의 깨끗한 PostgreSQL DB 를 쓰는 것이다.
embed_current_announcements() 가 모든 현행 공고를 임베딩하는 것은 운영상
맞는 동작이므로 조회 범위를 테스트에 맞춰 좁히면 안 된다. 그렇게 하면
실제 동작을 검증하지 못하게 된다.

6-3. 골든 최소성 4건 — 사람 확인 필요
