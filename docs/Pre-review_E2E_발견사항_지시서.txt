2-2. source_role 은 어떻게 부여되는가  [rev.1 정정]

rev.1 은 "source_role 은 Rule 만 붙이고 LLM 은 축만 낸다" 고 썼다. 틀렸다.

logic_validator.py:465-471, LLM 근거를 접지할 때

    source_role = fragment.source_role
    if (
        source_role is None
        and occurrence.axis_code not in _QUANTITATIVE_AXES
        and occurrence.axis_code != CplAxisCode.PROGRAM_LEVEL_ABSENT
    ):
        source_role = _AXIS_SOURCE_ROLES.get(occurrence.axis_code)

Rule 이 붙인 role 이 우선하고, 없으면 축에서 보충한다. 정량 축과
PROGRAM_LEVEL_ABSENT 만 보충 대상에서 제외된다.

_AXIS_SOURCE_ROLES 는 26개 축을 담는다. 다만 PURPOSE_* 축은 하나도 없다.
따라서 사업목적 계열 근거는 Rule 이 라벨에서 붙여주지 않는 한 role 이 비고,
그것은 설계된 동작이다.

2-3. FIT-1 재분석  [rev.1 정정]

fit_engine.py:54-65

    좌  PURPOSE_GOAL           axis PURPOSE_TARGET_CONDITION   role frozenset({None})
    우  TARGET_AND_CONDITIONS  axis TARGET_GROUP               role TARGET

좌측 선택자는 role 로 None 을 요구한다. 즉 role 이 비어 있는 것이 정상이며
FIT-1 실패는 role 과 무관하다.

E2E 에서 사업목적에 붙은 축은 PURPOSE_SPECIFIC_OBJECTIVE 였다.
FIT-1 이 보는 축은 PURPOSE_TARGET_CONDITION 이다. 순수한 축 불일치다.

2-4. 지시

순서를 지킬 것.

  1) 문제 1 을 먼저 고친다.
  2) 같은 문서로 E2E 를 다시 돌린다.
  3) 그 후에도 남는 관계만 대상으로 판단한다.

판단할 때 먼저 답할 것은 "문서에 그 축이 실제로 있는가" 이다.

    문서에 정말 없다                → INSUFFICIENT 가 정답. 고칠 것 없음
    있는데 LLM 이 다른 축을 붙였다   → cpl-v0.2.txt 의 축 설명 보완
    FIT 선택자가 축을 과하게 좁혔다   → FIT 판별기준 원문과 대조 후 조정

PURPOSE_SPECIFIC_OBJECTIVE 와 PURPOSE_TARGET_CONDITION 은 다른 축이다.
FIT-1 이 부족하다는 이유만으로 전자를 FIT-1 선택자에 끼워 넣지 말 것.
사업목적 문장에 대상 제한 조건이 실제로 없다면 INSUFFICIENT 가 옳은 판정이다.

FIT 선택자를 손대려면 반드시 원문을 근거로 삼는다.
중소기업지원사업_PreReview_FIT_판별기준_정리본_20260821.md 가 유일한 기준이다.
구현기준서 10.1 은 요약이므로 근거로 쓰지 않는다.

FIT-4 는 설계상 항상 INSUFFICIENT 다. 건드리지 않는다.

3-1. 현상

Top-1 후보(유사도 81, 가장 유사한 공고)만 실패했다. 2~5위는 정상 판정됐다.

3-2. 왜 원인을 모르는가

backend/app/services/sim/sim_engine.py:320-325

    except LLMTimeoutError:
        failure_code = "LLM_TIMEOUT"
    except LLMUnavailableError:
        failure_code = "LLM_UNAVAILABLE"
    except (LLMInvalidResponseError, ValidationError, ValueError):
        failure_code = "LLM_INVALID_RESPONSE"

세 종류의 예외를 한 코드로 뭉갠다. 예외를 변수에 바인딩하지도 않는다.
sim_engine.py 에는 logger 자체가 없다.

더 중요한 것은 _ground_response() 가 try 블록 안에 있다는 점이다.
_ground_response() 는 다음 여섯 경우에 ValueError 를 올린다.

    SIM response contains duplicate request evidence
    SIM response contains duplicate candidate evidence
    SIM response contains invalid request evidence
    SIM response contains invalid candidate evidence
    Assessable SIM response requires evidence on both sides
    Non-SIMILAR SIM response requires a reason code

즉 LLM_INVALID_RESPONSE 라는 이름과 달리, 실제 원인이 LLM 응답 형식이 아니라
근거 접지 실패일 수 있다. 여섯 메시지가 이미 구분되어 있는데 전부 버려진다.

Top-1 후보가 가장 내용이 풍부해 LLM 이 근거를 많이 낸 결과 접지 검증에
걸렸을 가능성이 있다. 가설이며 확인하지 못했다.

3-3. 지시 — 최소 변경으로 진단만 먼저

  (1) 예외를 바인딩하고 WARNING 으로 기록한다.

        except (LLMInvalidResponseError, ValidationError, ValueError) as error:
            failure_code = "LLM_INVALID_RESPONSE"
            ...
        logger.warning(
            "SIM comparison failed rank=%s failure=%s error=%s: %s",
            rank, failure_code, type(error).__name__, error,
        )

      예외 유형과 예외 메시지까지만 남긴다. 공고 본문, 요청서 원문, LLM
      응답 본문은 남기지 않는다. 구현기준서 15 를 따른다.

  (2) 같은 입력으로 재실행해 실제 원인을 확인한다.

  (3) 원인이 접지 실패인지 스키마 오류인지 확인한 뒤에 고친다.
      지금 단계에서 프롬프트나 접지 규칙을 추측으로 바꾸지 않는다.

  (4) 접지 실패로 확인되면 재시도 여부와 reason_code 분리를 검토한다.
      판단이 필요하므로 확인 결과를 사용자에게 보고한 뒤 결정한다.
