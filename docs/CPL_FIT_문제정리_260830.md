## 문제 1. 라벨 블록의 범위가 정의되어 있지 않다 (최우선)

### 현상

CPL이 LLM 근거를 대량으로 버린다. 실행 로그:

```
CPL evidence dropped field=TARGET_AND_CONDITIONS kept=0 dropped=5 reasons=['FIELD_OWNERSHIP_UNRESOLVED']
CPL evidence dropped field=TARGET_AND_CONDITIONS kept=0 dropped=4 reasons=['FIELD_OWNERSHIP_UNRESOLVED']
CPL evidence dropped field=BUSINESS_NEED         kept=0 dropped=1 reasons=['FIELD_OWNERSHIP_UNRESOLVED']
CPL evidence dropped field=LINKED_POLICY         kept=0 dropped=1 reasons=['FIELD_OWNERSHIP_UNRESOLVED']
CPL evidence dropped field=PURPOSE_GOAL          kept=0 dropped=2 reasons=['FIELD_OWNERSHIP_UNRESOLVED']
CPL evidence dropped field=DELIVERY_SYSTEM       kept=0 dropped=2 reasons=['FIELD_OWNERSHIP_UNRESOLVED', 'NOT_VERBATIM']
```

골든 76건 중 놓친 42건의 대부분이 여기서 나온다.
지원조건 9종을 모두 기재한 문서인데 9줄이 전부 버려졌다.

### 원인

파서는 표 한 칸을 조각(fragment) 하나로 넘긴다. 이 문서의
`신설·변경 주요내용` 칸에는 라벨 항목이 여러 개 들어 있다.

```
○ (지원조건)                                  ← 라벨만 있고 값이 없음
- 지역: 부산광역시 내 본사 또는 주된 사업장 보유   ← CPL 필드 라벨이 아님
- 업종: 한국표준산업분류 C(제조업), J(정보통신업)
- 업력: 업력 3년 이상 10년 이내
...
```

귀속 로직(`_evidence_context`, logic_validator.py:851)은
인용 구간이 들어 있는 **한 줄** 안에서만 라벨을 찾는다.
`- 업력: …` 같은 하위 줄에는 CPL 필드 라벨이 없으므로 소속 필드를 정하지 못한다.
폴백은 "조각 전체의 소유 필드가 정확히 1개일 때"만 동작하는데,
이 칸의 소유 필드는 `DELIVERY_SYSTEM`, `NEW_OR_CHANGED_CONTENT`,
`SUPPORT_CONTENT_AND_SCALE`, `TARGET_AND_CONDITIONS` 넷이라 걸리지 않는다.

`ground_llm_response`(logic_validator.py:572)에서 다음 분기에 걸려 버려진다.

```python
if not owned_fields and occurrence.axis_code not in _UNSCOPED_SAFE_AXES:
    dropped.append("FIELD_OWNERSHIP_UNRESOLVED")
    continue
```

정량 축(`_UNSCOPED_SAFE_AXES`)만 이 검사를 우회하므로,
**의미 축만 선택적으로 죽는다.**

### 검증 결과

골든의 LLM 담당 근거 48건에 대해 현재 귀속 성공률은 38/48이다.
실패 10건은 전부 위 형태의 하위 줄이다.

```
IMPLEMENTATION_PLAN    - 1단계(2026~2027년): …          (○ (연차별·내역사업별 추진계획) 아래)
IMPLEMENTATION_PLAN    - 2단계(2028년): …
IMPLEMENTATION_PLAN    - 내역사업 「스마트 기술사업화 지원」: …
BUSINESS_NEED          - 근거자료: 2025년 부산 중소기업 실태조사…  (○ (사업필요성) 아래)
TARGET_AND_CONDITIONS  - 지역 / 업종 / 기업규모 / 인증 / 기타 / 제외조건  (6건)
```

다만 실제 실행에서는 `PURPOSE_GOAL`, `LINKED_POLICY`처럼
골든 인용으로는 귀속이 되는 필드도 탈락했다.
LLM이 골든과 다른 구간(라벨을 포함하거나 줄을 넘는 구간)을 인용했기 때문이다.
따라서 실제 손실은 10건보다 크다.

### 기대 동작

- 값이 비어 있는 라벨 줄의 범위를 **같은 조각 안의 다음 라벨 줄 직전까지**로 정의한다.
- 인용 구간은 그 구간을 포함하는 **가장 안쪽 라벨 블록**에 귀속시킨다.
- 표 행 라벨(`신설·변경 주요내용`)은 안쪽 라벨 블록이 없을 때의 폴백으로만 쓴다.
- 같은 규칙을 `semantic_fragments`(logic_validator.py:817)와
  `_evidence_context`(logic_validator.py:851) 양쪽에 적용한다.

### 검토했다가 폐기한 안

"파서가 조각을 라벨 경계로 분할한다"는 안은 두 가지 이유로 폐기했다.

1. 표 행 라벨(`NEW_OR_CHANGED_CONTENT`)의 소유권이 분할된 모든 하위 블록에
   그대로 복제되어 모호성이 남는다. `len(field_codes) == 1` 폴백이 여전히 안 걸린다.
2. `semantic_fragments`는 값이 빈 라벨을 만나면 `_adjacent_table_value`로
   **이웃 칸**을 가리킨다. 표 라벨 칸을 전제한 코드라 이 경우 틀린 가정이며,
   분할된 블록이 자기 자신을 claim하지 못한다.

즉 조각 구조를 바꾸는 문제가 아니라 해석 규칙이 비어 있는 문제다.

## 문제 2. 지원근거 정규화가 거의 동작하지 않는다

### 현상

`_normalize_legal_basis`(logic_validator.py:1599) 실측:

```
「중소기업진흥에 관한 법률」 제62조의2   → {'law_name': '중소기업진흥에 관한 법', 'article': None}
「중소기업기본법」 제2조                 → {'law_name': '중소기업기본법',        'article': None}
「부산광역시 중소기업 육성 및 지원 조례」 제9조  → None
「정보통신 진흥 및 융합 활성화 등에 관한 특별법」 제18조 → {'law_name': '…특별법', 'article': None}
중소기업진흥에 관한 법률 제62조          → {'law_name': '중소기업진흥에 관한 법', 'article': None}
```

세 가지가 동시에 깨져 있다.

1. `법률`이 `법`으로 잘린다.
2. **조문이 한 건도 추출되지 않는다.** 제62조의2, 제9조, 제2조, 제18조 전부 `None`.
3. **조례를 인식하지 못한다.** 지자체 사전협의라 조례가 근거인 경우가 흔하다.

### 왜 눈에 안 띄었나

필드 상태가 `PRESENT`로 나온다. 근거 원문은 남아 있고
정규값만 비어 있거나 잘려 있어서 겉으로는 정상으로 보인다.

### 기대 동작

CPL 판별기준 §8.1은 "조문이 있으면 조문까지 추출"을 요구한다.
`법률`, `법`, `조례`, `규칙`, `특별법` 등 법령 종류를 온전히 남기고,
`제N조`, `제N조의M` 형태의 조문을 추출한다. 골든셋의 기대값은 다음과 같다.

```json
{"law_name": "중소기업진흥에 관한 법률",            "article": "제62조의2"}
{"law_name": "부산광역시 중소기업 육성 및 지원 조례", "article": "제9조"}
```

## 문제 3. 사업기간 정규화가 표기 하나에만 맞춰져 있다

### 현상

`_normalize_period`(logic_validator.py:1479) 실측:

```
2026. 01. ~ 2028. 12.                   → {'start': '2026-01', 'end': '2028-12', 'continuing': False}
2026. 01. 01. ~ 2028. 12. 31.           → None
2026-01-01 ~ 2028-12-31                 → None
2026.1.1.~2028.12.31.                   → None
'21년 ~ '25년(5년)                      → None
2026년 1월 1일부터 2028년 12월 31일까지   → {'start': '2026', 'end': None, 'continuing': False, 'single_year': True}
```

다섯 표기 중 하나만 정상이다.
마지막 줄은 실패가 아니라 **3년 사업을 단년도로 기록**하므로 더 위험하다.

이 때문에 지금까지 돌린 모든 문서에서 `BUSINESS_PERIOD`가
`NEEDS_CONFIRMATION / VALUE_NOT_SPECIFIC`으로 나온다.
실제 요청서는 대부분 일자까지 쓴다.

### 기대 동작

`_PERIOD_PATTERN`(logic_validator.py:185)에 표기를 하나씩 덧붙이는 방식은
다음 표기에서 다시 깨진다. 날짜 토큰을 한 번 파싱해 시작·종료 양쪽에
재사용하는 구조로 바꾼다. 골든셋의 기대값:

```json
{"start": "2026-01-01", "end": "2028-12-31", "continuing": false, "multi_year": true}
```

CPL 판별기준 §5가 요구하는 것은 시작 시점·종료 시점·단년도/다년도/계속사업
여부이지 특정 표기가 아니다.

## 문제 4. 범위 조건을 둘로 쪼개 없는 모순을 만든다

### 현상

`상시 근로자 10명 이상 300명 미만`은 하나의 범위 조건인데
occurrence가 두 개 생긴다.

```
COND_HEADCOUNT  "상시 근로자 10명 이상"
COND_HEADCOUNT  "상시 근로자 10명 이상 300명 미만"
```

`_CONDITION_PATTERNS`(logic_validator.py:204)의 정규식이 첫 연산자에서 끊어
앞부분만 잘라내고, LLM은 전체 구간을 잡는다. 두 occurrence가 모두 남는다.

이전 실행(mockup_07)에서 FIT-5가 이를 근거로 `CONFLICT`를 냈다.
모델 설명: *"conditions include multiple conflicting headcount requirements
(5 or more, and between 5 and 300)"*. **모순이 없는 문서에 CONFLICT를 낸 오탐이다.**

### 구분

축을 정하는 것은 Rule의 몫이 맞다. `근로자 … 명`이라는 단위어가 축을 결정하므로
답이 하나로 고정된다. 틀린 것은 축이 아니라 **구간**이다.

### 기대 동작

범위를 한 구간으로 잡고 `min`/`max`로 정규화한다. 골든셋 기대값:

```json
{"min_count": 10, "max_count": 300, "min_operator": "GTE", "max_operator": "LT", "unit": "PERSON"}
{"min_years": 3, "max_years": 10, "min_operator": "GTE", "max_operator": "LTE", "unit": "YEAR"}
{"period_years": 3, "min_amount_won": 1000000000, "max_amount_won": 30000000000,
 "min_operator": "GTE", "max_operator": "LTE", "unit": "KRW"}
```

`_normalize_condition_value`(logic_validator.py:1292)도 함께 바뀌어야 한다.
현재는 연산자를 하나만 찾는다.

## 문제 5. LLM이 축을 붙이지 않는 건이 남아 있다

문제 1~4를 고쳐도 남는 부분이다. 귀속은 되는데 LLM이 축을 아예 안 붙인 경우다.

```
PURPOSE_GOAL       PURPOSE_DIRECTION, PURPOSE_SPECIFIC_OBJECTIVE, PURPOSE_PROBLEM_DOMAIN  (4건)
SUPPORT_ITEM       시제품 제작비 / 공인 시험인증비 / 판로개척 마케팅비                      (3건)
EXPECTED_EFFECTS   EFFECT_SUBJECT, EFFECT_CONTENT, EFFECT_DIRECTION, KPI_NAME 일부         (10건)
DELIVERY_STEP_ROLE 단계별 역할 3건
```

프롬프트(`backend/config/prompts/cpl-v0.8.txt`)의 COVERAGE 절 문제로 보인다.
다만 문제 1을 고치기 전에는 프롬프트 효과를 측정할 수 없다.
귀속에서 버려지는 건과 축을 안 붙이는 건이 섞여 있기 때문이다.

**따라서 문제 1을 먼저 고치고 재측정한 뒤에 프롬프트를 손대야 한다.**

## 문제 6. 계약에 자리가 없는 항목

골든셋을 작성하면서 담을 축이 없어 넣지 못한 항목이다.
코드 수정이 아니라 계약 결정이 필요하다.

1. **사업목적의 정량 표현** — 판별기준 §3.1이 확인 항목으로 두지만
   (예: `지원기업 100개사`) `PURPOSE_GOAL`에 정량값을 담을 축이 없다.
   이 문서의 `지원기업 120개사`가 어디에도 들어가지 못한다.
2. **성과지표의 측정시점** — 판별기준 §15.1의 구조화 후보인데 축이 없다.
   `측정시점 사업 종료 후 1년`을 담을 자리가 없다.
3. **occurrence의 묶음 표현** — `CplOccurrence`에 그룹 키가 없어
   `목표값 30%`가 어느 지표의 것인지 표현할 수 없다.
   성과지표 4개의 이름·목표값·기준연도가 서로 연결되지 않는다.
   같은 이유로 수행절차 7단계와 단계별 역할 3건이 짝지어지지 않아
   FIT-6이 단계별 역할을 제대로 대조하지 못한다.
4. **지원규모의 구역 문제** — 실제 양식은 지원기업수·단가를 지원내용 안에
   쓰게 하고 지원규모를 별도 구역으로 두지 않는다. 그래서 이 문서의 지원 정량값은
   `source_role`이 전부 `SUPPORT_CONTENT`다.
   지원내용 구역과 지원규모 구역을 대조하는 FIT-7의 설계와 맞지 않아
   FIT-7은 이 양식을 따른 문서에서 항상 단측이 된다.

## 재현 방법

```bash
# 1) DB 기동 (이미 떠 있으면 재사용)
bash scripts/e2e_up.sh

# 2) 서버
cd backend && python -m uvicorn main:app --host 127.0.0.1 --port 8000

# 3) 전체 파이프라인 1회 통과
python scripts/e2e_run.py "samples/hwpx/mockup_08_CPL전항목_스마트기술사업화.hwpx"
```

골든셋 대조는 `samples/golden/mockup_08.json`의 각 occurrence를
리포트 API(`/api/v1/cases/{case_id}/report`)의
`self_check.items[].occurrences[]`와 `(field_code, axis_code, excerpt)` 기준으로
맞춰보면 된다. 골든의 모든 `raw_text`는 파서 조각에 그대로 존재함을 검증했다.
