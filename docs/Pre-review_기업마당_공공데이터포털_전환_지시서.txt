1. 문제
--------------------------------------------------------------------------------

현재 클라이언트는 기업마당이 자체 운영하는 RSS API 를 호출한다.

    https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do
    파라미터  crtfcKey

이 엔드포인트는 기업마당이 직접 발급하는 인증키만 받는다. 발급받으려면
기업마당 사이트에서 별도 신청해야 하고, 신청 시 시스템 IP 또는 시스템 URL 을
등록해야 하며 키가 그 출처에 묶인다.

현재 로컬 .env 에 들어 있는 키는 공공데이터포털(data.go.kr) 발급 키다.
이 키로 위 엔드포인트를 호출하면 다음이 돌아온다.

    {"reqErr":"존재하지 않는 인증키 입니다."}

키가 잘못된 것이 아니라 인증체계가 다른 서비스를 호출하고 있는 것이다.

영향 범위

    실제 공고를 사용하는 동기화가 되지 않는다. 따라서 실제 코퍼스로는
    Retrieval 을 검증할 수 없다.

    목업 공고 6건을 넣은 상태의 E2E 는 이미 통과했다. 파이프라인 자체가
    막혀 있는 것은 아니다.

2. 확인한 사실 — 두 API 는 같은 데이터다
--------------------------------------------------------------------------------

공공데이터포털에도 같은 기업마당 지원사업 공고가 REST API 로 열려 있다.

    https://apis.data.go.kr/1421000/bizinfo/pblancBsnsService
    파라미터  serviceKey, dataType, pageNo, numOfRows

실제로 호출해 응답을 받아 확인했다.

    resultMsg    NORMAL_SERVICE
    totalCount   1551      (2026-08-27 관측값. 계약이 아니다)
    numOfRows    500 수신 확인 (관측값. 영구 보장으로 단정하지 않는다)

응답 아이템의 필드명이 현재 _parse_item() 이 읽는 필드와 일치한다.
아래 20개 필드가 하나도 빠짐없이 그대로 온다.

    pblancId          pblancNm          pblancUrl
    jrsdInsttNm       excInsttNm        bsnsSumryCn
    creatPnttm        updtPnttm         reqstBeginEndDe
    trgetNm           inqireCo          hashtags
    reqstMthPapersCn  refrncNm          rceptEngnHmpgUrl
    flpthNm           fileNm            printFlpthNm
    printFileNm       pldirSportRealmLclasCodeNm

PublicAnnouncement 는 이 20개에 raw_payload 를 더해 21개 필드를 갖는다.

특히 bsnsSumryCn(본문 HTML)이 온다. 이것이 중요한 이유는 아래와 같다.

    announcement_sync.py:210-212
        summary_text = _html_to_text(source.summary_html)
        purpose = parts[0] ...

    compose_embedding_text()
        공고명 / 사업목적 / 지원대상 / 지원내용 / 해시태그

purpose, target, content 는 전부 summary_html 하나를 쪼개서 만든다.
본문이 없으면 임베딩이 공고명과 해시태그만 남아 Retrieval 품질이 무너진다.
공공데이터포털의 다른 기업마당 공개분(3034791 등)은 파일데이터(CSV)이고
본문이 없다. 반드시 위 pblancBsnsService 오퍼레이션을 써야 한다.

또한 _optional(item, "hashTags", "hashtags") 로 이미 소문자 별칭을 함께
보고 있어 해시태그도 그대로 잡힌다.

3. 왜 이 방향으로 고치는가
--------------------------------------------------------------------------------

선택지는 둘이었다.

    A. 기업마당 자체 인증키를 새로 발급받고 코드는 그대로 둔다
    B. 공공데이터포털 API 로 클라이언트를 바꾼다

B 를 택한다.

    - 키가 이미 있다. 발급 신청과 승인 대기가 없다.
    - IP / 시스템 URL 등록이 필요 없다. A 는 개발 PC, 발표장 회선, 배포 서버가
      바뀔 때마다 등록 문제가 생긴다.
    - 응답 필드가 일치하므로 정규화 계층을 손대지 않아도 된다.
    - 본문이 오는 것을 실제 호출로 확인했다.

바꾸는 범위가 클라이언트 어댑터 한 파일이다. 포트와 도메인은 그대로다.
이것이 ports/adapters 구조를 쓴 이유이므로 그 경계를 넘지 않는다.

4. 변경 내용
--------------------------------------------------------------------------------

4-1. 인증키 계약

  BIZINFO_API_KEY 에는 공공데이터포털의 **디코딩 키** 를 저장한다.
  쿼리 파라미터 인코딩은 HTTP 클라이언트가 담당한다.

  공공데이터포털은 인코딩 키와 디코딩 키를 함께 표시한다. 이미 URL 인코딩된
  키를 httpx 의 params 에 넣으면 % 가 다시 인코딩되어 인증에 실패한다.
  이 계약을 .env.example 주석에 적는다.

  실제 키 값은 로그, 테스트, Git 어디에도 남기지 않는다.

4-2. 요청 파라미터

  현재 (list_current_announcements 안)

      params={
          "crtfcKey": self._api_key,
          "dataType": "json",
          "searchCnt": "0",
      },

  변경

      params={
          "serviceKey": self._api_key,
          "dataType": "json",
          "pageNo": <페이지 번호>,
          "numOfRows": <페이지 크기>,
      },

4-3. 응답 봉투와 결과 코드

  현재

      channel = body["jsonArray"]
      items = channel.get("item", [])

  변경

      items = body["response"]["body"]["items"]["item"]

  items 가 dict 단건으로 오는 경우 리스트로 감싸는 기존 처리는 유지한다.
  공고가 0건이면 items 키가 없거나 빈 문자열로 올 수 있다. 그 경우 빈
  리스트로 처리하고 예외를 올리지 않는다.

  header.resultCode 를 다음과 같이 나눈다. 모두 Invalid 로 처리하면 안 된다.

      "00"          정상
      "05"          서비스 타임아웃  → 제한된 재시도 후 PublicDataTimeoutError
      "23"          초당 호출량 초과  → 제한된 재시도 후 PublicDataUnavailableError
      "22"          일일 호출량 초과  → 재시도하지 않고 PublicDataUnavailableError
      "20" "30"     권한·키 문제      → PublicDataUnavailableError. 재시도하지 않는다
      그 외 / 파라미터 오류            → PublicDataInvalidResponseError
      응답 구조 자체가 깨짐            → PublicDataInvalidResponseError

  resultMsg 는 로그에 남기되 serviceKey 는 절대 남기지 않는다.

  재시도하지 않아야 할 코드에 재시도를 걸면 일일 한도를 더 빨리 소진한다.

4-4. 페이징

  현재는 한 번만 호출하고 끝난다. 총 건수가 페이지 크기보다 크므로 그대로
  두면 일부만 들어온다.

  종료 조건을 다음과 같이 둔다.

      - body.totalCount 를 읽되 목표치로만 쓴다. 동기화 중 신규 공고가
        추가되면 값이 변할 수 있다.
      - 응답으로 돌아온 실제 numOfRows 를 기준으로 다음 페이지를 계산한다.
        요청한 값과 다를 수 있다.
      - 빈 페이지가 오면 중단한다.
      - 같은 pblancId 집합만 반복되면 중단한다.
      - 수집 결과를 pblancId 기준으로 중복 제거한다.
      - 최대 페이지 수 상한을 둔다. 무한 루프를 막는다.

  numOfRows 기본값은 상수로 둔다. 설정으로 뺄지는 판단에 맡긴다.
  1551 이나 500 을 코드나 테스트에 고정하지 않는다.

  기존 429 / 5xx 재시도 로직은 페이지 단위로 유지한다.
  페이지 사이에 짧은 간격을 둔다. 포털은 호출 한도가 있다.

4-5. 설정 파일

  .env.example 의 BIZINFO_API_URL 을 바꾼다.

      BIZINFO_API_URL=https://apis.data.go.kr/1421000/bizinfo/pblancBsnsService

  주석의 "기업마당" 표현을 "공공데이터포털" 로 정정하고, 디코딩 키를
  넣어야 한다는 4-1 계약을 적는다.

  BIZINFO_API_KEY 라는 이름은 그대로 둔다. 설정 키 이름을 바꾸면 config.py 와
  sync_bizinfo.py 까지 번지므로 이번 범위를 넘는다.

  실제 .env 는 건드리지 않는다. 사용자가 직접 바꾼다.

6. 테스트
--------------------------------------------------------------------------------

backend/tests/test_retrieval.py 의 MockTransport 스텁이 옛 봉투를 쓴다.
아래 세 곳을 새 응답 형태로 바꾼다.

    86-87행    json={"jsonArray": { ... }}
    127행      같은 형태
    160행      httpx.Response(200, json={"jsonArray": {"item": []}})

새 형태

    {"response": {
        "header": {"resultCode": "00", "resultMsg": "NORMAL_SERVICE"},
        "body": {"totalCount": <n>, "pageNo": 1, "numOfRows": <n>,
                 "items": {"item": [ ... ]}}}}

추가할 테스트

  (1) 페이징 — totalCount 가 페이지 크기보다 클 때 모든 페이지를 모아
      전체를 반환하는지. 스텁이 pageNo 별로 다른 아이템을 돌려주게 한다.
  (2) 중복 제거 — 페이지가 겹쳐 같은 pblancId 가 와도 한 번만 남는지.
  (3) 빈 페이지에서 중단하는지.
  (4) resultCode "22" 는 재시도 없이 실패하는지.
  (5) resultCode "05" / "23" 은 재시도 후 실패하는지.
  (6) 공고 0건일 때 예외 없이 빈 리스트를 반환하는지.
  (7) 응답 구조가 깨졌을 때 PublicDataInvalidResponseError 인지.

테스트에 실제 키를 쓰지 않는다. MockTransport 로만 검증한다.

기존 재시도 / 타임아웃 / HTTP 오류 테스트는 그대로 통과해야 한다.

7. 이후 단계 — 어댑터 작업과 분리한다
--------------------------------------------------------------------------------

아래는 어댑터 수정이 끝난 뒤의 별도 작업이다. 같은 커밋에 섞지 않는다.
어댑터 단위 테스트를 위해 DB 를 초기화할 이유는 없다.

    1) MockTransport 계약 테스트 통과            ← 6절
    2) 실제 API 1페이지 smoke test
       키를 출력하지 않고 소량만 받아 필드가 오는지 확인한다.
    3) 페이징 전체 수집 확인
       수집 건수와 totalCount 를 대조한다.
    4) 임베딩 예상 비용·시간 산정
       건수 × 본문 길이로 가늠한다. 사용자에게 보고하고 승인받는다.
    5) E2E 전용 DB 초기화
       scripts/e2e_down.sh → e2e_up.sh
       현재 DB 에는 목업 공고 6건이 있다. pblanc_id 가 MOCK- 로 시작한다.
       섞이면 SIM 후보 Top-5 에 목업이 올라온다.
    6) 실제 코퍼스 동기화 및 임베딩

임베딩 프로필은 첫 실행에 고정되며 이후 변경하려면 프로필 v2 와 전체
재임베딩이 필요하다. 4) 에서 설정값이 최종인지 함께 확인한다.
