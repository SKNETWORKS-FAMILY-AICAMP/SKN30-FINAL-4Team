0. 저장본과 API 응답의 차이
================================================================================

  inspection_report.report_json   아래 구조에서 report_download_url 을 제외한 것
  GET /cases/{id}/report          저장본 + report_download_url 을 동적으로 조립

AGENTS.md §5 가 명시한다.

    report_download_url 은 저장된 report_json 에 넣지 않고
    결과 조회 API 에서 동적으로 조립한다.

PDF 는 리포트 확정 이후 생성될 수 있으므로 불변 저장본에 넣으면 안 된다.
inspection_report 는 DDL 트리거로 UPDATE 가 금지되어 있다.

1. 최상위 구조
================================================================================

구현기준서 §13.1 의 키를 그대로 쓴다. 순서도 유지한다.

{
  "schema_version": "alpha-report-v0.1",
  "case": { ... },
  "ui_status": "COMPLETED",
  "self_check": { ... },
  "structural_consistency": { ... },
  "review_issues": [ ... ],
  "similar_candidates": [ ... ],
  "ben_references": [],
  "differences": [ ... ],
  "warnings": [ ... ],
  "report_download_url": null
}

** ben_references 는 알파에서 항상 빈 배열이다. **
구현기준서 §13.1 이 키를 명시하므로 자리는 유지한다.
BEN 은 알파 범위에서 제외하기로 했다(기준서 §4.2 부분 구현 허용).
프론트는 이 블록을 그리지 않는다.

6. review_issues  —  식별된 검토 쟁점
================================================================================

프론트 전달사항 §5 · 화면변경사항 §11-4 · 구현기준서 §17.3

** 백엔드가 집계한다. **
기준서 §17.3: "중복 저장 테이블을 만들지 않고 불변 report_json.review_issues 에 집계한다"

[
  {
    "issue_id": "CPL:TARGET_AND_CONDITIONS",
    "source": "CPL",
    "source_ref": "TARGET_AND_CONDITIONS",
    "source_label": "CPL-10",
    "title": "지원대상 기준 정보 부족",
    "description": "기업 규모와 업력 조건이 명확하지 않습니다.",
    "recommendation": "지원 가능한 기업의 규모·업력 조건을 확인하세요.",
    "sort_rank": 3,
    "evidence": [ Evidence x n ]
  }
]

  source        "CPL" | "FIT" | "SIM"
  source_label  화면 표시용 짧은 라벨. 프론트 §5.3 의 "출처: CPL-10" 형태.
                SIM 은 "SIM / 후보 1번".
  sort_rank     프론트 §5.4 정렬 순서를 백엔드가 계산해 넣는다.
                  1  불일치        CONFLICT
                  2  누락          MISSING
                  3  검토 필요·정보 부족  NEEDS_REVIEW · NEEDS_CONFIRMATION
                  4  판단 불가·파싱 실패  INSUFFICIENT · PARSE_FAILED
                프론트는 sort_rank 오름차순 정렬만 하면 된다.

** 심각도를 넣지 않는다. **
프론트 §5.2 가 심각 T1 · 검토 T2 · 높음·중간·낮음을 전부 금지했다.
사용자 표시 라벨은 전부 "검토 필요" 하나다.

수집 대상
  CPL   status ∈ {MISSING, NEEDS_CONFIRMATION, PARSE_FAILED}
  FIT   status ∈ {CONFLICT, NEEDS_REVIEW, INSUFFICIENT}
  SIM   후보별 축 status ∈ {PARTIAL, DIFFERENT} 중 differences 가 있는 것

  ** NOT_APPLICABLE 은 쟁점이 아니다. **
  프론트 §3.2: "누락, 정보 부족, 해당 없음은 분석 실패가 아니라 정상 결과"
  다만 "해당 없음" 은 보완할 것이 없으므로 쟁점 목록에서 제외한다.

12. ** Slice 10 전에 결정해야 할 문제 **
================================================================================

--------------------------------------------------------------------------------
12-1. Retrieval 실패가 전체 분석 실패로 처리된다
--------------------------------------------------------------------------------
현재 코드:

    analysis_pipeline._record_retrieval_failure()
        UPDATE sims.inspection_case SET status = 'FAILED' ...

그리고 임베딩 클라이언트가 없을 때도 이 경로를 탄다.

    if client is None:
        _record_retrieval_failure(engine, case_id, "RETRIEVAL_UNAVAILABLE")

즉 ** OPENAI_API_KEY 없이 돌리면 모든 분석이 "분석 실패" 로 끝난다. **
CPL 이 성공했어도 마찬가지다.

이는 두 계약과 어긋난다.

    ADR-005
      문서 파싱 자체가 실패하면 분석 실패다.
      CPL/FIT/SIM 중 일부만 실패하면 가능한 결과는 생성하고
      전체는 분석 완료로 표시한다.

    프론트 전달사항 §8.2
      Retrieval 실패 → Top-5 카드에 분석 실패 경고.
                      후보가 없으므로 SIM 도 판단 불가
      (화면 전체는 "분석 완료")

그리고 Slice 10 을 막는다.

    inspection_report.retrieval_run_id  bigint NOT NULL

리포트를 만들려면 retrieval_run 행이 있어야 하는데,
임베딩이 실패하면 retrieve_top_five() 가 그 행을 만들기 전에 끊긴다.

선택지
  (a) Retrieval 실패 시 case 를 FAILED 로 만들지 않고 경고만 남긴다.
      warnings 에 scope=RETRIEVAL 로 넣고 REPORTING 으로 진행한다.
      DDL 의 retrieval_run_id NOT NULL 을 만족시키려면
      실패해도 retrieval_run 행을 status=FAILED 로 먼저 만들어야 한다.
  (b) DDL 을 바꿔 retrieval_run_id 를 nullable 로 한다.
      ** AGENTS.md §5 가 DDL 완화를 금지하므로 사용자 확인 없이 하지 않는다. **

(a) 를 권장한다. ADR-005 와 프론트 §8.2 를 둘 다 만족하고 DDL 을 안 건드린다.

--------------------------------------------------------------------------------
12-2. CPL 실패도 같은 문제가 있다
--------------------------------------------------------------------------------
    _record_cpl_failure()  →  status = 'FAILED'

ADR-005 상 CPL 실패도 "분석 완료 + 해당 블록 판단 불가" 여야 한다.
다만 inspection_report.missing_check_run_id 도 NOT NULL 이라
CPL 이 저장되지 않으면 리포트를 만들 수 없다.

알파 범위에서는 CPL 실패를 FAILED 로 두는 것도 방어적으로 타당하다.
CPL 은 FIT·Retrieval·SIM 전부의 입력이므로 실패하면 남는 결과가 거의 없다.

** 12-1 과 12-2 를 같이 결정한다. 사용자 확인 대상이다. **

13. 프론트에 물을 것  —  두 개뿐
================================================================================

  1. 상태값을 코드값으로 받는 것이 맞는가
     이 초안은 PRESENT · MISSING · NEEDS_REVIEW 처럼 코드값을 준다.
     프론트가 §3.2 · §4.3 의 매핑표로 한글로 바꾼다.
     지금 GET /cases/{id}/status 는 한글("분석 중")을 주고 있어 표기가 섞여 있다.
     통일할지 함께 정한다.

  2. PDF 생성 전·중·완료를 화면이 구분하는가
     구분한다면 report_download_url 외에 pdf_status 필드가 필요하다.
     완료된 것만 링크가 뜨면 되면 null 여부로 충분하다.

나머지는 문서에 근거가 있으므로 통보만 하면 된다.

  - CPL 확인율 = (PRESENT + NOT_APPLICABLE) / 13     사용자 확정
                 화면변경사항 §13-1 의 미확정 항목이 해소됐다
  - 분석 건 삭제 알파 제외                            프론트 전달사항 §11
                 화면변경사항 §9 · §12 의 삭제 항목은 폐기된 것이다
  - BEN 참고정보 블록 알파 제외                       화면변경사항 §11-6 제외

15. 구현 시 지킬 것
================================================================================

  - report_json 은 불변이다. inspection_report 에 UPDATE 금지 트리거가 있다.
    재분석은 새 inspection_case 를 만든다(구현기준서 §8.2).
  - report_download_url 은 저장하지 않는다(AGENTS.md §5).
  - PDF 는 저장된 같은 report_json 으로 생성한다(프론트 §10.2).
    PDF 를 위해 별도 데이터를 다시 조회하지 않는다.
  - 버전 문자열은 DB 실행 레코드와 프로필에서 가져온다.
    Composer 에서 새로 만들지 않는다(AGENTS.md §5).
  - 금지 표현을 JSON 에 담지 않는다(프론트 §12).
    심각도 · 중복 확률 · 적합/부적합 · 승인 가능성 · 차별성 판정
