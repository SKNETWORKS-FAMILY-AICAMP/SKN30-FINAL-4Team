# Pre-review 챗봇 초기 화면 요구사항 v1.0

프론트는 다른 담당자가 작업 중이라 이 문서는 **요구사항 전달용**이다. 챗봇 작업자는
`frontend/` 를 직접 수정하지 않았다.

---

## 1. 기존 구현 확인 결과 (2026-09-10)

`frontend/src` 를 `안녕하세요 / 궁금한 / placeholder / suggested / example / welcome /
empty / initial / quick / prompt` 로 검색한 결과다.

| 기능 | 현재 상태 | 위치 |
|---|---|---|
| 초기 안내 문구 | **있음 (형태가 다름)** | `features/result/AiChat.tsx:22` |
| 예시 질문 (chip/quick prompt) | **없음** | — |
| 입력창 placeholder | **있음 (문구가 다름)** | `features/result/AiChatView.tsx:100` |

### 초기 안내 문구

지금은 안내 문구가 **assistant 말풍선 하나로** 들어가 있다.

```tsx
// AiChat.tsx
const [messages, setMessages] = useState<ChatMessage[]>([
    { id: '1', sender: 'ai', text: "분석 결과에 대해 궁금한 점을 물어보세요." }
])
```

DB 에 저장되지는 않지만 대화 목록의 첫 항목이라, 이전 대화를 불러오면 실제 이력 위에
가짜 말풍선이 얹힌다. **초기 UI 영역으로 분리**하는 편이 낫다 — 대화가 시작되면
숨기면 된다.

### 입력창 placeholder

```tsx
// AiChatView.tsx
placeholder="질문을 입력하세요..."
```

## 2. 요청사항

### 2.1 초기 안내 문구

대화 이력이 없을 때만 보여준다.

```text
안녕하세요! 리포팅에서 궁금한 것이 있으신가요?
```

실제 대화 이력에 저장되는 assistant message 가 아니라 **초기 UI 안내 문구**로
처리한다. 사용자가 질문을 보냈거나 기존 이력이 있으면 이 영역을 숨긴다.

기존 말풍선을 지우고 새로 만들 필요는 없다. 지금 구조를 유지하면서 문구만 맞춰도
되고, 초기 UI 로 분리하면 더 낫다.

### 2.2 예시 질문 (새로 추가)

안내 문구 아래에 클릭 가능한 예시 질문 5개를 둔다. 단순 placeholder 문자열이 아니라
chip/card 형태를 권장한다.

```text
[ 확인이 필요한 부분을 알려줘 ]
[ 내용이 서로 맞지 않는 부분이 있는지 봐줘 ]
[ 비슷한 기존 사업과 어떤 차이가 있는지 알려줘 ]
[ 전체 리포트를 5줄로 요약해줘 ]
[ 수정이 필요한 부분을 제안해줘 ]
```

**내부 이름(CPL·FIT·SIM)을 쓰지 않는다.** 사용자는 그 이름을 모른다. 업무
자연어만으로 필요한 결과가 골라진다.

- 배경은 반투명, 일반 말풍선보다 약한 대비
- hover 시 선택 가능한 느낌
- 클릭하면 입력창에 채워지거나 바로 전송
- 첫 화면에서만 노출, 대화 시작 후 숨김
- 디자인은 기존 프론트 스타일을 유지한다

이 5개는 요청자료 점검 · 정합성 · 유사사업 비교 · 전체요약 · 수정제안을 각각
대표하도록 고른 것이다.
바꾸려면 그 다섯 범위가 유지되는지 확인이 필요하다(3절 참조).

### 2.3 입력창 placeholder

```text
리포트에 대해 궁금한 내용을 입력해 주세요.
```

초기 예시 질문과 역할이 다르다. 예시 질문은 **무엇을 물어볼 수 있는지** 보여주고,
placeholder 는 **직접 입력하도록** 안내한다.

## 3. 예시 질문 5개는 실제로 검증했다

`chatmessage/scripts/run_chat.py` 로 다섯 질문을 모두 실행했다. 각 질문이 의도한
결과 섹션을 읽는지, 답변이 다른 결과와 섞이지 않는지 확인한 값이다.

| 예시 질문 | 읽은 결과 섹션 | 수정 제안 |
|---|---|---|
| 확인이 필요한 부분을 알려줘 | `cpl` | — |
| 내용이 서로 맞지 않는 부분이 있는지 봐줘 | `fit` | — |
| 비슷한 기존 사업과 어떤 차이가 있는지 알려줘 | `retrieval` `sim` | — |
| 전체 리포트를 5줄로 요약해줘 | 전체 8개 | — |
| 수정이 필요한 부분을 제안해줘 | 전체 8개 | 생성됨 |

전부 근거(`references`)가 생성됐고 grounding 경고는 없었다. 답변도 업무 언어로
나왔다 — "요청서의 필수 항목과 구조를 점검한 결과…", "사업 목적과 지원대상 간의
정합성을 확인한 결과…".

> 읽은 섹션은 **저장된 분석 결과 중 고른 것**이지 실행한 Agent 목록이 아니다.
> CPL·FIT·SIM·Model 은 분석 단계에서 이미 돌았고 챗봇은 다시 실행하지 않는다.

재현:

```bash
python chatmessage/scripts/run_chat.py \
  --fixture chatmessage/fixtures/sample_full_context.json \
  --sample-questions
```

## 4. 응답 계약 — 화면이 그려야 하는 것

말풍선 하나에 다음이 딸린다. POST 응답과 GET 이력이 같은 모양이다.

```json
{
  "id": 3,
  "role": "ASSISTANT",
  "content": "FIT 분석에서는 목적과 지원대상의 연결을 추가로 확인할 필요가 있습니다.",
  "references": [
    { "agent": "FIT", "item": "FIT-1", "evidence_id": "request:PURPOSE_GOAL:0" }
  ],
  "suggested_revision": "지원대상을 다음과 같이 구체화하는 방안을 검토할 수 있습니다."
}
```

`suggested_revision` 은 **답변과 시각적으로 구분해서** 그린다. 분석 결과와 AI 의
제안이 같은 판정처럼 보이면 안 된다.

```text
[일반 분석 답변]

------------------------
수정·보완 제안
"지원대상을 ... 형태로 구체화하는 방안을 검토할 수 있습니다."

※ 검토 후 반영 여부는 사용자가 직접 결정합니다.
------------------------
```

`references[].agent` 는 내부 코드값이다. **답변 본문에는 이 이름이 나오지 않는다** —
근거 표시에만 쓰고, 화면 이름은 따로 붙인다.

| agent | 화면 이름 |
|---|---|
| `CPL` | 요청자료 점검 |
| `FIT` | 내부 정합성 |
| `RETRIEVAL` | 유사공고 검색 |
| `SIM` | 유사공고 비교 |
| `MODEL_1` | 지원유형 모델 |
| `MODEL_2` | 지원규모 모델 |
| `MODEL_3` | 이례성 참고 |
| `SUMMARY` | 종합 |

`evidence_id` 가 `null` 인 것은 문서 인용이 없는 결과(ML 예측값 등)다. 오류가 아니다.

## 5. 구조 — 챗봇은 분석을 다시 하지 않는다

```text
[분석 단계]  요청서 → Parser → CPL/FIT/Retrieval/SIM/Model 1·2·3 → 결과 저장
[챗봇 단계]  질문 → 필요한 결과 섹션 선택 → Chat Context → 하나의 Chat LLM
```

화면·안내 문구에서 "AI 가 다시 분석합니다" 같은 표현을 쓰지 않는다. 챗봇은 이미
나온 리포트를 읽고 설명하는 기능이다.

---

## 6. 아직 연결되지 않은 것

챗봇 코어(`chatmessage/`)와 FastAPI Chat API 는 있지만, 화면에서 실제로 답이 오려면
남은 것이 있다.

- Model 1·2·3 결과의 영속 저장 구조가 확정되지 않았다. 지금은 `not_available` 로
  답한다(챗봇은 그 상태를 구분해서 안내한다).
- 프론트 `chatService` 는 현재 Supabase Edge Function 을 부른다. FastAPI 로 옮기는
  시점은 별도 결정 사항이다.

초기 화면 UI 는 위 두 가지와 무관하게 먼저 만들 수 있다.
