## 1. 어떻게 짰나

### 기술 스택

```
FastAPI                   API
PostgreSQL 15 + pgvector  DB · 벡터 검색
SQLAlchemy Core           raw text() SQL. ORM 안 씀
Pydantic v2               스키마 · 검증
OpenAI                    gpt-4o-mini · text-embedding-3-small
reportlab                 PDF
```

ORM 을 안 쓴 이유는 DDL 이 트리거·CHECK·부분 인덱스를 많이 쓰는 설계라
ORM 추상화가 오히려 방해가 되기 때문이다.

### 구조 — 모듈형 모놀리스 + 포트/어댑터

```
app/api/v1/          라우터 (auth, cases, analyze, report, chat)
app/services/        도메인 로직 (cpl, fit, retrieval, sim, report, chat)
app/ports/           인터페이스
app/infrastructure/  바깥 세계 구현체
app/schemas/         Pydantic 계약
app/db/              스키마 SQL · 세션
app/parsers/         HWP/HWPX 파서
```

| 포트 | 어댑터 |
|---|---|
| `DocumentParser` | `RhwpDocumentParser` (rhwp-python) |
| `LLMClient` | `OpenAILLMClient` |
| `EmbeddingClient` | `OpenAIEmbeddingClient` |
| `PublicDataClient` | `BizinfoPublicDataClient` (공공데이터포털) |
| `ObjectStorage` | `LocalObjectStorage` |
| `PdfRenderer` | `ReportlabPdfRenderer` |
| `JobDispatcher` | `InProcessJobDispatcher` |

이 구조가 실제로 값을 했다. 공고 API 를 기업마당 자체 RSS 에서 공공데이터포털로
바꿀 때 **어댑터 한 파일만 고쳤다.** 도메인 로직과 DB 는 손대지 않았다.

### 핵심 설계 결정 셋

**근거는 전부 원문 위치로 고정한다.** 모든 판정에 `evidence_ref` 가 붙는다.
요청서 쪽은 `block_id:cell:row:col` 로 표 셀 단위까지 특정한다. LLM 이 만들어낸
문장이 아니라 문서에 실제로 있는 문자열이라는 걸 검증한다(grounding).

**LLM 은 값을 만들지 않는다.** LLM 은 "이 문장이 무슨 축인가"만 태깅한다.
숫자·기간 같은 값 추출은 Rule 이 한다.

**모든 결과에 버전을 박는다.** `ruleset_version` · `prompt_version` ·
`scoring_version` · `model_profile` 이 리포트에 들어간다. 모델이나 프롬프트를
바꿨을 때 결과를 비교할 수 있다.

### 에이전트 구조

```
파싱 → CPL ─┬─→ FIT ──────────────┐
            │                      ├─→ Report → (Chat: 질문마다)
            └─→ Retrieval → SIM ──┘
```

| 단계 | 하는 일 | LLM |
|---|---|---|
| 파싱 | HWPX → 블록 · 표 셀 | 없음 (코드) |
| **CPL** | 13개 항목 추출 · 판정 | 1회 |
| **FIT** | 7개 관계 정합성 판정 | 1회 |
| Retrieval | pgvector 코사인 Top-5 | 없음 (임베딩만) |
| **SIM** | 후보별 4축 비교 | 5회 |
| Report | report_json + PDF 조립 | 없음 (코드) |
| **Chat** | 저장된 결과만 근거로 답변 | 질문당 1회 |

**FIT 과 Retrieval 은 형제다.** 둘 다 CPL 결과만 받고 서로를 안 본다.
FIT 결과를 쓰는 곳은 Report 하나뿐이다. 순서와 조립은 `analysis_pipeline.py` 가
코드로 관리하며 **오케스트레이터 LLM 은 없다.**

실측 토큰 (분석 1건, 최대 7회 호출)

```
cpl_semantic_evidence      3,700~4,900 토큰   11초
sim_candidate_comparison   약 2,600 × 5       각 4~6초
result_grounded_chat      25,000~29,000 토큰   4~7초   ← 질문 1회당
fit_internal_consistency   근거가 없으면 호출 자체를 안 한다
```

**Chat 하나가 나머지를 합친 것보다 크다.** 리포트 전체를 컨텍스트로 넣는다.

### 임베딩

문서 1건 = 벡터 1개. **청킹 없다.**

```
공고     공고명 · 사업목적 · 지원대상 · 지원내용 · 해시태그
요청서   사업목적 · 지원대상 · 지원내용
```

양쪽을 같은 라벨 형식으로 조립해야 코사인 거리가 의미를 갖는다.
실제 공고 100건을 재보니 평균 474자 · 최대 936자로 8000자 한도에 한참 못 미쳐
**쪼갤 게 없다.** 첨부 공고문 전문을 넣기 시작하면 그때 청킹이 필요해진다.

## 4. 왜 문제가 생기는가 — 근본 원인

증상 11개가 5개 원인으로 묶인다.

### 원인 1 — 조각을 셀 단위로 자르면서 "한 셀 = 한 역할" 을 가정했다

가장 크다. FIT 문제 대부분이 여기서 파생된다.

```python
source_role = next(iter(roles[...])) if len(roles[...]) == 1 else None
```

한 조각에서 역할이 **둘 이상 보이면 포기**한다. 그런데 24년도 서식은 한 셀에
여러 개념을 몰아넣는다.

```
신설·변경 주요내용 셀 (444자)
  ○ (사업기간) ...   ○ (사업예산) ...   ○ (지원대상) ...
  ○ (지원조건) ...   ○ (지원규모) ...   ○ (지원내용) ...
  ○ (수행기관) ...
```

실측: 조각 22개 중 최대 444자, 그 조각에서 역할 5개가 감지되어 `None` 이 됐다.

여기서 네 가지가 동시에 터진다.

```
role 0개          FIT 이 요구하는 axis + role 조합이 성립하지 않음
LLM 저커버리지     444자 안 8개 개념 중 1~2개만 태깅
인용 실패          긴 조각에서 정확 인용이 어려움 (NOT_VERBATIM 이 이 필드에서 발생)
값 뭉침            Rule 이 셀 전체를 한 값으로 잡음
```

**괄호 라벨 수정이 이걸 드러냈다.** 수정 전에는 `○ (지원대상)` 이 매칭되지 않아
역할이 하나만 보였고, 수정 후에는 다섯이 보여 포기한다.

```
수정 전   role 부여 1개 · 역할충돌 포기 0개
현재      role 부여 0개 · 역할충돌 포기 2개
```

CPL 근거와 축은 늘었는데 role 은 오히려 사라졌다. FIT-5 가 살아난 것은 Rule 이
아니라 **LLM 축에서 파생된 role** 덕분이다.

### 원인 2 — LLM 출력을 "검증 게이트" 로 다뤘다

부분 정답을 허용하지 않았다.

```
CPL   인용 1건 어긋남 → 13개 항목 전부 폐기     고침. 1/3 → 3/3
SIM   reason_code 1개 누락 → 후보 통째 폐기     아직. raise 11곳
```

LLM 은 확률적으로 부분 정답을 낸다. 30개 중 29개가 맞아도 1개 때문에 전부 버리면
커버리지를 올리려는 시도가 곧바로 실패율 상승이 된다. **원인 1 과 곱해진다** —
조각이 클수록 인용이 어긋날 확률이 크고 그게 전체 폐기로 이어진다.

### 원인 3 — 실패 원인을 사용자용 코드로 조기에 뭉갰다

```python
except (LLMInvalidResponseError, ValidationError, ValueError):
    failure_code = "LLM_INVALID_RESPONSE"     # 예외를 바인딩조차 안 함
```

하나의 코드가 두 청중을 섬기려 했다. 사용자에게 보여줄 코드와 개발자가 볼 원인이
분리되지 않았다. 접지 실패 6종과 스키마 오류가 전부 한 코드로 뭉쳐졌고,
`logging.basicConfig` 조차 없어 **모든 진단이 "먼저 로그부터 붙이기" 로 시작**해야
했다.

`httpx` 가 INFO 에서 요청 URL 을 통째로 남기므로 전역 INFO 를 켤 때
`httpx` 로거를 WARNING 으로 낮춰야 한다. 안 그러면 API 키가 로그에 남는다.

### 원인 4 — 정리본만 보고 실물 서식을 늦게 봤다

```
괄호 라벨       중기부 우수사례가 쓰는 표기인데 규칙이 못 읽음
요청사유        서식 항목명인데 코드는 "요청유형" 만 찾음
두 자리 연도     서식 예시가 '21년 인데 정규식은 20\d{2}
```

셋 다 같은 형태다. **판별기준 정리본은 개념을 기술하는데 코드는 표면형이 필요하다.**
그 간극을 실물 서식으로 메우지 않았다.

### 원인 5 — 확률적 출력을 1회 측정으로 판단했다

```
"확인율 84.6%"      실제로는 3번 중 1번
"SIM 1위만 실패"     실행마다 다름 (1~3건)
```

두 수치 모두 한 번 재고 보고했다가 정정했다. LLM 이 끼면 n회 측정이 기본이어야
한다.

### 방향 결정

**프론트에 완성본을 준다.** 초안을 미리 주고 병렬 작업하는 대신, Slice 10·11 을
끝내고 실제 동작하는 API 명세를 전달하기로 했다. 프론트가 "완성된 API 목록" 을
원했기 때문이다.

**공고 API 를 공공데이터포털로 전환한다.** 기업마당 자체 키는 IP 등록이 필요해
개발 PC·발표장·배포 서버가 바뀔 때마다 문제가 된다. 이미 가진 포털 키로 같은
데이터를 받을 수 있다는 것이 확인되어 어댑터를 교체했다.

**구동 스크립트를 커밋한다.** 개인 지침상 탐색용 스크립트는 커밋하지 않지만
이건 온보딩 도구라 성격이 다르다고 판단했다.

**오류 코드는 문서화만 한다.** 코드 체계를 바꾸는 대신 OpenAPI 선언을 채웠다.
프론트가 "성공·에러 코드를 공통으로 안 쓰는 이유" 를 물었는데, 실제로는 의미로
정해져 있었고 문서화만 빠져 있었다.

## 6. 남은 일

```
1. 원인 1 — 조각을 줄 단위로 쪼갠다        FIT 대부분이 여기서 풀림. 가장 큼
2. 원인 2 — SIM 에도 접지 관용 적용         CPL 에서 3/3 로 검증된 방법
3. FIT-7 가드 설계 결정                    FIT 판별기준 원문 확인 후
4. 전역 로깅 설정                          httpx 로거 WARNING 필수
5. 두 자리 연도 표기                        판별기준 원문에 규정 없음. 판단 필요
6. 실제 공고 코퍼스 동기화                  1,550건 · 임베딩 약 0.01달러
7. 비식별 실제 요청서 표본 E2E
```

**1번이 압도적이다.** 조각을 `○ (지원대상) ...` 같은 줄 단위로 쪼개면 각 줄이
라벨 하나·역할 하나를 갖게 되고, 그 순간 role 이 채워지면서 FIT-1·2·3·6 이
근거를 찾는다. LLM 도 20자짜리 조각에서는 정확히 인용하고 축을 놓치기 어렵다.

다만 `evidence_ref` 단위가 바뀌므로 접지·저장·중복제거에 영향이 간다.
지금까지 중 가장 큰 변경이다.

**7번을 잊으면 안 된다.** 지금까지 검증한 것은 목업이다. 기술 경로가 끊기지
않는다는 것은 확인했지만 실제 문서에서의 판정 품질은 아직 모른다.
