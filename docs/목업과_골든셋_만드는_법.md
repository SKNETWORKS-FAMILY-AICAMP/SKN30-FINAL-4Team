# 목업과 골든셋 만드는 법

평가용 문서(목업)와 정답(골든셋)을 어떻게 만들고 쓰는지 정리한 문서다.

---

## 왜 둘을 나누는가

목업은 **입력 문서**, 골든셋은 **정답지**다. 반드시 분리한다.

2026-08-29 이전 목업에는 본문에 이런 문장이 들어 있었다.

```
※ [치명적 충돌: FIT-5 CONFLICT] 업력 3년 미만 초기 창업기업에게
   3개년 연평균 매출 50억원을 요구하여 정면 모순 발생!
```

정답이 입력 안에 있으면 모델이 추론으로 맞혔는지 문서에 적힌 답을 읽었는지 구분할 수 없다.
마스터플랜 14.2의 `사람 라벨 일치` 지표도 무의미해진다.
그래서 목업 6건에서 이런 주석과 제목의 등급 표기를 전부 걷어내고 정답은 별도 파일로 옮겼다.
**결함 자체는 그대로 두었다.**

---

## 1. 목업 만들기

### 생성기를 쓴다

`scripts/make_mock_hwpx.py`에 문서를 블록 리스트로 정의하고 실행한다.

```bash
python scripts/make_mock_hwpx.py
# output/mock/ 에 생성되면 samples/hwpx/ 로 복사
```

문자열은 문단, 2차원 리스트는 표가 된다.

```python
CPL_FULL = [
    "【서식 1】 사전협의 요청서",
    "중소기업지원사업 사전협의 요청서",
    "< 부산광역시 >",
    [
        ["사전협의 요청사유", "□ 세부사업 신설  ■ 내역사업 신설  □ 내내역사업 신설\n..."],
        ["사업명",           "(세부) ...\n(내역) ...\n(내내역) ..."],
        ["신설·변경 필요성(사유)", "○ (사업목적) ...\n○ (사업필요성) ...\n..."],
        # ...
    ],
    "첨 부 : 1. 제출자료 자체 점검표 1부",
]
```

손으로 hwpx를 편집하지 않는다. 생성기에 넣어야 나중에 표현을 바꿔가며 다시 만들 수 있다.

### 실제 양식을 따른다

중소벤처기업부 [서식 1]이 요구하는 필수 기재항목은 다음이 전부다.

```
필요성(사유) : 사업목적, 사업필요성, 지원근거, 연계정책
주요내용     : 사업기간, 사업예산, 지원대상,
               지원조건(중소기업·종사자·매출액·인증기업 등),
               지원내용(지원기업수·단가 등), 수행기관
기대효과     : 파급효과, 성과지표
```

**양식에 없는 구역을 만들지 않는다.** 특히 `지원규모`는 별도 항목이 아니다.
양식은 지원기업수와 단가를 **지원내용 안에** 쓰게 한다.
과거 목업 하나가 `○ (지원규모)`를 독립 줄로 뺐다가 FIT-7에 실제 문서엔 없는
두 번째 측면을 만들어준 적이 있다.

### 지켜야 할 것

- **정답 주석 금지.** `※ [치명적 …]`, `→ FIT-6 발생` 같은 꼬리표를 본문에 쓰지 않는다
- **산술을 맞춘다.** 의도한 모순이 아니라면 `단가 × 기업수 = 지원금`이 맞아야 한다
  (mockup_08: 5,000만원 × 40개사 × 3년 = 60억 = 지원금, 총사업비 66억 = 지원금 60억 + 운영비 6억)
- **공란 표기를 다양하게 쓴다.** `(공란)`, `(미기재)`, `해당없음`, 값이 비어 있는 라벨.
  전부 한 가지로 쓰면 부재 처리가 한 번도 시험되지 않는다
- **개인정보 자리는 임의로 채운다.** 담당부서·성명·연락처는 원본이 마스킹돼 있으므로 지어낸다.
  반대로 원본이 원래 공란인 칸(타 제도 협의 등)은 채우지 않는다

### 목적별로 나눠 만든다

문서 하나가 모든 걸 시험할 수 없다.

- `mockup_08` — CPL 13필드와 축이 전부 나오는 표본. 결함 없음
- `mockup_03` — 보통사례. FIT-2 범위차이, FIT-6 정보부족이 의도된 결함
- `mockup_05` — 미흡사례. 대상·조건 모순이 의도된 결함

FIT-4(계층 비교)나 연차별 추진계획을 시험하려면 **내역사업 신설 + 다년도** 문서여야 한다.
`mockup_08`이 그렇게 만들어졌다.

## 2. 골든셋 만들기

`samples/golden/<문서명>.json`. 사람이 문서를 읽고 만드는 정답이다.

현재 `mockup_08.json`(79건), `mockup_03.json`(40건) 두 개가 있다.

### 기준 문서

`중소기업지원사업_PreReview_CPL_판별기준_정리본_20260821.md`를 따른다.
어떤 필드에서 무엇을 확인해야 하는지가 절별로 적혀 있다.

```
§7  사업필요성  문제·현황 / 원인·제약 / 대응 필요 / 근거자료
§11 지원조건    지역·업종·업력·매출액·종사자수·기업규모·인증·기타·제외조건
§12 지원내용    지원기업수·단가·기업당 한도·보조율·자부담률·총 지원규모
§13 수행체계    수행기관·수행방식·수행절차·단계별 역할
§15 성과지표    지표명·목표값·단위·기준연도·측정시점
```

### 구조

```json
{
  "document": "samples/hwpx/mockup_08_CPL전항목_스마트기술사업화.hwpx",
  "basis": "중소기업지원사업_PreReview_CPL_판별기준_정리본_20260821.md",
  "occurrence_count": 79,
  "fields": {
    "TARGET_AND_CONDITIONS": {
      "status": "PRESENT",
      "occurrences": [
        {
          "evidence_ref": "body:4:cell:3:1",
          "raw_text": "상시 근로자 10명 이상 300명 미만",
          "axis_code": "COND_HEADCOUNT",
          "source_role": "CONDITION",
          "normalized_value": {
            "min_count": 10, "max_count": 300,
            "min_operator": "GTE", "max_operator": "LT", "unit": "PERSON"
          },
          "extractor": "RULE"
        }
      ]
    }
  },
  "contract_gaps": ["..."]
}
```

- `raw_text` — 문서에서 **한 덩어리로 그대로 복사**한다. 이어 붙이거나 다듬지 않는다
- `axis_code` — 그 필드의 허용 축 안에서 고른다
- `source_role` — 어느 구역에서 나왔는지 (`TARGET`, `CONDITION`, `SUPPORT_CONTENT` 등)
- `normalized_value` — Rule이 뽑아야 할 정규값. **이상적인 값**을 적는다. 지금 코드가 못 뽑아도 그렇게 적는다
- `extractor` — `RULE`이면 닫힌 판단(값 정규화·라벨 범위), `LLM`이면 열린 의미 축

### 만들 때 반드시 검증한다

모든 `raw_text`가 파서가 만든 조각에 그대로 있는지 확인한다.
없으면 채점 때 `NOT_VERBATIM`으로 전부 떨어진다.

```python
from app.services.cpl.logic_validator import semantic_fragments
frags = {f.evidence_ref: f.text for f in semantic_fragments(doc)}
assert occ["raw_text"] in frags[occ["evidence_ref"]]
```

`evidence_ref`는 `body:4:cell:3:1` 형태다. 표 4번째 블록, 3행 1열 셀을 뜻한다.

### 주의할 점

**문서에 여러 번 나오는 짧은 문구는 피한다.** 서버는 같은 문구가 서로 다른 라벨 구간에
걸쳐 있으면 모호한 인용으로 거부한다. 의도된 동작이다.
`시제품 제작`은 mockup_08에 3번 나와서 거부된다. 더 긴 고유 구간을 쓴다.

**담을 축이 없으면 `contract_gaps`에 적는다.** 억지로 다른 축에 넣지 않는다.
`지원기업 120개사`(사업목적의 정량 표현)와 `측정시점 사업 종료 후 1년`이 현재 그렇다.

## 3. 채점하기

```bash
# 1) 파이프라인 1회 통과
python scripts/e2e_run.py "samples/hwpx/mockup_08_CPL전항목_스마트기술사업화.hwpx"

# 2) 리포트 JSON을 받아 채점
cd backend
python -m app.services.cpl.golden_evaluator \
  ../samples/golden/mockup_08.json <리포트 JSON 경로>
```

```json
{
  "field_status":      {"correct": 12, "total": 13},
  "occurrences":       {"matched": 46, "golden_total": 79,
                        "recall": 0.582, "precision": 0.708},
  "normalized_values": {"correct": 24, "total": 24, "accuracy": 1.0}
}
```

- `field_status` — 13필드 상태가 골든과 같은지
- `recall` — 골든 근거 중 몇 개를 찾았는지
- `precision` — 찾은 것 중 몇 개가 골든에 있는지
- `normalized_values` — 짝지어진 근거의 정규값이 맞는지 (Rule 정확도)

매칭은 필드·축·구역·위치가 모두 같고 원문이 겹칠 때만 1:1로 성립한다.

## 4. 왜 골든셋을 늘려야 하는가

한동안 `mockup_08` 하나로만 측정했다. 그 결과 다른 문서의 회귀를 놓쳤다.

- `mockup_05`의 `PURPOSE_TARGET_CONDITION`이 사라져 FIT-1이 `FIT` → `INSUFFICIENT`로 떨어진 것
- `mockup_03`에서 FIT-5가 없는 모순을 `CONFLICT`로 판정한 것

둘 다 사람이 이전 실행과 손으로 비교해서 찾았다. 골든셋이 있었으면 자동으로 잡혔다.

**성격이 다른 문서로 늘린다.** 전항목 정상(08), 부분 결함(03), 모순(05)처럼
서로 겹치지 않게 만들어야 커버 범위가 넓어진다.

## 파일 위치

```
samples/hwpx/            목업 문서
samples/golden/          골든셋 (occurrence 단위 정답)
samples/expected/        문서별 기대 결과 요약 (FIT 관계별 상태, 의도된 결함 목록)
scripts/make_mock_hwpx.py                        목업 생성기
backend/app/services/cpl/golden_evaluator.py     채점기
docs/중소기업지원사업_PreReview_CPL_판별기준_*.md   골든셋 작성 기준
```

`samples/expected/`는 골든셋보다 거친 단위다. 문서에서 걷어낸 정답 주석이 옮겨간 곳이고,
관계별 기대 상태와 `covered_by_contract` 플래그(결함은 실재하지만 현재 계약이
표현할 수 없는 것)를 담는다.
