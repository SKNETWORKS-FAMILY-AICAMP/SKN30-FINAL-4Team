0. 왜 고치는가
================================================================================

FIT 판별기준 정리본 6~9행이 FIT 의 설계 전제를 밝히고 있다.

    목적:
      - CPL에서 구조화한 항목을 재사용하여 관계 중심으로 검토

CPL 판별기준 §11.4 도 같은 말을 한다.

    이 정보는 이후 FIT / SIM / BEN 분석에서 재사용한다.

그런데 현재 CPL 은 13개 항목에 대해 "존재 여부 + 원문" 까지만 만들고
항목 내부를 구조화하지 않는다.

  Rule 이 만든 occurrence    normalized_value = {"text": 원문}  (dict)
                             단 기간·금액·법령·요청유형은 제대로 된 dict
  LLM 이 만든 occurrence     normalized_value = str | None      (문자열 그대로)

같은 필드 안에 dict 와 str 이 섞여 있고, 어느 쪽도 의미 축을 담지 않는다.

그 결과 FIT 7개 관계가 전부 온전하지 않다.

  FIT-1  좌항이 PURPOSE_GOAL 전체       — 목적의 대상조건만 써야 하는데 통째로 감
  FIT-2  좌항이 PURPOSE_GOAL 전체       — 동일
  FIT-3  우항이 기대효과+성과지표 뭉침   — 단계 구분 불가
  FIT-4  좌항이 REQUEST_TYPE            — 계층 정보가 없는 체크박스, 매핑 자체가 틀림
  FIT-5  좌항 = 우항 = TARGET_AND_CONDITIONS
  FIT-6  좌항 = 우항 = DELIVERY_SYSTEM
  FIT-7  좌항 = 우항 = SUPPORT_CONTENT_AND_SCALE

FIT-5/6/7 은 _evidence() 가 좌우에 동일한 dict 를 만들어
같은 occurrence 를 양쪽에 넣어도 검증을 통과한다. 자기 자신을 비교한다.
tests/test_fit.py:135 가 이 동작을 정답으로 고정하고 있다.

구현기준서 9.3 은 LLM 에게 의미 구조화를 시키라고 이미 정해두었다.

    LLM 사용 예시
      - 목적과 목표의 의미 단위 추출
      - 사업필요성의 문제 → 대응 필요 → 사업수단 구조화
      - 수행기관·역할·절차의 문맥 연결
      - 기대효과와 성과지표의 의미 구조화

지금 구현이 기준서보다 얕다.

1. 확정된 설계 결정
================================================================================

--------------------------------------------------------------------------------
1-1. CPL 13개 항목 목록은 바꾸지 않는다
--------------------------------------------------------------------------------
CplFieldCode 를 13개에서 늘리지 않는다. 이유:

  - 확인율 산식이 (PRESENT + NOT_APPLICABLE) / 13 으로 확정되어 있다.
    분모가 바뀌면 ADR-007 과 프론트 표시가 깨진다.
  - checker._seed_cpl_schema() 가 13행 호환성을 검사한다.
  - 저장된 request_extraction.raw_extraction 스냅샷 형식이 바뀐다.
  - SIM 지원대상 축이 "자격·제외 조건" 을 포함하므로(SIM 판별기준 §6.2)
    CPL 이 지원대상과 지원조건을 한 필드로 묶은 것은 SIM 기준으로는 맞다.

--------------------------------------------------------------------------------
1-2. occurrence 에 두 개의 좌표를 붙인다 — 구역과 축
--------------------------------------------------------------------------------
form_field_definition.parent_field_code 로 자식 행을 만들지 않는다.
DB 행 수, DDL, 확인율 산식을 건드리지 않기 위해서다.
CplOccurrence 에 필드를 더하는 additive 변경이며 기존 필드는 그대로 둔다.
저장된 raw_extraction 스냅샷 JSON 에 키가 늘어나지만 기존 키는 유지된다.

occurrence 하나에 두 가지를 기록한다.

    source_role   그 원문이 문서의 어느 서술 구역에서 나왔나  (Rule 이 정함)
    axis_code     그 값이 무슨 개념인가                       (LLM 이 정함)

둘이 필요한 이유는 FIT-7 이다. 같은 개념(기업당 한도)이
지원내용 서술과 지원규모 서술에 각각 나오고 값이 다른 것을 잡아야 한다.
axis_code 만으로는 좌우가 같은 집합이 되어 자기 비교가 된다.

    FIT 판별기준 §8.1
      지원내용과 지원규모에서 동일 개념의 수치·조건이
      서로 모순되게 기재되어 있는지 확인한다.

    §8.3 예시
      지원내용: 기업당 최대 3천만원 지원      ← source_role = SUPPORT_CONTENT
      지원규모: 기업당 최대 5천만원           ← source_role = SUPPORT_SCALE
      둘 다 axis_code = PER_COMPANY_LIMIT

--------------------------------------------------------------------------------
1-3. 수치는 LLM 이 아니라 Rule 이 정규화한다
--------------------------------------------------------------------------------
구현기준서 9.3 이 "날짜·기간·금액·비율 형식" 을 Rule 우선으로 명시했다.
팀원의 공고 파싱 검증에서도 "단계별 수치 결합" 오류가 실제로 관측됐다.

    LLM  축을 지목하고 해당 원문 구간을 인용한다
    Rule 그 구간에서 값을 정규화한다

LLM 응답 스키마에 value 필드를 두지 않는다. 값을 만들 수 있게 하면
FIT-7 이 그 숫자로 판정하므로 없는 불일치를 만들거나 있는 불일치를 놓친다.

--------------------------------------------------------------------------------
1-4. FIT-4 는 이번 범위에서 구현하지 않는다
--------------------------------------------------------------------------------
사전협의 요청서 한 장에는 보통 한 계층의 내용만 있다.
상위 사업의 대상·목적이 그 문서에 적혀 있다는 보장이 없다.

  - REQUEST_TYPE 체크박스는 "어느 계층의 신설인가" 일 뿐 계층별 내용이 아니다.
  - 기업마당 공고를 상위사업 기준점으로 쓰면 안 된다.
    FIT 은 정의상 "현재 요청서 내부" 정합성이다(FIT 판별기준 목적).
  - LLM 에게 없는 계층을 추론시키면 구조화가 아니라 환각이다.

** 이번 작업에서 FIT-4 는 PROGRAM_LEVEL 존재 여부와 무관하게 항상 다음이다. **

    status      = INSUFFICIENT
    reason_code = HIERARCHY_COMPARISON_NOT_AVAILABLE
    LLM 호출 없음

조건부 실행을 넣지 않는다. 애매하게 두면 반쪽짜리 판정이 나온다.
PROGRAM_LEVEL 축은 CPL 의 계층 언급 보존과 NOT_APPLICABLE 판정에만 쓴다(6-4).

계층 비교 구현은 세부·내역·내내역사업이 함께 기재된 실제 요청서 표본을
확보한 뒤 별도 작업으로 결정한다.

FIT-4 를 7개에서 제거하지 않는다. FIT_TOTAL_RELATIONS, Literal[7],
fit_scoring.json, 프론트 전달사항 §4.2·§4.5 가 모두 7을 전제한다.

2. 선행 작업 — 계약 정비

--------------------------------------------------------------------------------
2-1. OpenAI strict json_schema 제약
--------------------------------------------------------------------------------
infrastructure/openai_llm_client.py 가 strict: True 로 호출한다.
strict 모드는 모든 object 에 additionalProperties: false 를 요구하고
모든 property 가 required 여야 한다. 자유 dict(dict[str, str])는 쓸 수 없다.

--------------------------------------------------------------------------------
2-2. LLM 응답 스키마 — evidence_ref 기반
--------------------------------------------------------------------------------
    class CplAxisCode(StrEnum):
        ...   # 3절 축 목록. 영문 코드로 고정한다. 한글 자유 문자열 금지.

    class CplSemanticOccurrence(BaseModel):
        model_config = ConfigDict(extra="forbid")

        evidence_ref: str          # 서버가 부여한 fragment 식별자
        raw_text: str              # 그 fragment 안에서 해당 축에 해당하는 원문 구간
        axis_code: CplAxisCode

value 필드를 두지 않는다. raw_text 가 값이자 근거다.
source_role 은 LLM 이 정하지 않는다. 서버가 fragment 에 미리 붙여 알고 있다.

** 프롬프트에 반드시 넣을 제약 **

    raw_text 는 제공된 fragment 의 원문을 그대로 인용한다.
    바꿔 쓰거나 요약하거나 분류명으로 대체하지 않는다.
    축 목록에 적힌 예시 값은 그 축이 무엇을 가리키는지 설명하는 것이며
    raw_text 로 쓸 값이 아니다.

이 제약이 없으면 LLM 이 "해외시장 진출" 대신 "수출" 같은 분류명을 반환해
grounding 에서 배치 전체가 무효화된다. 호출 비용만 쓰고 결과가 없어진다.

** 왜 block_id 가 아니라 evidence_ref 인가 **

logic_validator._document_fragments() 는 표 블록을 셀 단위 fragment 로 펼치면서
모든 셀에 같은 block_id 를 부여한다.

    for cell in cells:
        fragments.append(_Fragment(..., block_id=block.block_id))

그래서 현재 ground_llm_response() 의 유일성 검사가 표에서 쉽게 깨진다.

    matches = [f for f in fragments
               if f.block_id == occurrence.block_id
               and occurrence.raw_text in f.text]
    exact_matches = [f for f in matches if f.text == occurrence.raw_text]
    if exact_matches:
        matches = exact_matches
    if len(matches) != 1:
        raise ValueError("LLM evidence cannot be grounded uniquely")

  - 짧은 raw_text 가 같은 표의 여러 셀에 걸리면 matches 가 2개 이상 → 배치 전체 무효
  - "셀 전체를 인용하라" 는 프롬프트 우회로도 해결되지 않는다.
    같은 표에 동일한 셀 텍스트가 두 번 나오면 exact_matches 도 2개가 된다.
  - 셀 하나에 금액이 여러 개면 Rule 이 어느 값을 그 축의 값으로 볼지 모호하다.
    예: "총 지원규모 50억원, 기업당 최대 3천만원"

--------------------------------------------------------------------------------
2-3. 도메인 타입 — axis_code 와 source_role 을 추가한다
--------------------------------------------------------------------------------
FIT 이 읽는 것은 CplOccurrence 다. Rule 이 만든 occurrence 에도 좌표가 있어야
FIT 이 Rule 결과와 LLM 결과를 동일하게 필터링할 수 있다.

    class CplSourceRole(StrEnum):
        TARGET                 = "TARGET"                  # 지원대상 구역
        CONDITION              = "CONDITION"               # 지원조건 구역
        SUPPORT_CONTENT        = "SUPPORT_CONTENT"         # 지원내용 구역
        SUPPORT_SCALE          = "SUPPORT_SCALE"           # 지원규모 구역
        EXPECTED_EFFECT        = "EXPECTED_EFFECT"         # 기대효과 구역
        PERFORMANCE_INDICATOR  = "PERFORMANCE_INDICATOR"   # 성과지표 구역
        DELIVERY_ORG           = "DELIVERY_ORG"            # 수행기관 구역
        DELIVERY_METHOD        = "DELIVERY_METHOD"         # 수행방식 구역
        DELIVERY_PROCEDURE     = "DELIVERY_PROCEDURE"      # 수행절차 구역
        ANNUAL_PLAN            = "ANNUAL_PLAN"             # 연차별 계획 구역
        SUBPROGRAM_PLAN        = "SUBPROGRAM_PLAN"         # 내역사업별 계획 구역

    class CplOccurrence(BaseModel):
        raw_text: str
        normalized_value: Any | None = None
        axis_code: CplAxisCode | None = None        # ← 추가, 기본값 필수
        source_role: CplSourceRole | None = None    # ← 추가, 기본값 필수
        page_no: int | None = Field(default=None, ge=1)
        section_path: list[str] = Field(default_factory=list)
        source_locator: dict[str, Any] = Field(default_factory=dict)
        block_id: str
        extraction_method: Literal["RULE", "LLM"]

** 기본값 None 을 반드시 준다. **
현재 CplOccurrence 는 raw_text · block_id · extraction_method 만 필수다.
기본값 없이 필드를 추가하면 기존 생성자 호출부가 전부 깨진다.

--------------------------------------------------------------------------------
2-4. LLM 입력 구성 변경
--------------------------------------------------------------------------------
analysis_pipeline._semantic_messages() 는 현재 블록 단위로 보낸다.

    blocks = [{"block_id":..., "text":..., "table_cell_texts":[...]}
              for block in document.blocks]

fragment 단위로 바꾸고 각 fragment 에 유일한 evidence_ref 를 부여한다.
Rule 이 정한 source_role 도 함께 보낸다. LLM 이 문맥을 파악하는 데 쓴다.

    일반 블록   "body:12"
    표 셀       "body:12:cell:3:2"        # block_id:cell:row:col

    {"evidence_ref": "body:12:cell:3:2",
     "source_role": "SUPPORT_SCALE",
     "text": "기업당 최대 3천만원, 100개사"}

서버가 ref → fragment 매핑을 들고 있다가 grounding 과 source_role 부여에 쓴다.

또한 현재는 문서의 모든 블록을 매 호출에 넣는다. 요청 필드와 무관한 fragment 를
줄이는 것을 검토하되, 이번 작업의 필수 범위는 아니다.

3. CPL 필드별 축 목록 — 프롬프트에 넣을 내용
================================================================================

출처는 CPL/FIT/SIM 판별기준 원문이다. 임의로 늘리거나 줄이지 않는다.
axis_code 는 아래 영문 코드를 CplAxisCode StrEnum 으로 고정한다.

--------------------------------------------------------------------------------
PURPOSE_GOAL  사업 목적·목표          [라벨 없음 · 전부 LLM]
--------------------------------------------------------------------------------
  PURPOSE_TARGET_CONDITION     목적 문장의 대상조건
  PURPOSE_PROBLEM_DOMAIN       문제영역·지원분야를 나타내는 원문 표현
  PURPOSE_SPECIFIC_OBJECTIVE   구체적 목적대상을 나타내는 원문 표현
  PURPOSE_DIRECTION            변화·방향 (확대 촉진 강화 개선 고도화 해소)

  근거: FIT §2.2 (대상조건) · SIM §5.2 (나머지 셋)
  SIM 판별기준 §5.2 가 사업목적을 세 층으로 나눈다.
    대상 문제영역 / 지원분야    수출 · 기술개발 · 디지털전환 · 창업 · 판로
    달성하려는 변화·방향        확대 · 촉진 · 강화 · 개선 · 고도화 · 해소
    구체적 목적대상             해외시장 진출 · 기술사업화 · 생산성 · 자금조달

  소비처: PURPOSE_TARGET_CONDITION 은 FIT-1
          PURPOSE_DIRECTION 은 FIT-2 · FIT-3 · SIM-1
          나머지 둘은 SIM-1

  ** raw_text 는 반드시 원문을 그대로 인용한다. **
  위 목록은 그 축이 무엇을 가리키는지 설명하는 분류 예시이지
  raw_text 로 쓸 값이 아니다.

      원문   "중소기업의 해외시장 진출 확대"

      PURPOSE_TARGET_CONDITION     raw_text = "중소기업"        ✓
      PURPOSE_PROBLEM_DOMAIN       raw_text = "해외시장 진출"   ✓
      PURPOSE_SPECIFIC_OBJECTIVE   raw_text = "해외시장 진출"   ✓
      PURPOSE_DIRECTION            raw_text = "확대"            ✓

      PURPOSE_PROBLEM_DOMAIN       raw_text = "수출"            ✗ 원문에 없음
                                                                  배치 전체 무효

  같은 원문이 두 축으로 태깅될 수 있다. axis_code 가 다르면 중복 판정에서
  둘 다 보존된다(4-4). 문서가 분야와 목적대상을 따로 적었으면 갈라지고,
  한 표현으로 적었으면 같은 raw_text 를 가리킨다.

  ** 알파에서 지원분야 taxonomy 를 생성하지 않는다. **
  SIM 판별기준 §9 가 "구체적인 분류체계는 실제 공고 데이터 확인 후 확정한다"
  고 했다. 보류 대상은 축이 아니라 다음이다.
    - 수출 · 창업 · R&D 같은 닫힌 분류 목록
    - "해외시장 진출" → "수출" 같은 정규화 매핑
    - 그 분류값을 Retrieval · Pruning 의 확정 필터로 쓰는 것
  분류체계가 확정되면 그때 normalized_value 에 붙인다. raw_text 는 그대로 둔다.

  ** 중요 — FIT 판별기준 §2.2 의 배제 규칙을 프롬프트에 반드시 넣는다. **
  다음 표현은 대상조건이 아니다. 목적 또는 지원방향에 해당한다.
      경쟁력 강화 · 디지털 전환 · 시장진출 · 기술사업화
  PURPOSE_TARGET_CONDITION 은 "지원대상 집합의 범위를 제한하는 표현" 만이다.

  예: "제조 중소기업의 기술혁신 지원"
      PURPOSE_TARGET_CONDITION = 제조 중소기업
      PURPOSE_DIRECTION        = 기술혁신 지원

--------------------------------------------------------------------------------
  SUPPORT_ACTIVITY           지원영역·활동 (스마트공장 구축 해외전시회 참가)
  SUPPORT_INSTRUMENT         지원수단 (보조금 융자 보증 바우처 컨설팅 교육)
  SUPPORT_ITEM               지원항목 (장비비 인건비 인증비 마케팅비)
  PER_COMPANY_LIMIT          기업당 지원액·한도       [KRW]

  ** 축 이름에 구역을 넣지 않는다. 구역은 source_role 이 담는다.
     정량 축 5개는 SUPPORT_CONTENT 구역과 SUPPORT_SCALE 구역 양쪽에
     나타날 수 있으며, 그것이 FIT-7 의 비교 대상이다. **

  ** 주의: SUPPORT_INSTRUMENT (보조금/융자/보증/바우처) 와
     DELIVERY_METHOD_TYPE (직접/보조/출연/위탁) 은 다른 개념이다.
     SIM §8.4 가 명시적으로 경고한다. 둘 다 "보조" 라는 단어를 쓴다. **

IMPLEMENTATION_PLAN  연차별·내역사업별 추진계획
--------------------------------------------------------------------------------
  ANNUAL_PLAN_CONTENT        연차별 추진내용
  PROGRAM_LEVEL              문서에 명시된 사업 계층 표현
  PROGRAM_LEVEL_ABSENT       계층 부재를 명시한 표현
  SUBPROGRAM_PLAN_CONTENT    내역사업별 추진내용

  ** PROGRAM_LEVEL 은 계층 종류까지 Rule 이 정규화한다. **

      normalized_value = {"program_level": "DETAIL"}         # 세부사업
                       = {"program_level": "SUBPROGRAM"}     # 내역사업
                       = {"program_level": "SUBSUBPROGRAM"}  # 내내역사업

  어휘는 이미 logic_validator._REQUEST_TYPES 에 있는 것과 같다.
  코드 이름도 거기 쓰인 DETAIL_NEW / SUBPROGRAM_NEW / SUBSUBPROGRAM_NEW 와
  같은 철자를 쓴다.

  ** 계층 종류를 구분하지 않으면 판정이 틀린다. **
  "세부사업" 언급만 있어도 PROGRAM_LEVEL 은 존재한다. 그러나 세부사업은
  상위 계층이므로 내역사업이 존재한다는 뜻이 아니다. 구분하지 않으면
  세부사업만 적힌 문서에서 내역사업별 계획을 누락으로 처리하게 된다.

  ** PROGRAM_LEVEL_ABSENT 는 다음 중 하나일 때만 인정한다. **

      1. 대상 계층이 원문에 명시됨
         "내역사업 없음" · "내내역사업 해당 없음" 등
      2. fragment 가 명시적인 내역사업별 추진계획 구역에 속함
         source_role == SUBPROGRAM_PLAN

  합쳐진 라벨("연차별·내역사업별 추진계획") 아래의 단독 "해당 없음" 은
  연차별 계획을 말하는지 내역사업별 계획을 말하는지 알 수 없다.
  이 경우 PROGRAM_LEVEL_ABSENT 로 태깅하지 않고 NEEDS_CONFIRMATION 으로 남긴다.

  ** PROGRAM_LEVEL 은 문서에 적힌 표현만 태깅한다. 추론 금지. **
  ** 계층별 대상·목적·지원내용의 구조화는 이번 범위가 아니다(1-4). **

  CPL §6 의 요청유형별 분기(신설이면 설계정보, 변경이면 기존 대비 비교)는
  FIT/SIM 이 소비하지 않으므로 이번 범위에서 구현하지 않는다.

================================================================================
4. Rule 이 처리할 것
================================================================================

--------------------------------------------------------------------------------
4-1. 라벨 매칭 — 구역을 정하고, 축은 확실할 때만 정한다
--------------------------------------------------------------------------------
_LABEL_ALIASES 는 이미 하위 라벨을 따로 갖고 있다. 그런데 _label_match() 가
별칭을 비캡처 그룹 alternation 으로 묶어 "어느 별칭에 매칭됐는지" 가 사라진다.

    alternatives = "|".join(re.escape(alias)... for alias in aliases)
    return re.match(rf"{_LINE_PREFIX}(?:{alternatives})(?:\s*[:：])?\s*(?P<value>.*)$", line)
                                      ↑ 비캡처         ↑ 값만 캡처

매칭된 별칭을 반환하도록 고친다. 그 별칭으로 다음을 정한다.

  ** 라벨 → source_role 은 항상 정한다 **

    "지원대상"                → TARGET
    "지원조건"                → CONDITION
    "지원내용"                → SUPPORT_CONTENT
    "지원규모"                → SUPPORT_SCALE
    "기대효과" "파급효과"      → EXPECTED_EFFECT
    "성과지표" "성과목표"      → PERFORMANCE_INDICATOR
    "수행기관"                → DELIVERY_ORG
    "수행방식"                → DELIVERY_METHOD
    "수행절차" "수행체계"      → DELIVERY_PROCEDURE
    "연차별 추진계획"          → ANNUAL_PLAN
    "내역사업별 추진계획"      → SUBPROGRAM_PLAN
    "내내역사업별 추진계획"    → SUBPROGRAM_PLAN

    합쳐진 라벨("지원대상 및 지원조건", "지원내용·지원규모")은 구역을 정하지 않는다.
    source_role = None 으로 둔다. LLM 은 구역을 추측하지 않는다.

  ** 축 → 구역 파생 — 축만으로 구역이 확정되는 경우에만 서버가 채운다 **

    LLM 이 축을 정한 뒤, fragment 의 source_role 이 None 이면 다음으로 파생한다.

      TARGET_GROUP                                  → TARGET
      COND_*                                        → CONDITION
      SUPPORT_ACTIVITY / INSTRUMENT / ITEM          → SUPPORT_CONTENT
      EFFECT_*                                      → EXPECTED_EFFECT
      KPI_*                                         → PERFORMANCE_INDICATOR
      DELIVERY_ORG_NAME                             → DELIVERY_ORG
      DELIVERY_METHOD_TYPE                          → DELIVERY_METHOD
      DELIVERY_PROCEDURE_STEP / DELIVERY_STEP_ROLE  → DELIVERY_PROCEDURE
      ANNUAL_PLAN_CONTENT                           → ANNUAL_PLAN
      PROGRAM_LEVEL / PROGRAM_LEVEL_ABSENT
        / SUBPROGRAM_PLAN_CONTENT                   → SUBPROGRAM_PLAN

    ** 정량 축은 파생하지 않는다. **
    PER_COMPANY_LIMIT · COMPANY_COUNT · SUBSIDY_RATE · SELF_BURDEN_RATE
    · TOTAL_SCALE 은 지원내용 구역과 지원규모 구역 양쪽에 나타날 수 있다.
    축만 보고 구역을 정하면 FIT-7 이 없는 비교를 만들어낸다.
    이 축들은 fragment 의 source_role 이 None 이면 None 으로 남긴다.

    ** source_role 이 None 인 정량 축 occurrence 는 FIT-7 비교에서 제외한다. **
    어느 구역에서 나왔는지 모르면 §8.1 의 "지원내용과 지원규모에서" 비교가
    성립하지 않는다.

    한계: 요청서가 지원내용과 지원규모를 한 칸에 합쳐 적으면 FIT-7 이
          INSUFFICIENT 가 된다. 없는 비교를 만드는 것보다 낫다.
          실제 표본에서 이 경우가 잦으면 그때 별도로 다룬다.

    PURPOSE_* 축은 PURPOSE_GOAL 필드에 구역 개념이 없으므로 항상 None 이다.

  ** 라벨 → axis_code 는 의미가 유일할 때만 정한다 **

    "지원대상" → TARGET_GROUP
    "수행기관" → DELIVERY_ORG_NAME
    "수행방식" → DELIVERY_METHOD_TYPE
    "수행절차" → DELIVERY_PROCEDURE_STEP

    나머지는 axis_code = None 으로 두고 LLM 이 세부 축을 나눈다.
    특히 다음을 축으로 단정하지 않는다.

      "지원조건" → COND_* 중 무엇인지 모른다
      "지원규모" → 한 줄에 기업당 한도·기업수·보조율이 함께 있을 수 있다
      "지원내용" → SUPPORT_ACTIVITY / INSTRUMENT / ITEM 중 모른다
      "기대효과" → EFFECT_SUBJECT / CONTENT / DIRECTION 중 모른다
      "성과지표" → KPI_* 중 모른다

--------------------------------------------------------------------------------
4-2. 수치 정규화
--------------------------------------------------------------------------------
현재 있는 정규식:  _PERIOD_PATTERN · _SINGLE_YEAR_PATTERN · _AMOUNT_PATTERN · _LAW_PATTERN

  금액   3천만원 → {amount_won: 30000000, unit: "KRW"}   _AMOUNT_PATTERN 있음
  기간   2026~2028 → {start, end, continuing}            있음
  비율   보조율 50% → {ratio: 0.5, unit: "PERCENT"}      ** 패턴 없음. 추가한다. **
  개수   100개사 → {count: 100, unit: "COMPANY"}         ** 없음. 추가한다. **
  연도   2026년 → {year: 2026, unit: "YEAR"}             _SINGLE_YEAR_PATTERN 재사용
  계층   내역사업 → {program_level: "SUBPROGRAM"}        ** 없음. 추가한다. **
         _REQUEST_TYPES 의 어휘를 재사용한다

정규화는 occurrence 의 raw_text 구간 안에서만 수행한다. fragment 전체가 아니다.
그래야 "총 지원규모 50억원, 기업당 최대 3천만원" 같은 셀에서
축별로 올바른 값이 잡힌다.

--------------------------------------------------------------------------------
4-3. 근거 검증
--------------------------------------------------------------------------------
ground_llm_response() 를 evidence_ref 기반으로 바꾼다.

    1. evidence_ref 로 fragment 를 유일하게 찾는다 (dict 조회).
       없는 ref 면 배치 전체 무효.
    2. raw_text 가 그 fragment.text 안에 실제로 포함되는지 확인한다.
       포함되지 않으면 배치 전체 무효.
    3. axis_code 가 해당 field_code 에 정의된 축인지 확인한다.
       정의되지 않은 축이면 배치 전체 무효.
    4. source_role 은 LLM 응답에서 받지 않는다.
       fragment 의 source_role 을 복사하고, 그것이 None 이면
       4-1 의 축 → 구역 파생 규칙을 적용한다. 파생 대상이 아니면 None 으로 둔다.

기존 block_id 선형 검색과 len(matches) != 1 로직은 제거한다.
무효 처리 경로는 기존 LLM_INVALID_RESPONSE 를 그대로 쓴다.

--------------------------------------------------------------------------------
4-4. Rule / LLM occurrence 중복 판정
--------------------------------------------------------------------------------
현재 merge_llm_result() 는 Rule 결과와 LLM 결과를 합친 뒤
_deduplicate_occurrences() 로 전체 JSON 이 완전히 같은 것만 제거한다.
extraction_method 가 RULE / LLM 으로 다르므로 같은 값이 두 번 남는다.

동일성 기준을 다음으로 정한다.

    page_no + block_id + source_locator + raw_text + axis_code + source_role

  - 이 여섯이 모두 같으면 동일 occurrence 로 보고 Rule 결과를 우선한다.
  - axis_code 나 source_role 이 다르면 각각 보존한다.
  - source_locator 를 포함하는 이유: 같은 표의 서로 다른 셀에 동일한 문구가
    있을 때 block_id + raw_text 만으로는 서로 다른 근거를 하나로 합쳐버린다.
  - Rule 이 axis_code = None 이고 LLM 이 같은 위치·원문에서 구체 축을 채운 경우:
      LLM 결과가 유효하면 Rule 의 axis_code = None occurrence 를 병합 결과에서 제거한다.
      LLM 이 실패해 merge_llm_result(llm_error=...) 경로로 갔으면 Rule occurrence 를 유지한다.
    구현 시 판단으로 남기지 않고 위 규칙으로 확정한다. 테스트로 고정한다.

--------------------------------------------------------------------------------
5-1. FIT-7 — 구역이 다른 같은 축을 비교한다
--------------------------------------------------------------------------------
** 좌우를 axis_code 로만 나누면 같은 집합이 되어 자기 비교가 된다. **
** source_role 로 좌우를 가르고, 같은 axis_code 끼리 짝짓는다. **

    좌  source_role == SUPPORT_CONTENT  이고 axis_code ∈ 정량 축
    우  source_role == SUPPORT_SCALE    이고 axis_code ∈ 정량 축

    정량 축 = PER_COMPANY_LIMIT · COMPANY_COUNT · SUBSIDY_RATE
             · SELF_BURDEN_RATE · TOTAL_SCALE

비교 전제조건 — 셋을 모두 만족할 때만 비교한다.

    동일 axis_code
    + 양쪽 모두 정규화 성공
    + 단위 동일 (KRW / PERCENT / COMPANY)

서로 다른 개념이나 단위를 비교하지 않는다.

** 같은 축에 occurrence 가 여러 개일 수 있다. 대표값을 고르지 않는다. **
마스터플랜 11.5 가 "동일 개념이 여러 위치에서 다르게 나오면 대표값을 임의
선택하지 않고 occurrence 를 보존한다" 고 했다. 축별 값 집합으로 비교한다.

    left_values[axis]  = SUPPORT_CONTENT 구역의 정규값 집합 (중복 제거)
    right_values[axis] = SUPPORT_SCALE   구역의 정규값 집합 (중복 제거)

    예:  지원내용 "3천만원, 5천만원"  /  지원규모 "3천만원"
         left  = {30000000, 50000000}
         right = {30000000}
         합집합 크기 2 → 서로 다른 값 존재 → NEEDS_REVIEW

판정 규칙 — FIT 판별기준 §8.3·§8.4 를 그대로 옮긴 것이다.

    어느 축이든 좌우 값 합집합에 서로 다른 값이 있음
                                           → NEEDS_REVIEW / NUMERIC_MISMATCH
    비교 가능한 모든 값이 동일             → FIT
    한쪽 구역에만 정량값 존재              → FIT / SINGLE_SIDED_NO_CONFLICT
    사용 가능한 정량값이 전혀 없음         → INSUFFICIENT

단위가 다르거나 정규화에 실패한 값은 비교에서 제외하고 warnings 에 남긴다.
제외하고 나서 사용할 값이 하나도 없으면
    INSUFFICIENT / COMPARISON_VALUE_INVALID
로 처리한다.

  ** "한쪽에만 존재" 를 INSUFFICIENT 로 두지 않는다. **
  §8.3 마지막 예시가 이 경우다.
      지원내용 "기술개발비 지원" (수치 없음) + 지원규모 "기업당 최대 5천만원"
      → "서로 충돌하지 않음"
  §8.4 의 "한쪽에만 정보가 존재 → 자동 Issue 아님" 과
  "비교할 정보가 부족함 → 판단 불가" 는 서로 다른 줄이다.

  ** 불일치를 CONFLICT 로 올리지 않는다. **
  §8.3 이 "지원규모 정보 간 불일치 확인 필요" 라고 적었으므로 NEEDS_REVIEW 다.

현재 analyze_fit() 은 양쪽에 근거가 있으면 무조건 _semantic_results() 로 보낸다.
FIT-7 을 그 앞에서 분기시킨다. LLM 을 호출하지 않는다.
config/prompts/fit-v0.1.txt 에서 FIT-7 줄을 제거한다.

6-4. IMPLEMENTATION_PLAN 의 상태 집계
--------------------------------------------------------------------------------
** 이 필드는 두 영역이 합쳐진 것이다. 하나만 해당 없음이라고 **
** 필드 전체를 NOT_APPLICABLE 로 만들면 안 된다. **

    CPL §4.1  연차별 추진계획   — 단년도면 해당 없음 가능
    CPL §4.2  내역사업별 추진계획 — 내역사업이 없으면 해당 없음

두 영역을 source_role 로 나눠 각각 판정한 뒤 합친다.

  연차별 영역 (source_role = ANNUAL_PLAN)
    BUSINESS_PERIOD 정규화 결과가 단년도로 확인됨      → 해당 없음
    다년도인데 ANNUAL_PLAN_CONTENT 축 근거 있음        → 확인
    다년도인데 근거 없음                               → 누락
    사업기간 자체를 모름                               → 확인 필요

  내역사업 영역 (source_role = SUBPROGRAM_PLAN)
    ** program_level 종류를 보고 판정한다. PROGRAM_LEVEL 존재 여부가 아니다. **

    PROGRAM_LEVEL_ABSENT 근거 있음 (3절 인정 조건 충족)   → 해당 없음
    SUBPROGRAM 또는 SUBSUBPROGRAM 명시 + 추진내용 있음    → 확인
    SUBPROGRAM 또는 SUBSUBPROGRAM 명시 + 추진내용 없음    → 누락
    DETAIL 만 명시됨                                     → 확인 필요
    아무 표현도 못 찾음                                  → 확인 필요

    ** DETAIL 만 있는 것을 누락으로 보지 않는다. **
    CPL §4.2 는 "내역사업이 존재하면 해당 내역사업의 추진내용이 식별되는지
    확인한다" 고 한다. 세부사업만 적힌 문서는 내역사업이 있는지 자체를 모른다.

  필드 전체 상태 — 순서대로 먼저 걸리는 것을 택한다

    1. 하나라도 누락                → MISSING
    2. 하나라도 확인 필요           → NEEDS_CONFIRMATION
    3. 두 영역이 모두 해당 없음     → NOT_APPLICABLE
    4. 그 외                        → PRESENT

  ** "확인 + 해당 없음" 은 PRESENT 다. **
  적용되는 영역이 모두 확인됐고 나머지는 적용 대상이 아니기 때문이다.
  예: 다년도 사업이라 연차별 계획이 확인됐고, 내역사업이 없다고 명시된 경우.

** 미검출을 부재로 단정하지 않는다. **

    내역사업 표현을 찾지 못함  ≠  내역사업이 존재하지 않음

파싱 실패나 표현 누락일 수 있다. PROGRAM_LEVEL_ABSENT 축에 명시적 근거가
있을 때만 해당 없음으로 본다.

AGENTS.md §5 가 "미확정 CPL NOT_APPLICABLE 계산 규칙 ... 임의로 결정하지 않는다"
고 했으므로, 위 분기를 IMPLEMENTATION_PLAN 에만 적용하고 다른 필드로 확대하지 않는다.

--------------------------------------------------------------------------------
8-4. 새로 필요한 테스트
--------------------------------------------------------------------------------
  raw_text 원문 인용  (2-2, 3)
    - 원문이 "해외시장 진출" 인데 raw_text = "수출" → 배치 전체 무효
    - raw_text = "해외시장 진출", axis = PURPOSE_PROBLEM_DOMAIN → 유효
    - 같은 원문이 PURPOSE_PROBLEM_DOMAIN 과 PURPOSE_SPECIFIC_OBJECTIVE 로
      각각 태깅되면 둘 다 보존된다
    - 축 설명의 예시 값을 raw_text 로 반환하면 무효

  근거 검증
    - 존재하지 않는 evidence_ref → 배치 전체 무효
    - raw_text 가 fragment 에 없음 → 배치 전체 무효
    - 정의되지 않은 axis_code → 배치 전체 무효
    - 같은 표의 두 셀에 동일한 텍스트가 있어도 evidence_ref 로 유일하게 확정
    - source_role 이 LLM 응답이 아니라 fragment 에서 채워짐

  중복 판정  (4-4)
    - 같은 위치·원문·축·구역의 Rule/LLM occurrence → Rule 우선, 1개만 남음
    - axis_code 가 다르면 둘 다 보존
    - source_role 이 다르면 둘 다 보존
    - 같은 표의 다른 셀에 동일 문구 → 별개 occurrence 로 보존
    - Rule 이 axis_code = None 이고 LLM 이 같은 위치·원문에서 구체 축을 채움
      → Rule 의 None occurrence 는 제거되고 LLM 것만 남는다
    - 같은 상황에서 LLM 이 실패(LLM_TIMEOUT 등)하면
      → Rule 의 None occurrence 가 유지된다

  구역·축 분리
    - 라벨 "지원내용" → source_role = SUPPORT_CONTENT, axis_code = None
    - 라벨 "지원규모" → source_role = SUPPORT_SCALE,   axis_code = None
    - 라벨 "지원대상" → source_role = TARGET, axis_code = TARGET_GROUP
    - 합쳐진 라벨 "지원내용·지원규모" → source_role = None
    - FIT-5 좌우가 서로 다른 occurrence 를 받는다 (자기 비교가 아님)

  축 → 구역 파생  (4-1)
    - fragment source_role = None + axis COND_INDUSTRY → CONDITION 으로 파생
    - fragment source_role = None + axis KPI_NAME → PERFORMANCE_INDICATOR 로 파생
    - fragment source_role = None + axis PER_COMPANY_LIMIT → None 유지 (파생 안 함)
    - fragment source_role 이 있으면 파생하지 않고 그대로 복사
    - PURPOSE_* 축은 항상 source_role = None

  FIT-7  ** 자기 비교 회귀 방지 **
    - 좌우가 서로 다른 source_role 의 occurrence 를 받는다
    - 지원내용 3천만원 vs 지원규모 5천만원 → NEEDS_REVIEW / NUMERIC_MISMATCH
    - 지원내용 3천만원 vs 지원규모 3천만원 → FIT
    - 지원내용에 수치 없음 + 지원규모 5천만원 → FIT / SINGLE_SIDED_NO_CONFLICT
    - 양쪽 모두 수치 없음 → INSUFFICIENT
    - 단위가 다르면 비교하지 않음 (KRW vs PERCENT)
    - LLM 을 호출하지 않음

  FIT-7 다중 occurrence 집계  (5-1)
    - 지원내용 {3천만원, 5천만원} vs 지원규모 {3천만원} → NEEDS_REVIEW
      (대표값을 고르지 않고 합집합으로 판정)
    - 지원내용 {3천만원, 3천만원} vs 지원규모 {3천만원} → FIT  (중복 제거)
    - 서로 다른 축은 섞지 않는다
      PER_COMPANY_LIMIT 와 TOTAL_SCALE 값이 달라도 그것만으로 불일치가 아니다
    - source_role = None 인 정량 축 occurrence 는 비교에서 제외
    - 단위 불일치로 전부 제외되면 INSUFFICIENT / COMPARISON_VALUE_INVALID
      그리고 warnings 에 남는다

  FIT-4
    - PROGRAM_LEVEL 축이 있어도 INSUFFICIENT / HIERARCHY_COMPARISON_NOT_AVAILABLE
    - LLM 을 호출하지 않음

  PROGRAM_LEVEL 정규화  (3, 4-2)
    - "내역사업" → {program_level: "SUBPROGRAM"}
    - "내내역사업" → {program_level: "SUBSUBPROGRAM"}
    - "세부사업" → {program_level: "DETAIL"}

  PROGRAM_LEVEL_ABSENT 인정 조건  (3)
    - "내역사업 없음" (대상 계층 명시) → PROGRAM_LEVEL_ABSENT 태깅
    - source_role = SUBPROGRAM_PLAN 구역의 "해당 없음" → 태깅
    - 합쳐진 라벨 아래 단독 "해당 없음" → 태깅하지 않음, NEEDS_CONFIRMATION

  IMPLEMENTATION_PLAN 상태 집계  (6-4)
    - 세부사업만 명시 + 추진내용 없음 → NEEDS_CONFIRMATION
      ** MISSING 이 아님을 고정하는 테스트다 **
    - 내역사업 명시 + 추진내용 없음 → MISSING
    - 내내역사업 명시 + 추진내용 있음 → 내역사업 영역 확인
    - 단년도(해당없음) + 내역사업 부재 명시(해당없음) → NOT_APPLICABLE
    - 단년도(해당없음) + 내역사업 있고 추진내용 없음(누락) → MISSING
    - 단년도(해당없음) + 내역사업 표현 자체가 없음(확인필요) → NEEDS_CONFIRMATION
    - 다년도 + 연차별 근거 있음(확인) + 내역사업 부재 명시(해당없음) → PRESENT
      ** "확인 + 해당 없음" 이 PRESENT 임을 고정하는 테스트다 **
    - 다년도 + 연차별 근거 있음(확인) + 내역사업 있고 추진내용 있음(확인) → PRESENT
    - 누락과 확인필요가 동시에 있으면 MISSING 이 우선

  정규화
    - 비율·개수 정규식 경계값
    - 한 fragment 에 금액이 두 개일 때 축별로 올바른 값이 잡히는지
