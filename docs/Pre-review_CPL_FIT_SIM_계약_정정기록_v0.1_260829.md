## 1. 이 기록을 남기는 목적

기존 문서의 `Rule 우선·LLM 최소 사용`이라는 표현은 "LLM이 필요 없는 결정적 작업에 LLM을 낭비하지 않는다"는 비용·재현성 원칙으로 작성되었다. 그러나 CPL→FIT 정합성을 보완하는 과정에서 이 문구가 "Rule이 LLM보다 우선한다" 또는 "기술적으로 코드로 만들 수 있으면 의미 판단도 Rule로 구현한다"는 일반 우선순위로 해석되었다.

그 결과 다음 편향이 실제 계약과 구현에 들어갔다.

- 표현이 열린 의미 분류까지 키워드와 예외 분기로 처리하여 목업 문구에 과적합할 위험이 생겼다.
- 비교할 양쪽 근거가 없는 상태를 `FIT` 또는 점수로 표현하여 "판정 가능한가"와 "충돌이 있는가"가 섞였다.
- 한 항목의 LLM 응답 결함이 다른 정상 항목까지 폐기할 수 있는 계약이 생겼다.
- SIM 공고 원문의 하나의 컨테이너 값을 여러 의미 축에 그대로 복제하여, 구조화가 된 것처럼 보이지만 실제 비교 토대는 만들어지지 않았다.
- 일부 축만 평가 가능해도 가중치를 재정규화하여 전체 검토등급을 내므로, 보조 축 하나만으로도 높은 등급이 나올 수 있었다.

이번 정정의 목적은 Rule 호출을 늘리거나 LLM 호출을 늘리는 것이 아니다. 각 판단에 필요한 최소 충분 수단을 선택하고, 근거가 부족하면 억지 판정 대신 명시적으로 판정 불가를 반환하도록 CPL·FIT·SIM의 생산자·소비자 계약을 맞추는 것이다.

이 두 행은 다른 항목과 달리 마스터플랜 원문을 그대로 두지 않고 같은 날 하이브리드 서사로 직접 고쳤다. 발표·평가 문서는 그대로 인용되어 슬라이드로 옮겨지므로, 원문을 남기고 이 기록으로만 대체하면 옛 명제가 그대로 발표될 위험이 있었다. 대신 마스터플랜 해당 위치에 원문 문구와 정정 이유를 인용 블록으로 남겨 기록성을 유지했다.

같은 이유로 14.1 실험군 P의 설명도 고쳤다. 840행 명제를 수단 분담으로 바꾸면 P 설명만 Rule이 앞장서는 표현으로 남아 명제와 실험군이 다른 구조를 가리키게 된다. P가 구현하는 시스템, B0~B2 비교 대상, 14.2 평가 지표는 그대로이며 P가 무엇인지에 대한 서술만 정정했다.

같은 원문에는 `문맥 판단이 필요한 부분은 LLM`, `Rule을 LLM으로 또는 LLM을 Rule로 바꿀 수 있다`는 설명도 있다. 따라서 최초 목적은 비용·재현성·책임 분리였지 Rule의 의미론적 우월성을 선언한 것이 아니었다. 이번 정정은 이 목적을 유지하면서 우선순위로 읽히는 표현의 적용 범위를 제한한다.

## 4. 변경하지 않는 계약

다음 항목은 이번 정정 후에도 유지한다.

- CPL 필드 13개와 `(PRESENT + NOT_APPLICABLE) / 13 × 100` 확인율
- occurrence의 원문 Evidence, `field_code`, `axis_code`, `source_role` 보존
- LLM이 `evidence_ref`, 원문 구간 `raw_text`, 의미 축만 제안하고 서버가 grounding하는 구조
- 숫자·금액·비율·기간·단위·기업수의 결정적 정규화와 값 집합 비교는 Rule이 담당한다는 원칙

- FIT-4는 비교 기준 표본이 생기기 전까지 LLM을 호출하지 않고 판정 불가로 둔다는 계약
- FIT-7은 LLM이 아니라 정규화된 정량값 집합을 Rule로 비교한다는 계약
- SIM의 목적·대상·지원내용·수행체계 4축과 완전 평가 시 가중치 30/30/30/10
- SIM은 최종 중복 여부를 판정하지 않고 검토 우선순위와 Evidence를 제공한다는 원칙
- 실제 공고 표본을 확인하기 전에는 수출·창업·R&D 같은 닫힌 taxonomy나 pruning 규칙을 확정하지 않는다는 원칙

## 5. 세부 정정 결정

### CR-01. Rule과 LLM에는 일반 우선순위를 두지 않는다

변경 전:

> Rule 우선·LLM 최소 사용. 코드로 가능한 작업은 Rule/SQL/일반 코드로 처리한다.

변경 후:

- Rule과 LLM 중 어느 쪽도 일반적으로 우선하지 않는다.
- Rule은 입력 문법과 판정 경계가 닫혀 있고, 표현이 달라져도 일반화되며, 같은 입력에 같은 결과를 내고, 완전한 계약 테스트를 만들 수 있는 사실 추출·정규화·검증·상태 전이에 사용한다.
- LLM은 사업목적, 문제영역, 대상·조건의 의미 축, 지원 활동·수단·항목, 역할 관계처럼 표현이 열려 있고 문맥 해석이 필요한 구조화와 관계 비교에 사용한다.
- "코드로 가능"은 정규식·키워드·예외 분기를 계속 추가하면 구현할 수 있다는 뜻이 아니다.
- LLM이 필요 없는 결정적 작업을 LLM에 맡기지 않지만, LLM 호출 수를 줄이기 위해 열린 의미 판단을 Rule로 밀어 넣지도 않는다.

변경 이유:

목업 문구에 맞춘 키워드 분기는 현재 표본에서는 통과해도 실제 문서 표현이 바뀌면 깨진다. 반대로 숫자 파싱, 허용 축 검증, 상태 전이처럼 닫힌 판단을 LLM에 맡기면 재현성과 비용이 나빠진다. 수단은 우선순위가 아니라 판단 성격에 따라 선택해야 한다.

### CR-02. 명시적 부재와 단순 미추출을 구분한다

변경 전:

> 필요한 축이 없으면 FIT이 CPL 재검을 요청하거나 LLM이 축 부재를 선언할 수 있다.

변경 후:

- `지원조건: 없음`, `지원조건: 해당 없음`, `별도 조건 없음`처럼 라벨 범위 안에서 명시된 부재는 Rule이 판정하는 결정적 사실이다.
- 이 Evidence는 삭제하지 않고 해당 필드, `source_role=CONDITION`, 원문, 그리고 `explicit_absence=true`에 해당하는 정규 메타데이터를 보존한다. 의미 조건 축을 임의 생성하지 않으므로 `axis_code`는 `None`일 수 있다.
- FIT-5는 대상군 근거가 있고 명시적 조건 부재가 있으면 재검하지 않고 `INSUFFICIENT / NO_CONDITIONS_SPECIFIED`로 둔다.
- 명시적 부재 문구가 없는데 필요한 축이 추출되지 않은 경우는 "없음"으로 단정하지 않는다. CPL 추출 상태와 Evidence에 따라 `NEEDS_CONFIRMATION` 또는 FIT `INSUFFICIENT / COMPARISON_EVIDENCE_MISSING`으로 둔다.
- LLM에게 원문에 쓰이지 않은 `NOT_STATED`나 축 부재를 사실로 선언하게 하지 않는다.

변경 이유:

명시된 `없음`은 Rule로 검증할 수 있지만, 문서 전체에서 어떤 의미가 존재하지 않는다는 판단은 현재 입력과 프롬프트만으로 접지할 수 없다. 둘을 구분해야 재검 낭비를 줄이면서도 허위 부재를 만들지 않는다.

### CR-03. 연계정책의 구체성은 의미 구조화 대상으로 둔다

변경 전:

> 연계정책 필드에 비어 있지 않은 문장이 있고 소수의 일반 문구 목록과 정확히 일치하지 않으면 Rule로 `PRESENT` 처리할 수 있다.

변경 후:

- 라벨·영역 존재와 빈 값 여부는 Rule로 판정한다.
- 특정 정책·계획·전략·과제와의 연계를 식별할 수 있는지는 표현이 열린 의미 판단으로 보고 LLM이 원문 구간에 접지해 구조화한다.
- 구현 시 `LINKED_POLICY_IDENTIFIER` 의미 축을 additive하게 도입한다. 이 축은 원문에 실제 있는 정책·계획·전략·과제 식별 표현만 가리키며, 원문에 없는 정식 명칭을 생성하지 않는다.
- `관련 정책에 따라 추진`, `정부 정책과 연계`처럼 구체 식별자가 없는 일반 문장만 있으면 `PRESENT`로 올리지 않고 `NEEDS_CONFIRMATION`으로 둔다.
- Rule 키워드 목록은 명백한 빈 값·placeholder 판별을 넘어서 구체 정책 여부를 대신 판단하지 않는다.

변경 이유:

정책명 표현은 열려 있고 표기 방식이 다양하다. 몇 개의 일반 문구 예외 목록으로 구체성을 판별하면 목업에 과적합되며, 새 표현마다 목록이 늘어난다. 다만 LLM 결과도 원문 식별 구간에 접지되어야 한다.

### CR-04. `source_role`은 fragment가 아니라 occurrence 근거 범위에 맞춘다

변경 전:

> fragment에 붙은 라벨 role을 그 fragment에서 생성된 모든 occurrence가 공유할 수 있다.

변경 후:

- 서버는 가능한 경우 라벨이 실제 지배하는 셀·문단·원문 구간별로 `source_role`을 정한다.
- 하나의 fragment에 여러 라벨 구역이 섞이면 occurrence가 인용한 근거 범위에 맞는 role만 부여한다.
- 어떤 라벨이 해당 구간을 지배하는지 결정할 수 없으면 추측하지 않고 `source_role=None`으로 둔다.
- LLM은 `source_role`을 생성하거나 변경하지 않는다.
- FIT은 role로 좌우를 갈라야 하는 관계에만 role 조건을 적용하고, 사업목적 근거에는 role을 요구하지 않는다.

변경 이유:

fragment 수준 role 전파는 목적 축이 정확히 추출됐어도 옆의 대상 라벨 때문에 `TARGET`으로 오염될 수 있다. 소비자에서 필터를 완화하는 것만으로는 보고서에 잘못된 provenance가 남으므로 생산자 좌표도 바로잡아야 한다.

### CR-05. LLM 실패는 신뢰할 수 없는 최소 범위에만 격리한다

변경 전:

> 요청 필드 누락·중복, 예상하지 않은 필드, JSON·스키마 위반은 배치 전체를 `LLM_INVALID_RESPONSE`로 처리한다.

변경 후:

- JSON을 파싱할 수 없거나, 최상위 스키마가 무너져 항목을 식별할 수 없거나, 응답과 요청 필드를 대응시킬 수 없는 경우만 배치 전체를 `LLM_INVALID_RESPONSE`로 처리한다.
- 응답 envelope를 파싱했고 `field_code`별 항목을 식별할 수 있으면 실패를 항목 단위로 격리한다.
- 요청 필드 누락은 누락된 필드만 실패 처리한다.
- 요청 필드 중복은 해당 필드만 실패 처리한다.
- 예상하지 않은 필드는 버리고 warning을 남기되 정상 요청 필드를 낮추지 않는다.
- 개별 occurrence의 ref 부재, 원문 불포함, 해당 필드에서 허용되지 않은 축은 그 occurrence만 제외한다. 그 occurrence 때문에 해당 필드가 신뢰 불가능해졌을 때만 그 필드를 `NEEDS_CONFIRMATION / LLM_INVALID_RESPONSE`로 낮춘다.
- Rule 근거와 다른 정상 필드·occurrence는 항상 보존한다.

변경 이유:

부분적으로 구조가 식별 가능한 응답에서 정상 결과까지 폐기하는 것은 실패 격리 원칙과 맞지 않으며, "하나라도 실패하면 다 버려지는" 동작을 만든다. 반대로 envelope 자체를 해석할 수 없는 경우에는 어떤 필드가 정상인지 증명할 수 없으므로 배치 실패가 타당하다.

### CR-06. FIT 재검은 추출 실패 보완에만 사용하고 축 제한은 유도와 검증을 분리한다

변경 전:

> FIT이 요구한 축이 없으면 재검하고, 재검 프롬프트의 `allowed_axes` 밖 축이 반환되면 해당 응답을 계약 위반으로 처리한다.

변경 후:

- 1차 CPL 의미 추출이 정상 완료되었는데 특정 축이 나오지 않았다는 이유만으로 재검하지 않는다. 없는 축을 반복 요청해도 원문 Evidence는 늘어나지 않는다.
- 재검은 해당 CPL 필드가 `LLM_UNAVAILABLE`, `LLM_TIMEOUT`, `LLM_INVALID_RESPONSE`, 부분 `PARSE_FAILED`이거나, 축 없는 원문 Evidence가 남아 의미 분류가 실제로 미완료된 경우에만 한 번 수행한다.
- 명시적 부재는 재검 대상이 아니다.
- FIT이 요청한 축 목록은 모델을 집중시키는 프롬프트 유도 조건이다.
- grounding의 허용 축은 해당 필드의 전체 `CPL_FIELD_AXES`를 기준으로 한다. 재검 응답에 요청하지 않은 다른 필드-유효 축이 함께 와도 원문에 접지되면 보존하고 기존 occurrence와 합집합·중복 제거한다.
- 그 필드에서 정의되지 않은 축, 허위 `evidence_ref`, 원문에 없는 구간은 계속 계약 위반으로 처리한다.

변경 이유:

프롬프트의 좁은 요청은 모델 집중을 위한 것이지 같은 필드의 다른 정상 의미를 무효화하기 위한 것이 아니다. 또한 성공한 추출에서 단순히 축이 없다는 이유로 재호출하면 비용만 늘고 LLM에게 부재를 꾸며낼 유인을 준다.

### CR-07. FIT-7 단측 정보는 충돌 없음이지 적합이 아니다

변경 전:

> 한쪽에만 정량값이 있으면 `FIT / SINGLE_SIDED_NO_CONFLICT`이며 기존 점수 계약에 따라 점수에 포함한다.

변경 후:

- 양쪽 같은 정량 축에 비교 가능한 값 집합이 있고 모두 같으면 `FIT`이다.
- 양쪽 값 집합 중 하나라도 서로 다르면 `NEEDS_REVIEW / NUMERIC_MISMATCH`다.
- 한 축이라도 한쪽에만 있어 값 집합이 완전히 대응하지 않으면 `INSUFFICIENT / SINGLE_SIDED_NO_CONFLICT`, `score=None`이다.
- 양쪽 모두 값이 없으면 `INSUFFICIENT`다.
- 단위 불일치나 정규화 실패 때문에 비교값이 모두 제외되면 `INSUFFICIENT / COMPARISON_VALUE_INVALID`와 warning을 남긴다.
- `SINGLE_SIDED_NO_CONFLICT`는 "현재 근거에서 충돌을 발견하지 못했다"는 설명일 뿐 `FIT`의 근거가 아니다.

변경 이유:

한쪽 값만으로는 일치 여부를 비교할 수 없다. 이를 `FIT`와 만점에 포함하면 6개 관계가 판정 불가인데 단측 FIT-7 하나만으로 종합 점수가 100이 되는 소비 결함이 생긴다. 팀 내부 FIT 원문도 단측 정보를 자동 Issue로 보지 않을 뿐 적합으로 확정하라고 요구하지 않는다.

### CR-08. SIM 공통 프로필은 원문 복제가 아니라 근거 기반 의미 매핑으로 만든다

변경 전:

> 공고의 `purpose`, `target`, `content` 컨테이너 원문을 각 축의 모든 하위 profile key에 동일하게 넣어 비교 입력을 구성할 수 있다.

변경 후:

- 요청서는 CPL occurrence의 `axis_code`와 검증된 정규값을 공통 SIM 프로필로 명시 변환한다.
- 공고는 원천 필드와 공통 프로필 키가 일대일로 고정되지 않으므로, 라벨·정형 컬럼처럼 결정적인 정보는 Rule로 옮기고 열린 본문 의미는 LLM이 원문 구간에 접지해 하위 키로 구조화한다.
- 하나의 컨테이너 원문 전체를 `problem_domain`, `direction`, `specific_objective` 등 모든 하위 키에 복제하지 않는다.
- 같은 원문 구간이 실제로 둘 이상의 의미 축을 지지하면 각 축 occurrence를 보존할 수 있지만, 각 매핑은 독립적으로 근거와 의미가 확인되어야 한다.
- 값이 없으면 빈 배열로 둔다. 원문은 있으나 구조화 실패 또는 LLM 실패이면 빈 값을 임의 의미로 채우지 않고 미확인 상태와 warning을 남긴다.
- `신청자격`은 target 컨테이너로 풀어 하위 조건에 매핑한다.
- 일반 자격 제외는 SIM-2 `target.exclusion`에 둘 수 있다. 중복수혜·참여제한은 BEN 근거로 분리하고 SIM-2 수혜 가능 집합의 자동 비중첩 근거로 사용하지 않는다.
- `우선지원`은 명시적 hard eligibility만 target에 넣고 가점·우대는 자동 제외 근거로 사용하지 않는다.

변경 이유:

원문을 여러 키에 반복하는 것은 구조화가 아니라 중복 복사이며, 모든 하위 의미가 존재하는 것처럼 모델에 잘못된 신호를 준다. 공고 표현은 열려 있으므로 고정 키워드 사전 대신 grounded semantic mapping이 필요하다.

### CR-09. SIM 전체 등급에는 핵심 3축의 평가 가능성을 선행 조건으로 둔다

변경 전:

> 평가 가능한 축이 하나라도 있으면 그 축들의 가중치 합으로 분모를 재정규화해 `weighted_score`와 검토등급을 계산한다.

변경 후:

- 각 축의 `SIMILAR`, `PARTIAL`, `DIFFERENT`, `INSUFFICIENT` 결과와 Evidence는 독립적으로 보존한다.
- 알파 안전 기본값에서는 핵심 축인 목적(SIM-1), 대상(SIM-2), 지원내용(SIM-3)이 모두 평가 가능할 때만 전체 `weighted_score`와 `FOCUS_REVIEW`, `GENERAL_REVIEW`, `LOW_PRIORITY` 등급을 낸다.
- 핵심 3축 중 하나라도 `INSUFFICIENT`이면 `weighted_score=None`, `review_grade=ON_HOLD`로 둔다. 평가 가능한 개별 축 결과와 `assessable_axis_count`는 그대로 보여준다.
- 수행체계(SIM-4)는 보조 축이다. 핵심 3축이 모두 평가 가능하고 수행체계만 불충분하면 평가 가능한 핵심 축의 30/30/30 가중치를 재정규화할 수 있다.
- 네 축이 모두 평가 가능하면 기존 30/30/30/10 가중치를 유지한다.
- 이 선행 조건은 실제 공고·요청서 라벨 평가세트를 확보하기 전까지 사용하는 `sim-alpha-v0.2` 안전 계약이다. 평가세트로 완화하려면 별도 버전과 변경 근거를 남긴다.

변경 이유:

목적·대상·지원내용은 중복 가능성을 설명하는 핵심 축이고 수행체계는 보조 축이다. 평가 가능한 축만으로 무조건 분모를 재계산하면 수행체계 하나가 유사하다는 이유만으로 전체 점수 100과 중점 검토가 나올 수 있다. 근거 범위보다 강한 등급을 내지 않도록 평가 가능성과 유사도 판단을 분리한다.

### CR-10. 하위 단계 실패로 이미 얻은 CPL·FIT 결과를 폐기하지 않는다

변경 전:

> Retrieval 또는 이후 단계의 예외가 분석 실행 전체를 `FAILED`로 만들 수 있다.

변경 후:

- 문서 전체 파싱 실패처럼 이후 모든 판단의 근거가 없는 경우와 CPL 결과 계약 자체를 만들 수 없는 치명 실패만 분석 실행 전체 실패로 처리한다.
- 유효한 CPL 결과가 생성된 뒤 FIT, Retrieval, SIM 중 일부가 실패하면 성공한 상위·병렬 모듈 결과를 보존한다.
- 실패한 모듈은 계약에 맞는 `UNAVAILABLE`, `INSUFFICIENT`, `ON_HOLD` 상태와 reason code, warning으로 표현한다.
- Report 단계는 부분 결과를 포함한 불변 `report_json`을 완성하고, 사용자가 어떤 단계가 실패했는지 확인할 수 있게 한다.
- 특정 모듈 실패를 정상 판정으로 위장하지 않으며, 재시도 가능 여부와 실패 원인을 warning에 남긴다.

변경 이유:

Retrieval 장애는 CPL의 13개 항목 확인 결과를 무효화하지 않는다. 한 하위 단계의 실패 때문에 이미 검증된 결과를 버리면 실패 격리와 Evidence 보존 목적에 어긋난다.

### CR-11. FIT semantic 응답도 관계 단위로 실패를 격리한다

변경 전:

> 요청한 관계 ID 집합과 응답 관계 ID 집합이 다르면 semantic FIT 응답 전체를 실패 처리한다.

변경 후:

- JSON 자체를 파싱할 수 없거나 관계 ID를 식별할 수 없으면 요청한 pending 관계 전체를 `INSUFFICIENT / LLM_INVALID_RESPONSE`로 둔다.
- envelope를 파싱했고 관계 ID를 식별할 수 있으면 누락·중복된 관계만 `INSUFFICIENT / LLM_INVALID_RESPONSE`로 둔다.
- 예상하지 않은 관계 ID는 버리고 warning을 남긴다. 정상 관계의 상태·Evidence·점수를 낮추지 않는다.
- 한 관계의 Evidence ref·상태·요약 검증 실패는 그 관계만 `LLM_INVALID_RESPONSE`로 격리한다.

변경 이유:

CPL에서 필드 하나의 응답 결함 때문에 다른 정상 필드를 폐기하지 않기로 정정했으므로, 같은 LLM 경계를 소비하는 FIT도 관계 단위 격리가 일관된다. 관계 ID를 전혀 해석할 수 없는 구조 오류만 전체 pending 관계를 낮춰야 정상 결과와 구조 오류를 구분할 수 있다.

## 6. 대체되는 기존 문구 목록

다음 문구는 원문에 그대로 남아 역사적 기록으로 기능하지만, 2026-08-29 이후 구현 판단에서는 이 문서의 해당 CR 조항으로 읽는다.

| 기존 문구 또는 계약 | 대체 조항 | 새 의미 |
|---|---|---|
| `Rule 우선·LLM 최소 사용` | CR-01 | 일반 우선순위가 아니라 결정적 작업에 불필요한 LLM을 쓰지 않는 원칙 |
| `코드로 확정 가능한 작업 → Rule` | CR-01 | 닫혀 있고 일반화·재현·완전 테스트 가능한 판단만 Rule |
| `왜 Rule 우선 멀티에이전트 구조를 선택했는가` (마스터플랜 544·840행) | CR-01 | 평가 논지는 Rule 우선이 아니라 Rule·LLM·코드 검증 하이브리드 대 단일 LLM 비교 |
| 요청 필드 누락·중복·예상 밖 필드이면 배치 전체 실패 | CR-05 | envelope 파괴만 배치 실패, 식별 가능한 오류는 항목 격리 |
| 필요한 축이 없으면 반복 재검 | CR-02, CR-06 | 명시적 부재는 Rule, 정상 추출의 단순 축 부재는 판정 불가, 실제 추출 실패만 1회 재검 |
| 재검 요청 축 밖의 정상 필드 축도 계약 위반 | CR-06 | 요청 축은 프롬프트 유도, grounding은 필드 전체 허용 축 |
| FIT-7 단측 `FIT / SINGLE_SIDED_NO_CONFLICT` | CR-07 | `INSUFFICIENT / SINGLE_SIDED_NO_CONFLICT`, 점수 제외 |
| 공고 컨테이너 원문을 모든 SIM 하위 키에 복제 | CR-08 | 원문 근거별 의미 매핑, 실패 시 빈 값과 warning |
| SIM 축 하나라도 평가 가능하면 전체 등급 산출 | CR-09 | 목적·대상·지원내용 모두 평가 가능해야 전체 등급 산출 |
| 하위 단계 예외가 전체 분석 결과 폐기 | CR-10 | 치명 기반 실패와 모듈 부분 실패를 분리 |

## 7. 구현 영향과 수용 테스트

이 문서 변경 자체에는 코드 수정을 포함하지 않는다. 후속 구현은 목업 결과를 맞추는 방식이 아니라 다음 계약 테스트와 실제 문서 표본으로 검증한다.

### CPL 수용 조건

- 구체 정책명이 없는 `관련 정책에 따라 추진`은 자동 `PRESENT`가 되지 않는다.
- 원문에 실제 정책·계획 식별자가 있으면 grounded `LINKED_POLICY_IDENTIFIER`로 보존된다.
- 라벨 범위의 `지원조건: 없음`은 명시적 부재로 보존되고 조건 의미 축 재검을 발생시키지 않는다.
- 목적과 대상이 한 fragment에 있어도 목적 occurrence에 `TARGET` role이 전파되지 않는다.
- 파싱 가능한 응답에서 한 필드가 누락·중복되어도 다른 정상 필드와 Rule occurrence는 유지된다.
- field 밖 축, 허위 ref, 원문 불포함은 지금처럼 거부된다.

### FIT 수용 조건

- 정상 완료한 CPL에서 단순히 특정 축이 없다는 이유만으로 반복 LLM 재검을 하지 않는다.
- 재검 모델이 요청 축과 함께 다른 field-valid 축을 반환해도 그 축 때문에 `LLM_INVALID_RESPONSE`가 되지 않는다.
- `지원조건: 없음`은 FIT-5 `INSUFFICIENT / NO_CONDITIONS_SPECIFIED`가 된다.
- FIT-7 단측 정량값은 `INSUFFICIENT / SINGLE_SIDED_NO_CONFLICT`, `score=None`이다.
- FIT-7 양측 동일값과 불일치값은 각각 `FIT`, `NEEDS_REVIEW / NUMERIC_MISMATCH`다.
- 식별 가능한 semantic 응답의 누락·중복·예상 밖 관계는 해당 관계만
  격리하고 정상 관계의 상태·점수·Evidence를 유지한다.

### SIM 수용 조건

- 공고의 하나의 `purpose`, `target`, `content` 문자열이 모든 하위 profile key에 자동 복제되지 않는다.
- 각 공통 프로필 값은 실제 원문 Evidence와 연결된다.
- 구조화 실패 시 빈 배열과 warning을 내며 임의 값을 생성하지 않는다.
- 중복수혜·참여제한은 BEN 근거로 분리되고 SIM-2 자동 비중첩 근거로 쓰이지 않는다.
- 수행체계 하나만 평가 가능한 후보는 점수 100이나 `FOCUS_REVIEW`가 아니라 `ON_HOLD`다.
- 목적·대상·지원내용 중 하나라도 불충분하면 전체 점수는 `None`이지만 개별 축 결과는 보존된다.

### 파이프라인 수용 조건

- Retrieval 또는 SIM을 강제로 실패시켜도 앞서 생성된 CPL·FIT 결과와 warning을 포함한 부분 보고서를 조회할 수 있다.
- 문서 전체 파싱 실패는 계속 전체 실패다.
- 실제 HWP/HWPX와 기업마당 공고 표본을 포함한 평가를 목업 테스트와 분리해 실행한다.
- 기존 테스트가 이전 계약을 고정하고 있으면 테스트를 삭제하거나 느슨하게 만들지 않고, 이 정정 계약을 검증하도록 기대값과 이유를 함께 바꾼다.

## 8. 구현 순서

계약 간 생산자·소비자 의존성을 고려해 다음 순서로 적용한다.

1. CPL: 명시적 부재, 연계정책 의미 축, occurrence별 role, 항목 단위 실패 격리
2. FIT: 재검 조건과 grounding 범위, FIT-7 단측 상태·점수
3. SIM: 공고 프로필 구조화, BEN 분리, 핵심 3축 평가 가능성 gate
4. 파이프라인: 부분 실패 보고서 완성 정책
5. 각 단계의 좁은 통합 테스트 후 전체 회귀와 실제 표본 eval

한 번에 결과 숫자를 맞추는 것이 아니라 생산자 계약부터 소비자 계약 순으로 고친다. Slice별 변경과 테스트를 분리해 어떤 결정이 결과를 바꿨는지 추적 가능하게 한다.

## 9. 아직 확정하지 않는 사항

- 실제 라벨 평가세트 없이 CPL 의미 축 키워드 taxonomy를 닫지 않는다.
- SIM 점수 threshold와 30/30/30/10 가중치의 품질을 공식 기준으로 간주하지 않는다.
- `sim-alpha-v0.2`의 핵심 3축 gate는 안전 기본값이며, 실제 표본에서 완화가 필요하면 새 버전과 근거를 남긴다.
- 페이지 번호는 실제 HWP/HWPX 파서가 신뢰 가능한 값을 제공하는지 확인하기 전까지 생성하지 않는다.
- 부분 보고서의 최종 API JSON 외형은 Slice 10 `report_json` 계약에서 프론트와 확정한다.

## 10. 기록 원칙

후속 변경에서도 기존 결정을 삭제해 현재 결과만 남기지 않는다. 최소한 다음을 새 버전의 정정 기록에 추가한다.

- 변경 전 계약과 버전
- 실제로 문제가 드러난 입력·소비 경로
- 변경 후 계약과 적용 범위
- 변경 이유와 검토한 대안
- 영향받는 생산자·소비자·API·DB
- 바뀌어야 하는 테스트와 새 수용 조건
- 미검증 범위와 되돌림 조건

이 형식을 지켜야 특정 목업, 임시 프롬프트 또는 당시 모델 응답에 맞춘 변경인지 나중에 판별할 수 있다.

## 11. 구현 진행 기록

2026-08-29 현재 CPL·FIT Slice는 이 작업 트리에서 다음 범위까지 구현되었다.

- `CplAxisCode.LINKED_POLICY_IDENTIFIER` 추가 및 연계정책을 semantic field로 전환
- 명시적 조건 부재 Evidence 보존과 조건 수치 정규화
- 인용된 원문 구간 기준 field ownership·`source_role` grounding
- 재검 축 제한을 프롬프트 유도에만 사용하고 field 전체 허용 축으로 grounding
- CPL LLM 오류의 필드 단위 격리와 실행 warning 전달
- CPL semantic prompt `cpl-semantic-v0.7`, Rule set `cpl-alpha-v0.3`
- FIT 입력 재검은 실제 CPL 실패·축 없는 원문 Evidence에만 한정하고, 정상
  추출의 단순 축 부재·Rule 소유 `source_role` 부재는 재검하지 않도록 조정
- FIT-7 단측·부분 정량값을 `INSUFFICIENT / SINGLE_SIDED_NO_CONFLICT`로
  변경하고 `score=None`으로 집계에서 제외
- FIT semantic 응답의 누락·중복·개별 grounding 오류를 관계 단위로 격리하고
  예상 밖 관계는 warning과 함께 무시
- FIT semantic prompt `fit-v0.4`, Rule set `fit-v0.3`, scoring snapshot
  `fit-alpha-v0.2`를 버전 파일로 분리
