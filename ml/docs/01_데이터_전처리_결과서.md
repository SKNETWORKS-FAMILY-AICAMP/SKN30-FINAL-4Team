## 4. 발견한 누수 3종

**전처리 단계에서 차단하지 않았다면 성능표 전체가 무의미해질 문제들이다.**

### 4.1 라벨 누수 ① — 2023 엑셀 `사업개요`

첫 줄에 정답이 그대로 적혀 있다.

```
【공고이름】 2023년 개인정보 보호·활용 기술개발 스타트업챌린지 지원
【사업개요】 경영 / 사업화(SW·서비스) / 중소기업(ICT·SW(보안)) / 개인정보보호위원회(...) / 4월
 ① 목적: ...
 ② 내용: ...
 ③ 대상: ...
 ④ 규모: ...
```

| 라벨 | 노출률 |
|---|---:|
| 대분류 | **100.0%** |
| 중분류 | **99.9%** |
| 업종 | 45.9% |

**조치**: `text_for_model`에서 메타 줄을 제외하고 본문(①목적/②내용/③대상)만 사용.

**실측 효과** (같은 5-fold, 메타 줄 포함 여부만 다름)

| 타깃 | 모델 | 누수 포함 | 누수 제거 | 차이 |
|---|---|---:|---:|---:|
| 중분류 | LinearSVM | 0.7762 | 0.5129 | **−0.2633** |
| 중분류 | LogisticRegression | 0.6760 | 0.4494 | −0.2266 |
| 업종 | LinearSVM | 0.8721 | 0.7030 | **−0.1691** |
| 업종 | LogisticRegression | 0.7853 | 0.6414 | −0.1439 |

메타 줄을 안 지웠다면 **Macro F1 0.87짜리 모델을 보고했겠지만 실제로는 0.70**이다.

### 4.2 라벨 누수 ② — Open API `hashtags`

첫 토큰이 분야 라벨과 동일하다.

```
hashtags = "경영,경기,2026,중소기업,..."
category_large = "경영"          ← 첫 토큰과 일치
```

**노출률 100.0%**

**조치**: 분야명과 겹치는 토큰을 제거한 `hashtags_safe` 컬럼 생성.

### 4.3 시간 누수 — 시계열 피처

`rolling_mean_12`를 전체 시리즈에 걸어놓고 나중에 자르면, **2022년 검증 샘플의 피처에 이미 2023년 값이 들어가 있다.**

**조치**: 모든 lag/rolling을 `shift(1)` 이후에 계산. 시점 t의 피처는 t−1 이전 정보만 담는다.

```python
prev = y.shift(1)                     # 당월 값이 자기 피처에 들어가지 않게
for w in (3, 6, 12):
    df[f"rolling_mean_{w}"] = prev.rolling(w, min_periods=w).mean()
```

#### ⚠ PDF 원문은 제외했다

`pdf-inspector`가 **표의 여러 행을 한 셀로 뭉쳐** 금액을 왜곡한다. 실측 결과:

`rhwp`는 HWP 표를 셀 단위로 정확히 읽는 반면, PDF는 행 경계를 잃는다.

```
표 원본 : 238만원 | 119만원 | 476만원 | 1,900만원   (4개 지원 유형)
파싱 결과: "최대 3개월, 238만 원 최대 3개월, 119만 원 ... 1,900만 원"  ← 한 셀로 뭉침
파서 출력: 39억원                                   ← 실제 최대는 1,900만원
```

병합 탐지 규칙으로 일부만 거르는 대신 **오류가 0인 HWP 계열만 사용**했다.

**두 단계 모두에 적용해야 했다.** 처음에는 관측 생성(`a02`)에만 넣었는데, 원문 병합

`a02`가 원문 없는 건의 폴백으로 그 값을 다시 끌어왔다. `f04`에도 같은 기준을 적용하고
구버전 추출본(`e01`) 대신 `e02`를 읽도록 바꿨다.

| | 이전 | 이후 |

2026년 642건은 **과거 연도와 동일한 모집단·동일한 수집 설계에서 나온 값이 아니다.**

| ❌ 이렇게 해석하면 안 됨 | ✅ 정확한 표현 |

**층화 표본의 성격** — 목록 5,000건은 `연도 × 대분류` 균등 배분으로 뽑았다. 모집단이 `기술 5,000건 / 금융 500건`이어도 표본에서는 비슷한 수를 뽑는다.

> **5,000건 표본은 원문 파싱 가능성 확보를 위한 층화 표본이며, 표본 내 관측량 자체를 전체 공고 모집단의 규모로 해석하지 않는다. 지원규모 시계열은 "관측된 공고의 지원규모 추이"로 해석한다.**

## 6. 지원규모 파싱 규칙

### 6.1 금액보다 "금액의 의미"를 먼저 확정한다

`per_company`(기업당)와 `total_budget`(총사업비)을 같은 컬럼에 넣고 평균 내면 무의미한 값이 나온다. 따라서 **집계 키에 `amount_type`을 반드시 포함**한다.

| 타입 | 예시 |
|---|---|
| `per_company` | 기업당 최대 5천만원 |
| `per_project` | 과제당 최대 1억원 |
| `total_budget` | 총사업비 100억원 |
| `periodic` | 월 200만원 / 연 2천만원 |
| `unknown` | 의미 불명확 |

### 6.2 공고당 대표금액 규칙

한 공고문에 여러 금액이 있을 수 있다.

```
기업당 최대 1억원 / 지원비율 70% / 1차년도 5천만원 / 2차년도 3천만원
```

이를 모두 관측치로 넣으면 공고 하나가 여러 번 카운트된다. 파서는 **공고당 대표금액 1개만** 선정한다.

- 의미가 확정된 타입 우선: `per_company` > `per_project` > `periodic` > `total_budget`
- 같은 순위면 금액이 큰 쪽

**실측 결과 공고 2,458건 = 관측 2,458행**으로 1:1이며 중복 카운트가 없다.

### 6.3 단위 정규화

```
5,000만원  → 50,000,000
60백만원   → 60,000,000
1억원      → 100,000,000
60~100백만원 → min 60,000,000 / max 100,000,000
```

### 6.4 이상치 필터

검수 중 파싱 오류를 발견했다.

> 2020년 정부 창업지원사업 통합공고: `"예산규모는 1조 4,517억원"` (정부 전체 예산)
> → 파서가 `1조`를 놓치고 `4,517억원`만 뽑아 **`per_company`(기업당)로 분류** (10건)

기업 한 곳에 4,517억을 준다는 값이 섞이면 평균·최대값이 무의미해진다. 금액 의미별 상식 범위(`SANE_RANGE`)를 정해 **72건(2.9%)을 제외**했다.

| 금액 의미 | 허용 범위 | 제외 |
|---|---|---:|
| `per_company` | 10만원 ~ 50억원 | 25건 (3.1%) |
| `periodic` | 1만원 ~ 1억원 | 23건 (9.2%) |
| `total_budget` | 100만원 ~ 10조원 | 18건 (4.7%) |
| `per_project` | 10만원 ~ 100억원 | 6건 (4.8%) |

**행을 지우지 않고 `is_outlier` 플래그를 붙인다.** 몇 건을 왜 뺐는지 추적할 수 있고, 기준을 바꿔도 원문을 다시 파싱할 필요가 없다.

#### ⚠ 필터가 파이프라인 일부에만 걸려 있었다

`SANE_RANGE`가 **참고범위 산출(`a05`)에만** 있어서, STL 분석(`a03`)과 예측(`a04`)은 4,517억원 같은 오류값을 **그대로 보고 있었다.** (세 스크립트는 이후 제거됐고, 기준은 `common.py` 에 남아 현재 소비처인 `s03f`·`s08a`·`s09a` 가 함께 씁니다.)

```
이전:  a02(원본) ─┬─→ a03 STL       ← 이상치 포함
                 ├─→ a04 예측       ← 이상치 포함
                 └─→ a05 참고범위   ← 여기서만 필터

현재:  a02(원본 + is_outlier 플래그) ─→ a03 · a04 · a05  모두 동일 기준
```

정의를 `common.py` 한 곳으로 옮겨 중복을 없앴다. 고치고 나니 STL 결과가 실제로 바뀌었다 — `per_company` 계절성이 **0.118 → 0.068 → 0.000**으로 계속 떨어져, 이전에 "구조가 있다"고 본 신호의 일부가 이상치가 만든 것이었음이 드러났다.

### 6.5 결측치 — 대부분 채우면 안 되는 것들

| 컬럼 | 결측률 | 성격 | 처리 |
|---|---:|---|---|
| `support_ratio` | 89.1% | **구조적** — 공고에 지원비율 명시가 드묾 | 채우지 않음 |
| `support_type` | 63.6% | **구조적** — 목록 표본엔 지원성격 라벨 자체가 없음 | 채우지 않음 |
| `amount_min` | 54.1% | **구조적** — 단일 금액이면 min이 없는 게 정상 | 채우지 않음 |
| `support_count` | 15.0% | 미기재 | 채우지 않음 |
| `amount_max`·`amount_type`·`large_category` | **0%** | — | — |

**대부분 "값이 없는 게 정보"인 구조적 결측이라 대치(imputation)하면 안 된다.** 목록 표본에 지원성격을 채워 넣으면 없는 라벨을 만들어내는 셈이다. 모델 학습에 쓰는 컬럼(`amount_max`, `amount_type`, `large_category`)은 결측이 0%다.

모델 1 학습 데이터(`business_taxonomy`)도 실제 사용 컬럼의 결측이 0건이다.

### 6.6 정규화·인코딩은 불필요하다

| 기법 | 판단 | 근거 |
|---|---|---|
| 스케일링 | **불필요** | TF-IDF가 **L2 정규화를 내장**한다. 트리 모델(GBDT)은 스케일 불변. 유일하게 필요한 Ridge는 이미 `Pipeline([StandardScaler, Ridge])`로 적용돼 있다 |
| 가변수화 | **불필요** | 모델 1은 **텍스트 한 컬럼만** 쓰고, 모델 2의 시계열 피처는 전부 수치형(`lag_*`, `rolling_*`)이다. 인코딩할 범주형이 파이프라인에 없다 |
| 금액 단위 정규화 | **필요 — 적용함** | 억/천만/백만원 표기를 원 단위로 통일(6.3절) |
| log 스케일 | **필요 — 적용함** | 금액이 만원~조원까지 자릿수를 넘나들어 STL·예측을 log10에서 수행 |
