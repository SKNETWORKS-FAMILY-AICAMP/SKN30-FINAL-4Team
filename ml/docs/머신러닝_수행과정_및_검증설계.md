## 0. 요약

세 개의 독립 모델을 만들고, 각각 **베이스라인부터 전 후보를 같은 분할·같은 시드로 측정**해서 채택 근거를 남겼다.

| 모델 | 과제 | 채택 | 성능 | 베이스라인 대비 |
|---|---|---|---|---|
| 1 | 지원성격 분류 (26클래스) | TF-IDF + LinearSVM | Macro F1 0.643 | Majority 0.017 |

설계서에 있던 **대분류(8분야) 분류는 제외**했다. 기업마당이 이미 8개로 분류해 부여하고 있어 새로 만들 필요가 없다.

**업종 분류도 제외**했다. 애초 필요했던 것은 "융자를 지원하는지 연구개발비를 지원하는지" 같은 **지원 방식** 판별이었고, 이는 업종(식품/ICT/로봇 등 산업분야)이 아니라 **중분류**의 역할이다. 중분류 61종을 지원성격 26종으로 재그룹화해 모델 1을 다시 정의했다(5장).

모델 1은 학습만으로 끝나지 않고, 라벨 없는 Open API 1,570건에 실제로 **적용**했다(6-A장). 신뢰 145건 / 참고용 256건 / 판단보류 1,169건.

## 3. 발견한 누수 3종

이 프로젝트에서 성능표를 무의미하게 만들 수 있었던 문제들이다.

### 3.1 라벨 누수 ① — 2023 엑셀 `사업개요`

첫 줄에 정답이 그대로 적혀 있다.

```
【공고이름】 2023년 개인정보 보호·활용 기술개발 스타트업챌린지 지원
【사업개요】 경영 / 사업화(SW·서비스) / 중소기업(ICT·SW(보안)) / 개인정보보호위원회(...) / 4월

```

**노출률: 대분류 100.0% / 중분류 99.9% / 업종 45.9%**

→ `text_for_model`에서 메타 줄을 제외하고 본문(①목적/②내용/③대상)만 사용.

**실측 효과** (같은 5-fold, 메타 줄 포함 여부만 다름)

| 타깃 | 모델 | 누수 포함 | 누수 제거 | 차이 |
|---|---|---:|---:|---:|
| 중분류 | LinearSVM | 0.7762 | 0.5129 | **−0.2633** |
| 중분류 | LogisticRegression | 0.6760 | 0.4494 | −0.2266 |
| 업종 | LinearSVM | 0.8721 | 0.7030 | **−0.1691** |
| 업종 | LogisticRegression | 0.7853 | 0.6414 | −0.1439 |

메타 줄을 안 지웠다면 Macro F1 0.87짜리 모델을 보고했겠지만 실제로는 0.70이다.

### 3.2 라벨 누수 ② — Open API `hashtags`

첫 토큰이 분야 라벨과 동일하다(`경영,경기,2026,...`). **노출률 100.0%**
→ 분야명과 겹치는 토큰을 제거한 `hashtags_safe` 생성.

### 3.3 시간 누수 — 시계열 피처

`rolling_mean_12`를 전체 시리즈에 걸어놓고 나중에 자르면, 2022년 검증 샘플의 피처에 이미 2023년 값이 들어가 있다.
→ **모든 lag/rolling을 `shift(1)` 이후에 계산.** 시점 t의 피처는 t−1 이전 정보만 담는다.

## 4. 검증 설계 (핵심)

### 4.1 모델별 분할 방식

| | 모델 1 분류 | 모델 2 시계열 | 모델 3 지원규모 |
|---|---|---|---|
| **방식** | Stratified 5-Fold | **Walk-forward** 3-Fold | **GroupKFold** 5-Fold |
| **분할 단위** | 행 (층 = 클래스) | 시간 | 그룹 = 사업명 |
| **데이터** | 896 / 900행 | 1,072행 | 361행 |
| **train : val** | **80 : 20** (고정) | 89~91 : 9~11 (가변) | **80 : 20** (고정) |
| **전 데이터 검증 사용** | 100% | **26.9%** | 100% |
| **K-Fold 교차검증인가** | ✅ | ❌ | ✅ |

### 4.2 fold별 실제 행수

**모델 1 — Stratified 5-Fold (중분류 896행)**

| fold | train | val |
|---|---:|---:|
| 1 | 716 (79.9%) | 180 (20.1%) |
| 2~5 | 717 (80.0%) | 179 (20.0%) |

896행 전부가 검증에 **정확히 1회씩** 사용된다.

**모델 2 — Walk-forward 3-Fold (1,072행)**

| fold | train | val |
|---|---:|---:|
| 1 | ~2021-12 · 768행 (88.9%) | 2022년 · 96행 (11.1%) |
| 2 | ~2022-12 · 864행 (90.0%) | 2023년 · 96행 (10.0%) |
| 3 | ~2023-12 · 960행 (90.9%) | 2024년 · 96행 (9.1%) |

**이것은 K-Fold 교차검증이 아니다.** 두 가지가 다르다.

1. 비율이 fold마다 달라진다(train이 계속 커지는 expanding window)
2. 1,072행 중 검증에 쓰인 건 **288행(26.9%)뿐**이고 나머지 784행(2014~2021)은 train 전용이다

K-Fold였다면 2014년 데이터도 검증에 쓰여야 하는데, 그러면 **2020년 데이터로 학습해 2014년을 예측**하게 된다. 시계열에서는 미래로 과거를 맞추는 누수다(설계서 13장 규칙 2).
문헌에서는 *time series cross-validation* / *rolling-origin evaluation*이라 부르지만, 산출물에는 **walk-forward validation**으로 표기하는 것이 정확하다.

2025년은 3/27까지의 부분 연도라 평가에서 제외했다.

**모델 3 — GroupKFold 5-Fold (361행 / 그룹 350개)**

| fold | train | val |
|---|---:|---:|
| 1 | 288 (79.8%) | 73 (20.2%) |
| 2~5 | 289 (80.1%) | 72 (19.9%) |

그룹은 **연도·지역 태그를 지운 사업명**이다. 같은 사업이 해마다 재공고되므로(`2025년 X사업` / `2026년 X사업`) 단순 KFold면 같은 사업이 train·test에 나뉘어 담겨 성능이 부풀려진다.

### 4.3 fold 내부에서 통제한 누수

**fold 밖에서 미리 계산하면 안 되는 것들**이다.

| 대상 | 잘못된 방식 | 적용한 방식 |
|---|---|---|
| TF-IDF 어휘 | 전체 데이터에 fit | **Pipeline으로 fold train에만 fit** |
| TruncatedSVD | 전체에 fit | fold train에만 fit |
| StandardScaler | 전체에 fit | fold train에만 fit |
| 결측 대치값(중앙값) | 전체 중앙값 | **fold train의 중앙값** |
| lag·rolling 피처 | 전체 시리즈에 rolling | **shift(1) 이후 계산** |
| SARIMA / Prophet | 전체 시리즈 1회 적합 | **fold마다 재적합** |
| 분야별 중앙값 베이스라인 | 전체 중앙값 | fold train에서 산출 |

**예외**: 사전학습 문장 임베딩(SBERT)은 우리 라벨을 전혀 보지 않으므로 전체에 대해 한 번 계산해도 누수가 아니다.

### 4.4 알려진 제약

- 중분류의 가장 작은 클래스가 **2건**이라 5-fold에서 fold 5개 중 2개에만 검증 표본이 들어간다. Macro F1이 낮게 나오는 원인 중 하나다.
- 단일 표본 클래스(중분류 13종 / 업종 9종)는 층화가 불가능해 제외했다. 커버리지는 98.6% / 99.0%로 손실은 작다.
- **고정 홀드아웃 테스트셋이 없다.** 데이터가 작아 전량을 교차검증에 쓴다. 설계서 18장 5순위가 요구한 "실제 서비스 입력과 동일한 형태의 별도 테스트셋"은 미구성 상태다.

## 5. 모델 1 — 지원성격 분류

### 5.0 문제 재정의 — 업종에서 지원성격으로

초기에는 대분류(8분야)와 함께 **업종**(식품/ICT/로봇 등 65종)도 분류 대상으로 검토했으나, 실제 필요는 "이 사업이 **융자**를 지원하는지 **연구개발비**를 지원하는지" 같은 **지원 방식** 판별이었다. 이건 업종이 아니라 **중분류**(연구개발/융자/보증/사업화/컨설팅 등)의 역할이라 **업종 분류는 제외**했다.

라벨 출처도 재확인했다. 세 원천 중 지원성격 라벨은 **2023 중앙부처 엑셀 909건에만 있다.**

| 원천 | 규모 | 대분류(8종) | 지원성격 |
|---|---:|:---:|:---:|
| 장기 공고목록 | 97,794건 | ✅ | ❌ |
| Open API | 1,570건 | ✅ | ❌ |
| **2023 중앙부처 엑셀** | 909건 | ✅ | **✅ 여기만** |

기업마당 두 원천은 8분야만 매기고 지원 방식은 어디에도 없다. 이 라벨의 유일한 출처로 학습한 모델을 라벨 없는 나머지 데이터에 적용하는 것이 모델의 목적이다(→ 7장).

### 5.1 중분류 재그룹화 — 61종을 26종으로

중분류 원본 61종은 `사업화(일반)/사업화(콘텐츠)/사업화(기술)/사업화(SW·서비스)/사업화(수출)`처럼 **괄호 안 세부유형까지 쪼개져** 과도하게 세분화돼 있었다. 괄호 앞 대분류만 남기면 지원성격 단위로 자연스럽게 묶인다.

```python
def coarsen(v):
    stripped = re.sub(r"\([^)]*\)", "", v)   # 괄호 제거 먼저 (괄호 안 콤마 대응)
    return stripped.split(",")[0].strip()     # 복수라벨은 첫 값을 대표로
```

| 단계 | 클래스 수 |
|---|---:|
| 원본 중분류 | 61종 |
| 괄호 제거 후 | 32종 |
| 지원 3건 미만 제외 (`MIN_SUPPORT=3`) | **26종 / 900건** |

**상위 분포**: 사업화 253 / 연구개발 109 / 컨설팅 100 / 판로 87 / **융자 49** / 설비 47 / 고용보조 36 / 교육훈련 36 / 기타지원 36 …

- 입력: `text_for_model` = 사업명 + ①목적 + ②내용 + ③대상 (메타 줄 제외, 3장 참조)
- 벡터화: `char_wb` 2~4 n-gram TF-IDF

### 5.2 결과 (지원성격 26클래스, 900건)

| 모델 | Accuracy | Macro F1 | Weighted F1 |
|---|---:|---:|---:|
| **TF-IDF + LinearSVM** | 0.7567 | **0.6428** | 0.7500 |
| TF-IDF + LogisticRegression | 0.7444 | 0.5866 | 0.7333 |
| SVD + XGBoost | 0.6644 | 0.3998 | 0.6321 |
| SVD + CatBoost | 0.6567 | 0.3662 | 0.6210 |
| SVD + LightGBM | 0.6322 | 0.3128 | 0.5998 |
| SVD + RandomForest | 0.5867 | 0.2979 | 0.5418 |
| Majority (하한선) | 0.2811 | 0.0169 | 0.1234 |

61클래스(중분류 원본, Macro F1 0.513) → 26클래스(0.643)로 재그룹화만으로 성능이 올랐다. 클래스가 커지면서 클래스당 표본이 늘어난 결과다.

### 5.3 핵심 클래스 성능 — 융자 vs 연구개발

| 클래스 | Precision | Recall | F1 | 표본 |
|---|---:|---:|---:|---:|
| **융자** | 0.849 | 0.918 | **0.882** | 49 |
| **연구개발** | 0.759 | 0.927 | **0.835** | 109 |
| 사업화 | 0.854 | 0.763 | 0.806 | 253 |
| 판로 | 0.757 | 0.897 | 0.821 | 87 |
| 고용보조 | 0.821 | 0.889 | 0.853 | 36 |
| 종합지원 | 0.000 | 0.000 | 0.000 | 4 |
| 판로지원 | 0.000 | 0.000 | 0.000 | 5 |

**융자와 연구개발 둘 다 F1 0.83 이상.** 혼동행렬상 두 클래스가 서로 오분류되는 사례는 1~4건뿐으로, 상호 혼동 없이 구분된다. 반면 표본이 3~5건인 꼬리 클래스는 F1 0.0으로 전혀 못 맞춘다 — 26클래스에서도 꼬리는 여전히 길다.

### 5.4 채택 근거

**LinearSVM 채택.** GBDT 3종이 뒤진 주된 원인은 **SVD**다. TF-IDF 6만 차원을 150차원으로 압축하면서 정보가 크게 깎이는데, GBDT는 모두 그 압축본을 입력으로 받는다. 시계열·회귀에서 CatBoost가 1위였던 것과 정반대 결과라, **데이터 성격에 따라 승자가 갈린다**는 근거가 된다.

### 5.5 겪은 문제

**LightGBM 설정 붕괴.** 초기 측정(중분류 49클래스 단계)에서 LightGBM이 Macro F1 0.0081로 Majority보다도 낮았다. 클래스당 표본이 약 14개인데 `min_child_samples=5`가 분할을 막고 있었다. `min_child_samples=1`로 완화하니 0.2338로 회복 — 모델 성질이 아니라 설정 문제였다.

**CatBoostClassifier shape 버그.** `predict()`가 `(n,1)` 형태를 반환해 인덱싱 오류가 났다(m04, m06 두 곳에서 재발). `.ravel().astype(int)`로 평탄화해 해결.

GBDT 예산도 조정했다. 부스팅은 다중분류에서 **반복 1회당 클래스 수만큼 트리**를 만든다. 26~49클래스 × 400 iterations는 fold당 최대 19,600그루로 비현실적이어서, 세 모델 **모두 동일하게** 150~300으로 낮춰 공정 비교를 유지했다.

### 6.4 겪은 문제 — 한국어 Windows에서 Prophet 백엔드 실패

Prophet이 `'Prophet' object has no attribute 'stan_backend'`로 죽었다. 실제 원인은 다른 데 있었다.

cmdstanpy 1.3.0이 `where.exe tbb.dll`을 실행하고 출력을 UTF-8로 디코딩하는데, DLL을 못 찾으면 Windows가 **CP949 한글 오류 메시지**를 뱉는다. 이때 `UnicodeDecodeError`가 나고 Prophet이 이를 삼켜 엉뚱한 오류로 바꾼다.

→ `tbb.dll` 경로를 `PATH`에 추가하는 우회를 스크립트에 넣었다(`m02_forecast.py::_ensure_tbb_on_path`).

**이전 두 번의 Prophet 측정(MAE 41.93)은 전부 평균 대체값이라 무효였다.** 위 표는 수정 후 실측값이다(실패 0건).

## 6-A. 모델 1의 실전 적용 — 라벨 없는 데이터에 추론

지원성격 라벨은 2023 엑셀 909건에만 있고, Open API 1,570건에는 없다. 이걸 채우는 두 가지 방법을 검토했다.

## 8. 결론 세 가지

1. **데이터 성격에 따라 승자가 갈린다.** 텍스트 분류는 희소 TF-IDF + 선형 모델(LinearSVM), 범주형 표 형태는 CatBoost, 시계열은 이질적 앙상블이 이겼다. 한 모델이 전부를 이기지 않았다.

2. **베이스라인이 강하다.** 시계열에서 Seasonal Naive가 단일 ML 모델 대부분을 이겼다. 모델을 늘리는 것보다 베이스라인 대비 개선 여부를 보이는 게 중요하다.

3. **누수를 통제하지 않으면 성능표가 무의미하다.** 라벨 누수만으로 Macro F1이 0.14~0.26 부풀려졌다.

4. **모델의 자체 확신도를 그대로 믿으면 안 된다.** 지원성격 모델을 라벨 없는 데이터에 적용할 때 임계값 0.4를 썼더니 94.1%가 판단보류였다. 원인은 도메인 차이가 아니라 **도메인 내부에서도 평균 확신도가 0.32**였다는 점 — 900건 26클래스 모델은 원래 그렇게 퍼진다. 임계값은 항상 실측(CV 정밀도 곡선)으로 재보정해야 한다.
