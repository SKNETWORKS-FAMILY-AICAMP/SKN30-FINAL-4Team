## 0.1 세 모델이 담당자에게 무엇을 해주는가

세 모델의 공통 목적은 사업기획 담당자 대신 최종 판단을 내리는 것이 아닙니다.
**사전협의 요청서를 제출하기 전에, 어떤 기존사업과 먼저 비교해야 하는지 ·
지원규모가 비교군 안에서 어디에 있는지 · 어떤 설계요소가 유사사업과 크게
다른지**를 빠르게 확인하게 하는 것입니다.

| 하지 않는 것 | 하는 것 |
|---|---|
| 최종 정책 판단 | 비교 범위 축소 |
| 적정 / 부적정 판정 | 비교군 내 상대적 위치 제공 |
| 정상 / 비정상 판정 | 검토 우선순위 제시 · 비교근거 제공 |

세 모델은 독립적인 기술모델 셋이 아니라 하나의 Pre-review 흐름입니다.
앞 단계의 출력이 뒤 단계의 **비교 모집단**을 정의하기 때문에 순서가 있습니다.

```text
사전협의 요청서
  ↓ CPL 구조화
모델 1  지원성격 분류        →  "이 사업은 어떤 종류인가"   →  비교할 기존사업 범위 축소
  ↓ 유사사업 비교군 구성
모델 2  지원규모 상대비교      →  "비슷한 사업들 사이에서    →  금액 근거 점검 우선순위
                               지원규모는 어디쯤인가"
  ↓
모델 3  설계 패턴 이례성 분석   →  "여러 설계값의 조합이     →  검토할 설계축 우선순위
                               유사사업과 얼마나 다른가"
  ↓
SIM / FIT / BEN / DIF 참고정보  →  Evidence Trace  →  담당자가 요청서 검토·보완
```

- **모델 1**은 신규사업의 지원성격을 자동 분류해 비교할 기존사업 범위를 빠르게 좁힙니다.
- **모델 2**는 유사사업 대비 지원규모의 상대적 위치를 보여줘 금액 근거를 우선 점검할 수 있게 합니다.
- **모델 3**은 여러 설계요소의 조합이 유사사업과 얼마나 다른지 보여줘 어떤 부분을
  우선 검토해야 하는지 알려줍니다.

> 한 줄로: **세 모델의 목적은 담당자 대신 사업을 판정하는 것이 아니라, 사전협의
> 제출 전에 비교할 사업과 검토할 설계요소를 빠르게 좁혀 First-pass Quality를
> 높이는 것입니다.**

이 위치 설정이 성능 해석에도 그대로 걸립니다. 판정기가 아니므로 **셋 다 정답
대조 정확도 하나로 채택을 결정하지 않았습니다** — 모델 1은 판단보류를 건 커버리지
곡선으로, 모델 2는 비교군 중앙값 대비 개선율로, 모델 3은 신호 안정성으로
읽습니다.

## 1. 모델 1 — 지원성격 분류

### 1.0 담당자에게 왜 필요한가

신규 사업 요청서는 기관·사업마다 표현 방식이 달라, 어떤 기존사업들과 먼저
비교해야 하는지 바로 판단하기 어렵습니다. 모델 1은 신규 사업을 19개 지원성격
중 하나로 분류해 **비교해야 할 기존사업의 범위를 먼저 좁힙니다.**

모델 1의 값어치는 분류 자체가 아니라 **올바른 비교군을 잡기 위한 첫 단계**라는
데 있습니다. 여기서 성격을 잘못 잡으면 모델 2의 percentile 도 모델 3의
대표벡터도 **다른 모집단에서 계산됩니다** — 뒤 두 모델의 오차가 아니라 입력이
틀리는 것이라, 이 단계의 오류는 뒤에서 복구되지 않습니다.

> **신규사업의 지원성격을 자동 분류해 비교할 기존사업 범위를 빠르게 좁힙니다.**

판단보류가 이 구조에서 중요한 이유도 같습니다. 커버리지 70%에서 정확도 0.9275는
"확실할 때만 비교군을 자동으로 좁히고, 애매하면 담당자에게 넘긴다"는 뜻입니다 —
틀린 비교군을 자신 있게 제시하는 것보다 낫습니다.

**채택: KLUE-BERT** (그룹CV macroF1 0.8350 / 외부 131건 정확도 0.8422 ± 0.0072)

| 후보 | 계열 | 외부 131건 정확도 |
|---|---|---:|
| **KLUE-BERT** | DL | **0.8422 ± 0.0072** |
| KLUE-RoBERTa | DL | 0.8143 ± 0.0157 |
| TF-IDF + LinearSVM (ML 기준선) | ML | 0.7252 |
| KoELECTRA | DL | 0.7583 ± 0.0072 |
| SBERT + LogReg/SVM | DL(임베딩) | 0.7176 / 0.5878 |

BERT vs ML 기준선 McNemar p=0.024로 유의한 우위. `predict_proba`를 활용한
판단보류(임계값 0.20/0.35)로 커버리지 70%에서 정확도 0.9275까지 오릅니다.

검증은 `program_stem` 기준 StratifiedGroupKFold(재공고 그룹 누수 차단) +
Open API 외부 131건 holdout. **한 차례 판정이 뒤집혔던 이력**: 초기 41건
대조에서 RoBERTa가 51.2%로 무너져 ML(LogisticRegression)을 채택했으나,
원인은 모델이 아니라 **DL만 학습·서빙 텍스트가 어긋난 것**이었습니다. 입력을
맞추고 정답셋을 131건으로 늘리자 DL이 다시 앞섰습니다.

**폐기**: 지원규모 월별 시계열 예측 — 4종 전부 Last Value baseline에 크게
뒤짐(계절성 0.00) + 부처 실효성 부족. 대신 **관측 기반 참고범위**(중앙값·
P10~P90)를 제공합니다. 상세: `ml/reports/dl15_final_selection.md`.

### 1.1 클래스별 진단 — 정확도 0.8422 는 어디서 깎이는가 (M54)

새 모델을 더 찾는 대신 채택 모델의 **약점 위치**를 봤습니다. 학습을 새로 하지
않고 이미 저장된 산출물(dl12 예측·dl16 커버리지 곡선·m03 입력정합)만 다시
집계한 결과입니다. 클래스별 표는 3시드 중 **한 시드**의 예측이라 정답이 1~2건인
클래스는 ±1건에 통째로 흔들립니다 — 순위로만 읽습니다.

| 읽은 것 | 근거 |
|---|---|
| **오차가 다수 클래스로 빨려 들어간다** | 학습 1,404건 중 사업화 438건(31%). 외부셋에서 사업화는 정답 11건인데 예측 26건, 정밀도 0.42. 오답 흐름 상위가 대부분 `→ 사업화` |
| **오차의 대부분이 정답셋이 애매했던 건에 있다** | 라벨 확신도 '높음' 79건에서 오답 약 4건, 나머지 52건에서 약 18건. 확신도별 정확도 0.9494(높음) vs 0.57~0.71(그 외) |
| **그래서 판단보류가 성능표보다 중요하다** | 커버리지 100%→70%에서 정확도 0.8422→0.9275로 단조 상승 |
| **입력 정합은 정확도가 아니라 분포를 고친다** | 정합 입력(M03 E1)에서 예측분포 TVD 0.299→0.272, 예측 클래스 15종→17종, 판단보류율은 거의 동일 |

정확도 0.8422 는 **모델의 한계와 정답셋의 모호성이 섞인 숫자**이고, 뒤쪽은
모델을 바꿔서 줄지 않습니다. 모델 1의 오류는 뒤 단계에서 **비교군을 통째로
잘못 잡는 것**으로 이어지므로, 애매한 건을 강행 분류하는 것보다 담당자에게
넘기는 쪽이 파이프라인 전체에서 쌉니다. 상세: `ml/reports/m54_m1_class_diagnosis.md`.

### 1.2 마감 검증 — 섞인 두 숫자를 분리하고 Freeze (M57)

M54 가 "정확도 안에 정답셋 모호성이 섞여 있다"고 말했다면, M57 은 그것을
**분리해서 잽니다.** 새 모델을 찾지 않고 학습도 하지 않았습니다 — 저장된
예측(DL 3종 + ML 3종)만 라벨 확신도로 갈라 다시 집계했습니다.

**라벨 확신도별 성능** (외부 131건, 시드 1개 예측 · Macro-F1 은 그 부분집합의
정답에 등장한 클래스만)

| 부분집합 | N | Accuracy | 95% CI | Macro-F1 | 95% CI | 오류 |
|---|---:|---:|---|---:|---|---:|
| 전체 external | 131 | 0.8321 | 0.763 ~ 0.893 | 0.7184 | 0.611 ~ 0.865 | 22 |
| **High-confidence** | 79 | **0.9494** | 0.899 ~ 0.987 | **0.8170** | 0.712 ~ 0.982 | 4 |
| Non-high-confidence | 52 | 0.6538 | 0.519 ~ 0.769 | 0.6186 | 0.431 ~ 0.752 | 18 |

격차는 정확도 **+0.2968** (95% CI +0.161 ~ +0.442, P(격차>0)=1.000),
Macro-F1 **+0.2501** (95% CI +0.038 ~ +0.468). 각 부분집합 **안에서** 층화
리샘플한 값입니다 — 전체를 리샘플하면 부분집합 크기까지 흔들려 격차가 아니라
구성비 변동을 재게 됩니다. **구간이 0을 품지 않으므로 표본 흔들림으로 설명되는
차이가 아닙니다.**

> 두 개의 '확신도'를 섞지 않습니다. 위 표의 **라벨 확신도**는 라벨러가 사후에
> 붙인 등급이라 **서비스 시점에 존재하지 않습니다.** 운영 판단보류는 모델의
> softmax 최고확률로만 합니다(dl16). 위 표는 운영 규칙이 아니라 *정확도
> 0.8422 안에 무엇이 섞여 있는가* 에 대한 답입니다.

**`사업화` 쏠림의 정체** (정답 11건 · 예측 26건 · 정밀도 0.4231)

| 확인한 것 | 결과 |
|---|---|
| 어떤 정답 클래스가 흡수되는가 | 흡수 15건이 컨설팅 5 · 판로 2 · 융자 2 · 설비/연구개발/SW·솔루션/성능인증/고용보조/창업보육 각 1 로 **넓게 퍼짐** |
| low-confidence 에 몰려 있는가 | 15건 중 **11건(73%)** 이 non-high 라벨 |
| 백본의 버릇인가 | 후보 **6종 중 5종**이 `사업화` 를 정답수보다 많이 예측 — TF-IDF+LinearSVM 까지 포함 |
| 같은 공고가 모든 모델에 그렇게 보이는가 | **아니오.** 건별 모델 합의 수 중앙값 2/6 |
| 라벨 모호성만으로 설명되는가 | **아니오.** High 부분집합 안에서도 정답 2건 · 예측 6건(정밀도 0.33) |

읽으면 이렇습니다. 특정 두 클래스의 경계가 겹치는 것이 아니라, **다수 클래스
쪽으로 향한 사전확률 압력**입니다(사업화가 학습 1,404건 중 438건 = 31%). 각
모델이 *서로 다른* 애매한 건에서 각자 그쪽으로 밀립니다. 그래서 백본 교체로
없어지지 않고, 남은 개선 여지는 모델이 아니라 **라벨 정의와 학습 표본 구성**
쪽입니다.

**Freeze 결정**

```text
모델            KLUE-BERT 확정. 새 PLM 탐색·재학습·test 에 맞춘 튜닝 없음
남은 오차의 정체  ① 정답셋 모호성(High 0.9494 vs Non-high 0.6538)
                ② 다수 클래스 사전확률(사업화 학습 31%)
                둘 다 백본 교체로 줄지 않음
운영            판단보류 적용 권장. 임계값은 이 외부셋이 아니라 학습셋 OOF 에서
                커버리지 목표(예: 70%)를 먼저 정하고 잡는다
```

상세: `ml/reports/m57_m1_confidence_split.md`.

## 2. 모델 2 — 지원규모 상대비교

### 2.0 담당자에게 왜 필요한가

모델 2는 "이 지원금액이 적정하다 / 부적정하다"를 판정하는 모델이 아닙니다.
같은 성격·방식·지원단위·출처의 기존사업들과 비교했을 때 현재 사업의 지원규모가
**어느 위치에 있는지**를 보여줍니다.

```text
유사사업 기업당 지원규모        시스템이 하지 않는 말
P10 = 2,000만원                "1억원은 부적절합니다."          ❌
P50 = 4,000만원
P90 = 8,000만원                시스템이 하는 말
                              "현재 사업의 기업당 지원규모는
신규사업 = 1억원                유사사업 비교군에서 높은 구간에
                              위치합니다."                    ✅
```

담당자는 이를 보고 **왜 이 사업은 기존사업보다 지원규모가 큰지, 요청서에
설명·근거가 충분한지를 먼저 확인**할 수 있습니다. 판정이 아니라 **점검 순서**를
바꾸는 것이 이 모델의 기여입니다.

> **유사사업 대비 지원규모의 상대적 위치를 보여줘 금액 근거를 우선 점검할 수
> 있게 합니다.**

그래서 이 모델의 1차 산출물은 회귀 예측값이 아니라 **비교군 percentile**입니다.
회귀는 비교군이 얇아 percentile 을 그대로 못 낼 때의 보조 추정이고, 아래 MAE 는
그 보조 추정이 "비교군 중앙값을 그냥 답하는 것"보다 나은지를 재는 숫자입니다.

**현행 canonical: 비교군 percentile + XGBoost(구조화 feature + 사업 제목 텍스트)**
— MAE(log10) **0.4155**, n=1,877 (M56 에서 승격, 2.3절)

| 모델 | feature | MAE(log10) | baseline 대비 |
|---|---|---:|---:|
| **XGBoost (현행 canonical)** | 구조화 + 제목 | **0.4155** | **−21.8%** |
| LGBM-quantile50 | 구조화 + 제목 | 0.4384 | −17.5% |
| XGBoost | 구조화만 | 0.4536 | −14.6% |
| LGBM-quantile50 (**이전 canonical, M45**) | 구조화만 | 0.4681 | −11.9% |
| Quantile MLP (DL) | 구조화만 | 0.4883 ± 0.0038 | 미채택 — fold σ(0.0109) 이상 나쁨 |
| FT-Transformer (DL) | 구조화만 | 0.5024 ± 0.0025 | 미채택 |
| 비교군중앙값 (baseline) | — | 0.5315 | — |

> DL 두 후보(0.4883 / 0.5024)는 **구조화 feature 조건에서 측정한 값**입니다
> (DL19). 제목 텍스트를 넣은 조건에서 다시 재지 않았으므로 위 표의 상위
> 세 줄과 직접 비교하지 않습니다.

**이전 canonical(M45)의 수치는 지우지 않습니다** — MAE 0.4681 / 개선 11.9% /
커버리지 79.6% / 구간폭 33.2배가 그 시점의 확정값이고, 2.3절의 비교표가
같은 조건에서 두 세대를 나란히 놓습니다.

타깃은 `stated_cap`(원문 명시 한도)만 쓰고, 비교군 사다리에 **출처

### 2.2 개선 측정 (M53) — 무엇이 얼마나 움직였는가

M52가 읽은 것에만 대응했습니다. 프로토콜은 M45 그대로입니다(같은 타깃
`stated_cap` only, 같은 1,877건, 같은 GroupKFold(5) by `program_stem`,
같은 baseline 0.5315).

| 후보 | MAE(log10) | baseline 대비 |
|---|---:|---:|
| **C7 제목텍스트 + XGBoost(MAE)** | **0.4155** | **−21.8%** |
| C4 제목텍스트 + LGBM 튜닝 | 0.4275 | −19.6% |
| C6 제목텍스트 + XGBoost(분위50) | 0.4290 | −19.3% |

3. 알고리즘 교체(XGBoost)는 **텍스트를 넣은 위에서만** 추가로 움직였습니다.

**누수 점검**: 제목을 넣으면 "지역·연도만 다른 거의 같은 제목"이 새 누수

21.8%). 근거문(`evidence_text`)은 타깃이 파싱된 문장이라 **처음부터
쓰지 않았고**, 제목 1,877건 중 금액 표현이 있는 것은 0건입니다.

### 2.3 canonical 승격 (M55~M56) — 숫자가 좋아졌다는 것만으로는 바꾸지 않았습니다

M53은 측정·권고 상태였고, 교체는 **재현성 고정 → 누수 최종 점검 → 동일조건
비교 → 서빙 동기화**를 모두 통과한 뒤에 했습니다.

**① 재현성 고정 (STEP 1)** — feature pipeline을 `ml/scripts/m2_features.py`
한 곳에 못 박고, 실행할 때마다 지문을 남깁니다: 데이터셋 sha256, 원본 3,963 →
필터 후 1,877(기대값 일치), 타깃 `log10(per_recipient)` · basis `stated_cap`
(`total_budget`·`budget_div_count`·`loan_limit` 제외 근거 명시), feature/grouping
버전, XGBoost 파라미터 전체(라이브러리 기본값도 값으로 적어 고정), seed 42,
실행 시각. 매니페스트: `ml/data/processed/m56_model2_canonical/manifest.json`.

**② 제목 누수 최종 점검 (STEP 2, M55)**

| 점검 | 결과 |
|---|---|
| 제목에 금액·비율 문자열 | 숫자+단위 0건 / 단위어 생략 0건 / % 0건 / 한도·최대·이내 0건 / 기업당·과제당 0건 |
| 금액 마스킹 전후 | 바뀐 제목 0건 → MAE 0.4155 = 0.4155 (차이 +0.0000) |
| 마스커 자체 점검 | `최대 1억원 지원 스마트공장` → `최대 [AMOUNT] 지원 스마트공장` 등 5종 통과 |
| 계열 누수 (정규화제목 그룹) | 개선율 **20.8%** 유지 (같은 조건 M45는 11.7%) |
| 계열이 fold를 넘는 수 | 정규화제목 분할 **0개** (같은 계열 기준으로 `program_stem` 분할을 재면 122개) |
| 제목 단독(B) vs 구조화 단독(A) vs 둘 다(C) | 0.5037 / 0.4536 / **0.4155** — C가 최선 |

세 번째 줄이 중요합니다. `program_stem` 그룹만 쓰면 지역·연도만 다른 같은
사업 계열 **122개가 학습/검증에 걸쳐 있었습니다.** 그래서 제목을 넣은 뒤로는
`normalize_business_title()`(지역·연도·회차·재공고 표현·숫자 제거)로 만든
계열 그룹을 진짜 기준으로 삼았고, 거기서도 개선이 유지되는 것을 확인했습니다.

마지막 줄은 제목의 **역할**을 가릅니다. 제목만으로는 구조화 feature보다
나쁘고 둘을 합쳤을 때만 가장 좋습니다 — 제목이 행 식별자로 쓰이는 것이
아니라는 뜻입니다.

> 쓰지 않는 표현: `사업 제목이 지원규모를 결정한다`
> 쓰는 표현: **`사업 제목은 지원규모의 원인이 아니라, 기존 구조화 feature에서
> 충분히 표현되지 않은 사업 유형·지원형태·세부 목적 정보를 보완하는 텍스트
> feature다`**

**③ 동일조건 비교 (STEP 3)** — 두 세대를 **같은 split 루프 안에서** 학습했습니다.
같은 dataset·target·N(1,877)·fold·baseline·metric을 쓰고 달라지는 것은 feature와
학습기뿐입니다.

| 지표 | M45 | M56 | 판정 |
|---|---:|---:|---|
| MAE(log10) | 0.4681 | **0.4155** | M56 우세 |
| baseline 대비 개선 | 11.9% | **21.8%** | +9.9%p |
| Within 2x | 43.1% | **48.8%** | +5.6%p |
| fold 재구성 10회 | 11.7% ± 0.8% | **21.8% ± 0.7%** | M56 우세 |
| 최저 개선율 / 통과 | 10.0% / 9회 | **20.6% / 10회** | M56 우세 |
| CQR Coverage | 79.6% | **80.3%** | 유사·소폭 개선 |
| 구간폭 중앙값 | 33.2배 | **25.1배** | M56 우세 |
| 비교군 등급 (가능/넓음/어려움) | 12 / 14 / 3 | **16 / 12 / 1** | M56 우세 |

개선이 어디서 왔는지는 2×2로 갈립니다.

```text
              구조화만      구조화+제목
LGBM          0.4681        0.4384      <- feature 를 바꾼 이득
XGBoost       0.4536        0.4155      <- 학습기를 바꾼 이득
```

두 축이 겹치지 않고 각각 붙습니다. 제목 feature는 학습기와 무관하게 MAE를
내리고(LGBM에서도 XGBoost에서도), 학습기 교체도 feature와 무관하게 내립니다.
엄격 그룹에서도 같은 순서입니다(0.4858 / 0.4627 / 0.4758 / 0.4356).

**④ 서비스 inference 동기화 (STEP 4)** — 학습만 새 파이프라인이고 서빙이 옛
feature를 쓰면 승격이 아닙니다(모델 1이 정확히 그 이유로 한 번 뒤집혔습니다,
1장). 전체 데이터로 적합한 산출물(TF-IDF·SVD·점추정·분위·CQR delta·feature
order·범주 목록)을 저장하고, **저장물만으로** 만든 feature가 학습 때와 같은지
왕복 확인했습니다 — feature 순서·수치·범주·예측값 4종 모두 일치.

이 저장소에는 별도의 서비스 추론 코드베이스가 없습니다(demo는 정적 목업).
따라서 `m2_features.py` + `m56_m2_canonical.serve()`가 곧 추론 경로이고,
다른 곳에서 모델 2를 호출할 때 feature를 다시 구현하면 안 됩니다.

승격 점검표 11개 항목 전부 PASS. 상세: `ml/reports/m55_m2_leakage_audit.md`,
`ml/reports/m56_m2_canonical.md`.

> **M45는 삭제하지 않습니다.** `ml/scripts/m45_m2_amount.py`는 이전 canonical로
> 그대로 남아 있고, 타깃 정제·비교군 사다리·percentile 조회·구간 등급은 M56이
> 그 코드를 그대로 import해서 씁니다. 바뀐 것은 feature와 학습기 둘뿐입니다.
>
> 같은 이유로 **M56 도 삭제하지 않습니다.** 2.5절에서 canonical 산출물이
> 데이터 수정본 위로 재적합되지만, `m56_m2_canonical.py` 와
> `m56_model2_canonical/` 은 이전 세대로 남습니다 — 이 절의 수치(0.4155 /
> 21.8% / 48.8%)가 그 세대의 확정값이고, `design_features.parquet` 이 그
> 지문입니다.

### 2.4 데이터 품질을 고치고 같은 M56 으로 다시 (M62 · M63)

새 모델을 찾지 않았습니다. **바꾼 것은 입력 데이터셋 하나**이고, 타깃
`stated_cap`·필터·비교군 사다리·feature 규격·XGBoost 파라미터·GroupKFold(5)·
baseline·seed 42 는 전부 그대로입니다. 무엇을 고쳤는지는 2.5절과 전처리결과서
8.4 에 있습니다.

**대상 행이 1,877건으로 같습니다.** 수정이 타깃·금액·필터를 건드리지 않았기
때문입니다. 그래서 이 비교는 M56 승격 때(STEP 3)와 같은 규율로 **같은 split
루프 안에서** 두 데이터셋을 학습한, 같은 행·같은 타깃·같은 fold 대조입니다.
달라지는 것은 아래 칸뿐입니다.

| 바뀐 컬럼 | 값이 바뀐 행 |
|---|---:|
| `project_duration` (근거문에서 복원) | 524 |
| `support_method` (근거문 재도출) | 114 |
| `self_burden_ratio` (근거문에서 복원) | 78 |
| `support_unit` (근거문 재도출) | 35 |
| `support_ratio` (파싱 오류 제거) | 1 |
| `per_recipient`(타깃) · `title` · `amount_type` · `support_count` | **0** |

마지막 줄이 이 비교의 전제입니다. 근거문이 닿지 않는 컬럼은 **한 행도 움직이지
않았습니다** — 상류 산출물까지 맞춘 뒤에야 이 줄이 0 이 됐고, 그 사연은 2.5절
1번에 있습니다.

| 지표 | M56 on 현행(v1) | M56 on 수정(v2) | |
|---|---:|---:|---|
| MAE(log10) | 0.4155 | **0.4117** | 개선 |
| v1 baseline 대비 개선 | 21.8% | **22.5%** | +0.7%p |
| 2배 이내 | 48.8% | **49.2%** | +0.4%p |
| 3배 이내 | 67.6% | **68.1%** | +0.5%p |
| 엄격 그룹(정규화 제목) 개선율 | 20.8% | **21.7%** | +1.0%p |
| fold 재구성 10회 개선율 | 21.75% ± 0.73% (최저 20.56%) | **22.46% ± 0.80%** (최저 21.29%) | 개선 |
| CQR 커버리지(명목 80%) | 0.803 | **0.807** | 유사 |
| 구간폭 중앙값 | 25.1배 | **24.1배** | 개선 |
| 비교군 등급 (가능/넓음/어려움) | 16 / 12 / 1 | **16 / 15 / 0** | 개선 |
| **비교군중앙값 baseline** | 0.5315 | **0.5223** | **개선** |
| *각자의* baseline 대비 개선 | 21.8% | 21.2% | 사실상 동일 |

**첫 줄이 공표 수치와 정확히 일치합니다**(0.4155 / 21.8% / 48.8% / 67.6%).
재현이 먼저 확인된 뒤라야 두 번째 열을 읽을 수 있습니다.

**MAE 차이부터 짝지어 검정합니다.** 두 열은 같은 fold·같은 행이므로 행 단위로
오차를 짝지을 수 있고, 그러면 차이의 분산이 MAE 각각의 분산보다 훨씬 작아집니다.

| 짝지은 절대오차 차이 (v1 − v2) | 값 |
|---|---:|
| 평균 | +0.00374 |
| 부트스트랩 95% 구간 | −0.00031 ~ +0.00783 |
| P(차이 > 0) | 0.967 |
| v2 가 더 정확한 행 | 958 / 1,877 (51.0%) |
| Wilcoxon 부호순위 p | 0.113 |

**구간이 0을 아슬아슬하게 품고, 부호검정도 유의수준에 못 미칩니다.** 방향은
일관되지만(P(차이>0)=0.967) **유의하다고 말하지 않습니다.** MAE 0.4155 →
0.4117 은 이 표본에서 표본 흔들림과 확실히 갈라지지 않습니다.

**그렇다면 무엇이 움직였는가 — 마지막 두 줄입니다.** 비교군 중앙값 baseline 은
모델이 아니라 **비교군 자체가 금액을 얼마나 잘 설명하는가**입니다. 그 값이
0.5315 → 0.5223 으로 같이 내려갔다는 것은 `support_method` 를 바로잡자
**비교군이 실제로 더 동질해졌다**는 뜻입니다 — 모델과 무관한 독립 증거입니다.
그래서 각자의 baseline 대비 개선율로 재면 두 세대가 거의 같습니다. **모델이
좋아진 것이 아니라 모델과 baseline 이 함께 좋아졌습니다.**

**지시서가 '필요할 때만' 이라고 한 두 후보를 한 번 돌렸습니다.** 데이터 수정만
으로 예측 오차가 확실히 움직이지 않았으니 여기가 그 '필요할 때'입니다.

| 후보 | MAE(log10) | 판정 |
|---|---:|---|
| 기준 (XGBoost, 수정 데이터) | 0.4117 | — |
| XGBoost + LightGBM 단순 평균 | 0.4169 | 미채택 |
| XGBoost + 비교군 잔차 보정 | 0.4136 | 미채택 |

**둘 다 기준보다 나쁩니다.** 잔차 보정에서 한 가지를 적어 둡니다 — 처음에는
train fold 의 **in-sample** 잔차로 비교군 중앙값을 잡았고 그때는 기준보다 좋게
나왔습니다. 그런데 XGBoost 800 트리는 train 을 거의 맞히므로 그 잔차 중앙값은
0 근처로 눌리고, 보정이 아니라 과적합 방향으로 밀어준 것에 가깝습니다.
inner GroupKFold(3) 로 OOF 잔차를 다시 잡자 뒤집혔습니다. **측정 방식이
결론을 만들던 자리**라 그대로 남깁니다.

**지시서의 종료 조건에 답하면 — 모델 2 쪽 추가 실험은 종료합니다.** "실질
개선이 없으면 추가 모델 실험은 종료한다"가 조건이었고, 예측 오차에서는 유의한
개선이 없으며 보조 후보 2종도 현행을 넘지 못했습니다. 데이터 수정이 남긴 것은
다른 축입니다.

> **모델 2에서 데이터 수정의 값어치는 MAE 가 아닙니다.** 바뀐 칸을 보면
> 타깃도 금액도 제목도 한 행이 안 움직였고, 움직인 것은 비교군 축과 보조
> 수치축입니다. M52~M53 이 이미 잰 대로 이 모델의 오차는 대부분 *사업의 내용*
> 에서 오고 그건 제목 텍스트가 이미 담고 있습니다. **수정이 고친 것은 예측
> 오차가 아니라 `융자 사업이 보조금 분포에서 percentile 을 받는` 상태**입니다
> — 그건 MAE 가 재는 값이 아니라 **1차 산출물인 percentile 조회의 정합성**
> 입니다(2.0절: 회귀는 보조 추정이고 percentile 이 1차 산출물). baseline 이
> 같이 내려간 것이 바로 그 정합성이 좋아졌다는 신호입니다.

상세: `ml/reports/m62_data_quality.md`, `ml/reports/m63_m2_requal.md`.

### 2.5 원인을 원천에서 고치고 canonical 산출물을 재적합 (M65)

**이 절은 MAE 개선을 위한 모델 변경이 아니라 입력 데이터 정합성 확보를 위한
canonical artifact 갱신입니다.**

```text
바꾸지 않은 것   feature 구성 (m2_features.py) · split (GroupKFold 5) ·
                모델 구조 (XGB 파라미터) · 추론 경로 (build_serving_frame/serve) ·
                타깃·필터 (stated_cap only, n=1,877)
바꾼 것          입력 데이터셋 하나 — 그리고 그 데이터셋을 만드는 F06 을 근본 수정
```

M65 는 M56 의 `paired_oof` · `stability` · `intervals` · `fit_artifacts` 를
**그대로 호출**합니다. 파이프라인이 같다는 것을 문장으로 주장하지 않고 같은
함수를 부르는 것으로 보장합니다.

**① 근본 수정과 그 검증 — legacy 재현이 한 건을 잡았습니다.**

`_pack_bizinfo` 가 근거문 자리에 금액을 뽑지 않은 텍스트를 저장하던 것을 F05 와
같은 문서 선택 규칙으로 고른 원문으로 바꿨습니다(목록 표본 + Open API 407행).
전처리결과서 8.4 에 상세가 있고, 여기서는 검증만 적습니다.

| 검증 | 결과 |
|---|---|
| `--legacy` 로 수정 전 동작 재현 | **34개 컬럼 3,963행 전부 일치** |
| 수정본 결정성 | 다시 만들어도 같은 sha256 (`eced88f6767e2e24`) |
| 규칙 품질 (라벨 대조, `융자` n=388) | `loan` 판정 F1 **0.735 → 0.808** (재현율 0.649 → 0.918 · 정밀도 0.846 → 0.722) |
| 문맥 구역 선택 | 문서 전체 F1 0.715 / **지원내용 절 0.824(채택)** / scale 과 동일 0.830 |

첫 줄이 처음부터 이랬던 것은 아닙니다. **처음 대조에서는 `support_count`
82행 · `extraction_confidence` 55행이 달랐습니다.** 원인은 근거문이 아니라
**상류 산출물이 어긋나 있던 것**이었습니다 — `business_taxonomy.parquet` 의
오래된 사본(28컬럼)이 M32 의 지원기업수 파싱 수정 이전 값을 담고 있었습니다
(`6개월간`→6개사, `110개소`→110개사, `18개국 85개 물류센터`→18개사).
`f03_taxonomy.py` 로 재생성해 맞춘 뒤에야 완전 일치가 나왔습니다.
**그 상태로 재적합했으면 근거문 수정의 효과와 상류 어긋남이 섞였을 것입니다** —
legacy 재현을 승격 절차 앞에 둔 이유가 이것입니다.

세 번째 줄이 이 작업의 **판단 기준**입니다. 표본을 눈으로 골라 읽으면 원하는
결론을 만들 수 있으므로, 독립적으로 붙은 축(`support_type`)을 대리지표로 삼아
쟀습니다. 네 번째 줄은 설계 선택도 같은 자로 했다는 기록입니다 — 문서 전체를
지원방식 문맥으로 넘기면 신청서류·유의사항의 `금리`·`상환` 이 걸려 **문서
길이가 지원방식을 정하게** 됩니다.

> **`컨설팅` 축은 F1 이 0.207 → 0.123 으로 내려갑니다.** 원인을 확인했습니다 —
> `service` 31 → 23, `mixed` 6 → 19 로, 빠져나간 8건이 대부분 `mixed`
> (현금 증거와 서비스 증거가 함께 잡힌 상태)로 갔습니다. `service ∪ mixed`
> 로 읽으면 37 → 42 로 오릅니다. 규칙이 나빠진 것이 아니라 **한 단계 더 세분해
> 판정한 것**이고, F1 은 그 세분을 오답으로 셉니다.

## 3. 모델 3 — 사업 설계 이상패턴 탐지 (유사사업 대비 이례성 · 검토 우선순위 보조)

> **정의(현재).** 신규 사업의 정책적 정상·이상 여부를 판정하지 않고,
> 지원규모·지원건수·지원율·사업기간 등 정형 설계정보를 벡터화하여 유사사업
> 비교군의 대표 설계와 얼마나 떨어져 있는지를 계산한다. 이를 통해 과거
> 유사사업 대비 드문 설계 조합과 주요 차이축을 제시해 담당자의 검토
> 우선순위 설정을 보조한다.
>
> 서비스 문구는 `이상 사업 / 부적절 / 수정 필요`가 아니라 `유사사업 대비
> 이례적인 편 / 검토 우선순위 높음 / 관련 설계축 확인 필요`를 씁니다.

### 3.0 담당자에게 왜 필요한가

모델 3은 지원액 하나만 보는 모델이 아닙니다. 기업당 지원액·지원 기업수·지원비율
·사업기간 등 **정형 설계요소를 함께** 봅니다.

```text
기업당 지원액은 높음
지원 기업수는 적음        ← 값 하나하나는 흔할 수 있어도
사업기간은 김               그 조합 전체가 유사사업에서는 드물 수 있다
지원비율도 높음
```

설계값을 하나의 vector 로 만들고 유사사업 비교군의 대표 vector 와 비교해
**기존사업과 다른 설계 조합**을 찾습니다. 방향·기여도는 점수에 넣지 않고
**어떤 설계축이 차이를 만들었는지 설명하는 용도로만** 씁니다.

```text
신규사업 Vector X          D = X − C
비교군 대표 Vector C        ‖D‖ = 유사사업 대비 설계 패턴 이례성 score
```

담당자에게 나가는 말은 "이 사업은 이상합니다 / 잘못 설계되었습니다"가 아니라
이렇습니다.

```text
"유사사업 대비 설계 조합의 차이가 큰 편입니다."

주요 차이축:  기업당 지원액 ↑84%  /  사업기간 ↓13%  /  지원기업수 ↑3%
```

그래서 담당자는 **요청서 전체를 같은 강도로 검토하는 대신, 기존사업과 차이가 큰
설계요소부터 먼저 확인**할 수 있습니다.

> **여러 설계요소의 조합이 유사사업과 얼마나 다른지 보여줘 검토 우선순위를
> 잡게 합니다.**

**상태: 구조 채택(Freeze).** 재설계(M44) → 안정성·민감도 검증(M47~M49) →
얇은 비교군·설명축 보완(M50~M51) → 설계 희소성 개선 실험 4종(M58~M61)까지
마쳤습니다.

> **운영 경고 cutoff 미확정은 모델 미채택을 뜻하지 않습니다.** 모델 3은
> 정상/이상을 최종 분류하는 classifier가 아니라 이례성 점수·상대순위·주요
> 차이축을 제공하는 참고신호이므로, 그 셋은 지금 그대로 쓸 수 있습니다.
> "상위 몇 %부터 검토 대상으로 표시할 것인가"는 실제 담당자의 검토 가능
> 업무량에 달린 **운영 파라미터**라 사용자 workflow 검증 이후 정합니다.

| 구성요소 | 상태 |
|---|---|
| 이례성 점수 (비교군 대표벡터 거리) | **사용** |
| 비교군 내 상대순위 | **사용** |
| 주요 차이축 (기여도 %) | **사용** |
| 운영 경고 cutoff (상위 2/5/10%) | 사용자 workflow 검증 후 결정 |

### 3.1 첫 버전(OneClassSVM)이 왜 무너졌는가

| 검증 기준 | recall | precision | ROC-AUC |
|---|---:|---:|---:|
| 합성 이상치 (튜닝 후) | 80.0% | 100% | — |
| 사람 라벨 50건 (M30, 실제 검증) | 0.33 | 0.25 | **0.48** |

ROC-AUC 0.48은 사실상 무작위 수준입니다. 합성 이상치는 "만들어 넣은
방향으로 잘 도는가"만 잴 뿐, 사람이 실제로 이상하다고 보는 것과는 다른
축이었습니다. 사람이 비전형이라 본 15건 중 8건은 설계가 드문 게 아니라
**값이 잘못 들어온 행**(파싱 오류 — 예: 사업기간 "26년"이 실은 공고연도
2026 오파싱)이었습니다.

### 3.2 구조를 다시 짠 결과 (M44, 최신)

비교군 대표벡터와의 거리(`||X − C||`)를 이상 점수로, 벗어난 방향은 점수에
안 넣고 설명 전용으로만 쓰는 구조로 재설계했습니다. **독립 라벨 53건**
(양성 5건)으로 **재튜닝 없이** 측정:

**이 표의 이름은 `정상/이례 판별력`이 아니라 `이례성 점수의 탐색적 정합성
(독립 라벨셋)`입니다.** 모델 3은 판정기가 아니므로 이 숫자들은 최종 정책
판별 정확도가 아니라, **사람이 이례적이라고 본 사례가 모델 점수에서도 상대적으로
높은 순위에 있는지**를 본 탐색적 지표입니다. 라벨을 붙인 사람이 공무원·사전협의
전문가가 아니므로 `전문가 Ground Truth`라고 부르지 않고, **비전문가 탐색적
라벨셋**이라고 씁니다.

**이례성 점수의 탐색적 정합성 (독립 라벨셋 53건, 양성 5건)**

| 지표 | 값 | 95% CI |
|---|---:|---|
| ROC-AUC | **0.7542** | 0.575 ~ 0.908 |
| PR-AUC | **0.2184** | 0.144 ~ 0.519 |
| Recall (상위 20%) | 0.60 | 0.000 ~ 1.000 |
| Precision (상위 20%) | 0.27 | 0.000 ~ 0.417 |
| F1 | 0.375 | 0.000 ~ 0.588 |
| 재표집 안정성(hold-out 상위11 유지율) | 0.918 | — |

신뢰구간을 함께 싣는 이유는 이 표가 **작은 표본에서 나온 탐색적 결과**임을
숫자로 드러내기 위해서입니다. PR-AUC 0.2184 / Precision 0.27 은 양성이 9.4%인
평가셋에서 상위 20%를 경고로 잡았을 때의 값이라, ROC-AUC 만 떼어 읽으면 실제보다
좋게 들립니다. 그래서 이 셋은 항상 함께 제시합니다.

M30의 0.48보다 크게 개선됐고 목록 안정성도 확보했지만 두 가지가 아직
막혀 있습니다 — **양성이 5건뿐이라 신뢰구간이 넓고**, 지금의 경고율 2%
임계선(pool 기준 0.980)을 이 53건에 그대로 적용하면 **경고가 0건**입니다.
임계선을 다시 잡으려면 점수가 아니라 **층화 추출된 별도의 운영
캘리브레이션 세트**가 필요합니다. 적용 범위도 전체의 59.9%(수치 축 2개
이상인 행)로 제한적입니다.

상세: `ml/reports/m30_m3_real_eval.md`(초기 붕괴 원인), `ml/reports/m44_m3_final_test.md`(재설계·최신 성능).

### 3.3 검증 방향 재정의 — 정답 대조에서 신호 안정성으로 (M47~M49)

3.2절의 53건·양성 5건은 **도메인 전문가(공무원·사전협의 담당자) Ground
Truth 가 아닙니다.** 이 라벨을 150~280건으로 늘려 ROC-AUC 를 재검증하려던
계획을 재검토했습니다 — 비전문가가 "이 사업이 행정적으로 비전형적인
설계인가"를 대규모로 판정하는 것은 신뢰성이 낮습니다. **대신 사람 라벨을
한 건도 쓰지 않고 잴 수 있는 것, 즉 이례성 신호 자체가 안정적인가를
검증했습니다.**

| 실험 | 검증 내용 | 핵심 결과 |
|---|---|---|
| M47 민감도 | 대표벡터·scaling 대안이 현행보다 나은가, 특정 feature 하나가 점수를 지배하는가 | mean·standard 유지 근거 확인. RobustScaler 는 ROC +0.0041 이지만 상위 30건 중 **67%를 다른 사업으로 교체** — ROC 하나만 보면 안 되는 근거 |

### 3.4 남은 두 약점을 마감하고 Freeze (M50~M51)

3.3절이 구조를 바꿀 근거가 없다는 것과 **약점의 위치**를 함께 찾아냈습니다.
① 흔들림이 얇은 비교군 5~6개에 집중, ② `기업당 지원액` 설명 귀속률 56%.
둘 다 탐지 점수 공식은 건드리지 않고 마감했습니다.

**M50 — 얇은 비교군 대표벡터 shrinkage: 현행 유지**

얇은 비교군의 대표벡터를 상위 비교군 쪽으로 끌어당기는 방식(`w = n/(n+k)`)을
k=5~40으로 훑었습니다. **대표벡터 분산은 0.2595 → 0.1318로 절반 가까이
줄었지만, 정작 목적이던 순위 흔들림은 14.24점 → 15.32점으로 늘었습니다.**

이례성 점수는 절대거리가 아니라 **비교군 내부 거리분포의 백분위**입니다.
대표벡터를 상위로 끌어당기면 구성원 전체가 자기 평균이 아닌 점에서
측정돼 내부 분포가 쏠리고, 상위 비교군도 재표집마다 흔들려 불안정 요인이
하나에서 둘로 늡니다. **대표벡터 안정성과 순위 안정성은 다른 문제였고,
운영에 중요한 것은 후자입니다.** 얇은 비교군 흔들림은 표본이 20~30건이라는
사실 자체에서 오는 것이라 계산법으로 풀 수 없습니다 — 표본 확대가 해법입니다.

**M51 — 설명축 attribution: 기여도 출력 채택**

`기업당 지원액` 귀속률 56%의 원인은 **신호 대 잡음비**였습니다.

| 설계축 | 비교군 내 기존 편차 | 10배 이동량 | 신호/잡음 | 귀속률 |
|---|---:|---:|---:|---:|
| 기업당 지원액 | 0.418 | 0.979 | **2.35** | 56% |
| 지원 기업수 | 0.454 | 1.352 | 2.98 | 72% |
| 지원비율 | 0.275 | 1.001 | 3.65 | 95% |
| 사업기간 | 0.198 | 4.130 | **20.85** | 79% |

금액은 log 축이라 10배를 곱해도 log10으로 1.0밖에 안 움직이는데, 비교군
안에서 원래 가장 넓게 퍼져 있습니다. **56%는 고장이 아니라 "금액 10배는
비교군 기준으로 그리 이례적이지 않다"는 사실의 반영**입니다. 그래서 고칠
것은 점수가 아니라 `argmax`라는 설명 연산자였습니다.

```text
기존   argmax |D_j|          -> "기업당 지원액이 원인"
채택   D_j² / ΣD² (부호는 D_j) -> "기업당 지원액 ↑84% / 사업기간 ↓13% / 지원기업수 ↑3%"
```

top1 적중률 자체는 argmax와 같습니다(`D_j²` 최대 = `|D_j|` 최대이므로
당연합니다). **이득은 적중률이 아니라 근소한 차이를 단정하지 않는
출력 형태**입니다. 한편 관련 범주축(`amount_type`·`support_unit`)을 금액에
묶는 semantic 합산은 금액을 65%로 올리지만 다른 축을 희생해 평균이
75%→74%로 낮아져 **채택하지 않았습니다**.

**탐지 구조 불변 확인**: 섭동 점수 동일, pool 순위상관 `1.000000` —
설명 로직만 바뀌었고 점수·순위·Top-K는 그대로입니다.

상세: `ml/reports/m50_m3_shrinkage.md`, `ml/reports/m51_m3_attribution.md`.

### 3.5 설계 희소성 점수 개선 실험 4종 (M58~M61)

3.4절까지는 **현행 구조가 우연에 기대고 있지 않은가**를 봤습니다. M58~M61 은
한 걸음 더 나가 **더 나은 구조가 있는가**를 봅니다. 지시서가 정한 순서 그대로
`비교군 정교화 → multi-prototype → thin cohort fallback → scaling/distance`
입니다.

네 실험 모두 **사람 라벨 ROC-AUC 를 목표로 튜닝하지 않았습니다.** 판정은
라벨 없이 pool 1,948행에서 재는 지표로 하고, exploratory ROC 는 보조로만
싣습니다. 판정 문턱(Top30 겹침 0.918 / Spearman 0.969)은 M44·M48 이 이미 잰
재표집 변동폭에서 가져와 **결과를 보기 전에 고정**했습니다.

| 실험 | 후보 | 판정 | 결정적 근거 |
|---|---|---|---|
| **M58** 비교군 정교화 | 지원성격만 / +지원단위 / +기관계열 | **현행 유지** | `+기관계열` 은 ROC 가 0.7542→**0.8271** 로 넷 중 가장 높은데도 reject — 재표집 Top30 이 0.796→0.709, 얇은 비교군 195→274 |
| **M59** multi-prototype | KMeans k=2 / k=3 | **현행 유지** | 재표집 Top30 0.796→0.729(k=2) / 0.720(k=3). 표집 50%에서는 0.656→0.469 |
| **M60** thin cohort fallback | MIN_COHORT 15~40 × 사다리 2종 | **현행 유지 (20)** | MIN_COHORT 30 은 얇은 비교군을 0으로 만들지만 전체 fallback 이 79→**197건**(pool 의 10%)으로 급증 |
| **M61** scaling / distance | robust · MAD · log1p · 축가중 · Mahalanobis | **현행 유지** | robust 는 상위 30건의 63%를 교체. 원인은 `지원비율` 하나가 기여도의 **96%**(현행 26%)를 가져가는 것 |

**이 실험들이 실제로 남긴 것 넷.**

**① "ROC 가 올라도 reject" 가 실물로 나왔습니다.** 지시서가 못박은 규칙이
M58 의 `+기관계열` 에서 정확히 발동했습니다. 기관계열은 pool 의 **37%가
결측**이라, 정보가 늘어난 것이 아니라 *기관계열을 아는 사업* 과 *모르는 사업*
을 갈라놓은 것에 가깝습니다. ROC 하나만 봤다면 채택했을 변경입니다.

**② 안정성과 동질성은 다른 축이고, 서로 반대로 움직입니다.** 비교군을 굵게
잡으면(`지원성격`만) 표본이 커져 재표집 안정성은 **전 구간 최고**가 됩니다.
그러나 차이벡터 중 범주 one-hot 의 점유율이 0.241→0.280 으로 **올라갑니다** —
점수가 "드문 설계"보다 *"융자인데 보조금 무리에 섞여 있음"* 을 더 재게
된다는 뜻입니다. 실험의 목적과 반대 방향이라 채택하지 않았습니다. 두 축을
같이 보지 않으면 **"전부 한 덩이로 묶으면 제일 안정적"** 이라는 결론에
도달합니다.

**③ 얇은 비교군은 계산법으로 풀리지 않는다는 것이 다시 확인됐습니다.**
M60 이 행 단위로 재보니 흔들림은 실제로 얇은 비교군이 독점합니다
(n≤30 행 14.22점 vs 두꺼운 비교군 2.23점, **6.4배**). 그런데 `MIN_COHORT` 를
올려서는 회수되지 않습니다 — 얇은 비교군이 사라지는 만큼 그 행들이 "전체
평균과 비교"로 떨어져, **안정성이 좋아진 것이 아니라 재는 대상을 바꿔서
흔들릴 일을 없앤 것**이 됩니다. 게다가 문턱을 20→25 로 올리면 얇은 비교군의
흔들림이 오히려 14.22→17.39점으로 **늘어납니다**: 원본에서 n=25인 비교군은
80% 재표집에서 n≈20이 되어 문턱 아래로 떨어지고, 그 순간 비교 대상이 통째로
바뀌기 때문입니다(**단계 이탈**). M50 의 shrinkage 도, 이번 fallback 문턱도
같은 벽에 부딪혔습니다. 해법은 모델링이 아니라 **그 비교군의 표본 확대**입니다.

**④ scaling 실험이 데이터 오류 1건을 찾아냈습니다.** 지시서 7절이 "바꾸기
전에 축부터 보라(왜도·꼬리·0값·단위 오류)"고 한 대로 진단을 먼저 돌린
결과입니다. `기업당 지원액`·`지원 기업수`는 log10 이 이미 잘 듣고 있었지만
(왜도 20.60→-0.14, 30.43→1.06), `지원비율` 은 최소값이 **-320%** 였습니다.
비율이 음수일 수 없으므로 파싱 오류이고, 886건 중 **정확히 1건**입니다
(`[전남] 2025년 강소기업 육성사업`). scaler 로 다룰 문제가 아니라 M31 파서
감사 대상입니다.

> **아쉽게 놓친 후보 하나를 기록해 둡니다.** M61 의 `Mahalanobis 유사` 는
> 재표집 안정성이 네 표집비율 **전부**에서 현행보다 낫고, 축 점유율도
> 0.377→0.332 로 내려가며, ROC 는 0.7542 로 동일합니다. 그런데 상위 30건의
> 10%가 교체되어 사전 고정 문턱(8%)을 2%p 넘겨 reject 됐습니다. **문턱을
> 결과를 보고 옮기지는 않습니다** — 그 순간 문턱은 판정 기준이 아니라 결론을
> 정당화하는 장식이 됩니다. 다만 이것은 "기각"이 아니라 **"라벨이 확보되면
> 가장 먼저 다시 볼 후보"** 입니다. 지금 갈라놓을 근거가 양성 5건뿐이라 못
> 가리는 것입니다.

상세: `ml/reports/m58_m3_cohort_refine.md`, `ml/reports/m59_m3_prototype.md`,
`ml/reports/m60_m3_fallback.md`, `ml/reports/m61_m3_scaling.md`.

### 3.7 데이터 품질을 원천에서 고치고 같은 구조로 다시 (M62 · M64 · M65)

3.6 의 남은 항목 중 **모델링이 아닌 것 셋**(지원단위 결측 · 파싱 오류 ·
cohort feature 품질)을 실행하고, 구조를 하나도 건드리지 않은 채 재평가했습니다.
새 이상탐지 알고리즘은 찾지 않았습니다.

**원인 — 파서가 아니라 저장 단계였습니다.**

`f06_design_features.py::_pack_bizinfo` 가 근거문 자리에 **금액을 뽑지 않은**
**텍스트**를 넣어 저장했습니다 — 목록 표본에는 제목을, Open API 행에는 CSV
요약을. F05 는 공고문 원문에서 금액·지원비율·지원기업수를 뽑았는데 그 원문이
하류로 넘어오지 않아, 근거문에서 도출하는 두 파생값이 엉뚱한 텍스트를 보고
만들어졌습니다 — 그 둘이 하필 **비교군 사다리의 축**입니다.

M65 가 F06 을 원천에서 고쳤습니다(전처리결과서 8.4). 목록 표본과 Open API

2,451 로 늘어(사업기간이 복원되며 수치축 2개 조건을 넘긴 행) 크기가 다르므로,

읽는 순서가 결론입니다.

1. **비교군 구성은 확실히 좋아졌습니다.** 얇은 비교군 행이 39% 줄고, 비교군
   표본수의 하위 10%가 30 → 45 로 굵어지고, 두꺼운 비교군과 전역 fallback 행의
   순위 변동이 각각 2.08 → 1.58 · 1.28 → 0.64 로 내려갑니다. 늘어난 pool
   전체(2,451행)에서는 전역 fallback 이 79 → 57 입니다.
2. **그런데 상위 목록의 재현성은 나빠졌습니다.** 순위상관은 그대로인데 Top30
   겹침만 0.827 → 0.635 입니다. 원인은 같은 표 안에 있습니다 — 얇은 비교군
   행의 변동이 13.83 → 19.05 로 **올라갑니다.**
3. **M60 이 이름 붙인 단계 이탈입니다.** `support_method` 를 바로잡으면 L1
   (성격x방식) 칸이 잘게 나뉘고 일부가 `MIN_COHORT=20` **문턱 바로 위**에
   놓입니다. 80% 재표집에서 그 칸은 문턱 아래로 떨어져 L2 로 후퇴하고, 그
   순간 비교 대상이 통째로 바뀝니다. 실제로 성격만으로 후퇴한 행이 126 → 161
   로 늘었습니다.

> *`grant` 한 덩어리로 뭉쳐 있어서* 나온 숫자입니다 — 목록이 흔들릴 일이
> 없었던 것이지 맞는 목록이라 안정적이었던 것이 아닙니다. **안정성과 정합성이**
> **반대로 움직이는 자리**이고, M58 이 `A1 성격만` 에서 이미 같은 것을
> 봤습니다(굵게 묶으면 전 구간 최고 안정성).

**얇은 비교군 표본 확대는 절반 이상이 '새 수집'이 아니었습니다.** 지시서
1순위가 "표본 확대 가능성 확인"이라 세어 봤습니다. 수정 후 얇은 비교군

**M58 A3(+지원단위) 재검토 — 다시 reject.** 3.6 이 "결측 15% 해소되면 열린다"고
예약해 둔 항목이라 실행했습니다. 문턱은 M58 이 결과를 보기 전에 고정한 값
그대로(Top30 겹침 0.918 / 순위상관 0.969)입니다.

| | 현행 | A3 +지원단위 |
|---|---:|---:|

| 현행 대비 Top30 겹침 | 1.000 | **0.767** |
| 얇은 비교군 행 | 274 | 297 |
| 탐색적 ROC-AUC | 0.7250 | **0.7833** |

M58 의 `+기관계열` 과 **같은 모양**입니다 — ROC 는 더 높은데 목록이 통째로
바뀝니다. 같은 행 기준 결측을 14.9% → 10.1%로 줄이고도 열리지 않은 이유는
결측률이 아니라 **비교군을 한 단계 더 자르면 문턱 근처 칸이 또 늘기**
**때문**입니다. 결측을 더 줄여서 열릴 문이 아니라 **표본이 늘어야 열리는**
**문**이었습니다.

**Mahalanobis 유사 거리는 돌리지 않았습니다.** 지시서가 "향후 재검토 후보로만

## 5. 검증 방법 (공통 원칙)

- **그룹 K-Fold**: 같은 사업(`program_stem`)의 재공고가 학습/검증에 갈라지면
  최대 macroF1 0.025~0.26이 부풀려집니다. 전 모델 통제.
- **fold 내부 fitting**: TF-IDF·Scaler·결측 대치값을 fold train에만 적합.
- **외부/실제 검증셋**: CV·합성 벤치마크만으로 채택하지 않고, 모델 1은 외부
  Open API 131건, 모델 3은 사람 라벨 50건으로 재확인 — 둘 다 CV 단계와
  다른 결론이 나왔습니다.
- **정답이 불확실한 과제는 정답 대조 대신 신호 안정성을 검증**: 모델 3처럼
  "무엇이 정답인가" 자체에 비전문가 라벨의 신뢰도 문제가 있는 과제는, 라벨을
  늘려 정확도를 재검증하는 대신 재표집·민감도·synthetic stress test로
  **라벨 없이 신호가 안정적인지**를 검증합니다(3.3절).

- **타깃이 파싱된 문장은 feature 로 쓰지 않습니다**: 모델 2의 근거문
  (`evidence_text`)은 타깃 `per_recipient`가 뽑혀 나온 바로 그 문장이라,
  넣으면 정답을 읽어주는 것과 같습니다. 제목만 씁니다(제목에 금액 표현이
  있는 행은 0건).
- **텍스트를 넣을 때는 그룹 기준을 한 단계 더 조입니다**: 제목 텍스트는
  "지역·연도만 다른 거의 같은 공고"라는 새 누수 경로를 만듭니다. 실제로
  `program_stem` 그룹만 쓰면 그런 사업 계열 **122개가 학습/검증에 걸쳐**
  있었습니다. `normalize_business_title()`로 만든 계열 그룹에서는 걸치는
  계열이 0개이고, 거기서도 개선율이 유지되는지 확인합니다(2.3절, 20.8%).
