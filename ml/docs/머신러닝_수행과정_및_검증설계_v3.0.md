## 0. 요약

**베이스라인부터 전 후보를 같은 분할·같은 시드로 측정**해서 채택 근거를 남긴다는 원칙은 v2.0과 같다. 다만 설계서 v3에서 모델 3의 문제 정의가 바뀌었다.

| 모듈 | 과제 | 채택 | 성능 | 베이스라인 대비 |
|---|---|---|---|---|
| 1 | 지원성격 분류 (26클래스) | TF-IDF + LinearSVM | Macro F1 0.643 | Majority 0.017 |
| 2 | 월별 공고량 예측 | Ensemble(단순평균) | MAE 21.45 | Seasonal Naive 22.75 (**+5.7%**) |
| 3 | 지원규모 **추출 → 집계 → 시계열** | 정보추출 파이프라인 | 관측 3,786건 / 7년치 | **예측은 미제공**(조건 미충족) |

**모델 3이 단일 classifier에서 파이프라인으로 바뀌었다.** 설계서 v3 14장이 요구한 대로다. 프로젝트에 실제로 필요한 질문은 "이 공고의 지원금이 어느 등급인가"가 아니라 "분야·시기별 지원규모가 어떻게 변해왔는가"이기 때문이다. 기존 3등급 분류(Macro F1 0.691)는 탐색 결과로 보존한다(7장).

설계서에 있던 **대분류(8분야) 분류는 제외**했다. 기업마당이 이미 8개로 분류해 부여하고 있어 새로 만들 필요가 없고, 대신 **집계 축**으로 쓴다.

**업종 분류도 제외**했다. 애초 필요했던 것은 "융자를 지원하는지 연구개발비를 지원하는지" 같은 **지원 방식** 판별이었고, 이는 업종(식품/ICT/로봇 등 산업분야)이 아니라 **중분류**의 역할이다. 중분류 61종을 지원성격 26종으로 재그룹화해 모델 1을 다시 정의했다(5장).

모델 1은 학습만으로 끝나지 않고, 라벨 없는 Open API 1,570건에 실제로 **적용**했다(6-A장). 신뢰 182건 / 참고용 281건 / 판단보류 1,107건.

### 1.1 원천 3종

인코딩이 제각각이다. 목록 CSV는 `cp949`(잘못된 바이트 1개 포함 → `errors="replace"`), Open API는 `utf-8-sig`다.

### 1.2 공고문 원문 취득

세 원천 모두 요약문만 담고 있어 지원규모 정보가 빈약했다. 실제 공고문 파일을 받는 경로를 실측으로 규명했다.

| | 목록 97,794건 | Open API 1,570건 |
|---|---|---|
| 출발점 | `상세URL` (302 → 상세페이지) | `printFlpthNm` |
| 파일 URL | 페이지 HTML 안의 `/cmm/fms/fileDown.do?atchFileId=…` | **이미 CSV에 있음** |
| 요청 수 | 2회 (페이지 → 파일) | 1회 |

- 인증 조건: `JSESSIONID` 쿠키 + `Referer` 헤더가 없으면 **403**
- 페이지의 뷰어 경로(`DG_viewer/…&viewerSelect=image`)는 원본을 **이미지로 렌더링**하므로 사용하지 않음
- `robots.txt` 확인: Disallow 목록(`/super /upload /html /images /agspa /error /common /lib /WEB-INF /download /direct_do`)에 사용 경로(`/cmm/fms/`, `/sii/siia/`)가 없음

**다운로드 실적**

| 대상 | 결과 |
|---|---|
| Open API 1,570건 | 성공 **1,563 (99.87%)** / 실패 2 / 586MB / 30.2분 |
| 목록 표본 5,000건 | 성공 **4,757 (95.1%)** / 문서없음 243 / 실패 0 / 3시간 11분 |

목록 전량은 약 19.6만 요청(54시간)으로 공공 서버 부담이 커서 **층화 표본 5,000건**만 받는다.
연도별 탐침 결과 **2013~2018은 첨부 0/5, 2019~2025는 5/5**여서 2019년 이후로 한정했고, 분야 8 × 연도 7 균등 배분했다(분야 570~635, 연도 661~724).

"문서없음" 243건은 첨부가 zip·이미지뿐이거나 아예 없는 공고다.

### 1.3 파일 형식과 추출 — 도구 교체로 해결

공고문 원문은 PDF만이 아니다. 전체 6,325개 파일 기준:

| 형식 | 건수 | 비중 |
|---|---:|---:|
| **HWP** | 3,755 | **59.4%** |
| PDF | 2,383 | 37.7% |
| HWPX | 120 | 1.9% |
| 이미지(png/jpg) | 62 | 1.0% |
| DOCX | 5 | 0.1% |

**HWP가 과반이다.** Open API는 PDF가 많지만(55%) 목록 표본은 HWP가 68%였다. 초기 도구(PyMuPDF + pyhwp/LibreOffice)로는 이 3,755건을 처리할 수 없었다 — Windows 로컬에 LibreOffice가 없어 원격 리눅스 박스가 필요했고, pyhwp는 표 내용을 `<표>`로 비워버렸다.

**도구를 교체해 두 문제를 동시에 해결했다.**

| | E01 (기존) | **E02 (교체 후)** |
|---|---|---|
| PDF | PyMuPDF — 표 셀이 줄바꿈으로 흩어짐 | **pdf-inspector**(Rust) — 마크다운 표로 행-열 관계 보존 |
| PDF 스캔본 판별 | 페이지당 50자 휴리스틱 | `classify_pdf` — 신뢰도 포함 분류 |
| HWP | pyhwp(표 소실) 또는 LibreOffice(원격 필요) | **rhwp-python** — 로컬에서 표까지 보존 |
| HWPX | ZIP+XML | 동일 (rhwp 폴백 추가) |

**추출 실적: 6,325건 중 성공 6,057건(95.8%), 표 보존 2,030건.**
실패 268건은 대부분 이미지 파일(62건)과 미지원 확장자로, 원래 OCR 대상이다.

무작위 검증: PDF 25건 중 성공 23·표보존 22(88%), HWP 59건 전건 성공(평균 7,029자).

> **부수 효과**: rhwp가 LibreOffice를 대체하면서 **HWP 처리 목적의 원격 GPU 박스가 불필요**해졌다. 원격은 이제 딥러닝 학습에만 쓰면 된다.

## 3. 발견한 누수 3종

이 프로젝트에서 성능표를 무의미하게 만들 수 있었던 문제들이다.

### 3.1 라벨 누수 ① — 2023 엑셀 `사업개요`

첫 줄에 정답이 그대로 적혀 있다.

```
【공고이름】 2023년 개인정보 보호·활용 기술개발 스타트업챌린지 지원
【사업개요】 경영 / 사업화(SW·서비스) / 중소기업(ICT·SW(보안)) / 개인정보보호위원회(...) / 4월
 ① 목적: ...
```

**노출률: 대분류 100.0% / 중분류 99.9% / 업종 45.9%**

→ `text_for_model`에서 메타 줄을 제외하고 본문(①목적/②내용/③대상)만 사용.

**실측 효과** (같은 5-fold, 메타 줄 포함 여부만 다름)

| 타깃 | 모델 | 누수 포함 | 누수 제거 | 차이 |
|---|---|---:|---:|---:|
| 중분류 | LinearSVM | 0.7762 | 0.5129 | **−0.2633** |
| 중분류 | LogisticRegression | 0.6760 | 0.4494 | −0.2266 |
| 업종 | LinearSVM | 0.8721 | 0.7030 | **−0.1691** |
| 업종 | LogisticRegression | 0.7853 | 0.6414 | −0.1439 |

메타 줄을 안 지웠다면 Macro F1 0.87짜리 모델을 보고했겠지만 실제로는 0.70이다.

### 3.2 라벨 누수 ② — Open API `hashtags`

첫 토큰이 분야 라벨과 동일하다(`경영,경기,2026,...`). **노출률 100.0%**
→ 분야명과 겹치는 토큰을 제거한 `hashtags_safe` 생성.

### 3.3 시간 누수 — 시계열 피처

`rolling_mean_12`를 전체 시리즈에 걸어놓고 나중에 자르면, 2022년 검증 샘플의 피처에 이미 2023년 값이 들어가 있다.
→ **모든 lag/rolling을 `shift(1)` 이후에 계산.** 시점 t의 피처는 t−1 이전 정보만 담는다.

## 4. 검증 설계 (핵심)

### 4.1 모델별 분할 방식

| | 모델 1 분류 | 모델 2 공고량 | 모델 3 등급분류*(탐색)* | 모델 3 지원규모 시계열 |
|---|---|---|---|---|
| **방식** | Stratified 5-Fold | **Walk-forward** 3-Fold | **GroupKFold** 5-Fold | **Walk-forward** 2-Fold |
| **분할 단위** | 행 (층 = 클래스) | 시간 | 그룹 = 사업명 | 시간 |
| **데이터** | 900행 | 1,072행 | 361행 | 80개월 |
| **train : val** | **80 : 20** (고정) | 89~91 : 9~11 (가변) | **80 : 20** (고정) | 83~90 : 10~17 (가변) |
| **전 데이터 검증 사용** | 100% | **26.9%** | 100% | 25% |
| **K-Fold 교차검증인가** | ✅ | ❌ | ✅ | ❌ |

시계열 두 모델(모델 2, 모델 3 시계열)은 **walk-forward validation**이며 K-Fold가 아니다. 아래 4.2에서 이유를 설명한다.

### 4.2 fold별 실제 행수

**모델 1 — Stratified 5-Fold (중분류 896행)**

| fold | train | val |
|---|---:|---:|
| 1 | 716 (79.9%) | 180 (20.1%) |
| 2~5 | 717 (80.0%) | 179 (20.0%) |

896행 전부가 검증에 **정확히 1회씩** 사용된다.

**모델 2 — Walk-forward 3-Fold (1,072행)**

| fold | train | val |
|---|---:|---:|
| 1 | ~2021-12 · 768행 (88.9%) | 2022년 · 96행 (11.1%) |
| 2 | ~2022-12 · 864행 (90.0%) | 2023년 · 96행 (10.0%) |
| 3 | ~2023-12 · 960행 (90.9%) | 2024년 · 96행 (9.1%) |

**이것은 K-Fold 교차검증이 아니다.** 두 가지가 다르다.

1. 비율이 fold마다 달라진다(train이 계속 커지는 expanding window)
2. 1,072행 중 검증에 쓰인 건 **288행(26.9%)뿐**이고 나머지 784행(2014~2021)은 train 전용이다

K-Fold였다면 2014년 데이터도 검증에 쓰여야 하는데, 그러면 **2020년 데이터로 학습해 2014년을 예측**하게 된다. 시계열에서는 미래로 과거를 맞추는 누수다(설계서 13장 규칙 2).
문헌에서는 *time series cross-validation* / *rolling-origin evaluation*이라 부르지만, 산출물에는 **walk-forward validation**으로 표기하는 것이 정확하다.

2025년은 3/27까지의 부분 연도라 평가에서 제외했다.

**모델 3 — GroupKFold 5-Fold (361행 / 그룹 350개)**

| fold | train | val |
|---|---:|---:|
| 1 | 288 (79.8%) | 73 (20.2%) |
| 2~5 | 289 (80.1%) | 72 (19.9%) |

그룹은 **연도·지역 태그를 지운 사업명**이다. 같은 사업이 해마다 재공고되므로(`2025년 X사업` / `2026년 X사업`) 단순 KFold면 같은 사업이 train·test에 나뉘어 담겨 성능이 부풀려진다.

### 4.3 fold 내부에서 통제한 누수

**fold 밖에서 미리 계산하면 안 되는 것들**이다.

| 대상 | 잘못된 방식 | 적용한 방식 |
|---|---|---|
| TF-IDF 어휘 | 전체 데이터에 fit | **Pipeline으로 fold train에만 fit** |
| TruncatedSVD | 전체에 fit | fold train에만 fit |
| StandardScaler | 전체에 fit | fold train에만 fit |
| 결측 대치값(중앙값) | 전체 중앙값 | **fold train의 중앙값** |
| lag·rolling 피처 | 전체 시리즈에 rolling | **shift(1) 이후 계산** |
| SARIMA / Prophet | 전체 시리즈 1회 적합 | **fold마다 재적합** |
| 분야별 중앙값 베이스라인 | 전체 중앙값 | fold train에서 산출 |

**예외**: 사전학습 문장 임베딩(SBERT)은 우리 라벨을 전혀 보지 않으므로 전체에 대해 한 번 계산해도 누수가 아니다.

### 4.4 알려진 제약

- 중분류의 가장 작은 클래스가 **2건**이라 5-fold에서 fold 5개 중 2개에만 검증 표본이 들어간다. Macro F1이 낮게 나오는 원인 중 하나다.
- 단일 표본 클래스(중분류 13종 / 업종 9종)는 층화가 불가능해 제외했다. 커버리지는 98.6% / 99.0%로 손실은 작다.
- **고정 홀드아웃 테스트셋이 없다.** 데이터가 작아 전량을 교차검증에 쓴다. 설계서 18장 5순위가 요구한 "실제 서비스 입력과 동일한 형태의 별도 테스트셋"은 미구성 상태다.

## 5. 모델 1 — 지원성격 분류

### 5.0 문제 재정의 — 업종에서 지원성격으로

초기에는 대분류(8분야)와 함께 **업종**(식품/ICT/로봇 등 65종)도 분류 대상으로 검토했으나, 실제 필요는 "이 사업이 **융자**를 지원하는지 **연구개발비**를 지원하는지" 같은 **지원 방식** 판별이었다. 이건 업종이 아니라 **중분류**(연구개발/융자/보증/사업화/컨설팅 등)의 역할이라 **업종 분류는 제외**했다.

라벨 출처도 재확인했다. 세 원천 중 지원성격 라벨은 **2023 중앙부처 엑셀 909건에만 있다.**

| 원천 | 규모 | 대분류(8종) | 지원성격 |
|---|---:|:---:|:---:|
| 장기 공고목록 | 97,794건 | ✅ | ❌ |
| Open API | 1,570건 | ✅ | ❌ |
| **2023 중앙부처 엑셀** | 909건 | ✅ | **✅ 여기만** |

기업마당 두 원천은 8분야만 매기고 지원 방식은 어디에도 없다. 이 라벨의 유일한 출처로 학습한 모델을 라벨 없는 나머지 데이터에 적용하는 것이 모델의 목적이다(→ 7장).

### 5.1 중분류 재그룹화 — 61종을 26종으로

중분류 원본 61종은 `사업화(일반)/사업화(콘텐츠)/사업화(기술)/사업화(SW·서비스)/사업화(수출)`처럼 **괄호 안 세부유형까지 쪼개져** 과도하게 세분화돼 있었다. 괄호 앞 대분류만 남기면 지원성격 단위로 자연스럽게 묶인다.

```python
def coarsen(v):
    stripped = re.sub(r"\([^)]*\)", "", v)   # 괄호 제거 먼저 (괄호 안 콤마 대응)
    return stripped.split(",")[0].strip()     # 복수라벨은 첫 값을 대표로
```

| 단계 | 클래스 수 |
|---|---:|
| 원본 중분류 | 61종 |
| 괄호 제거 후 | 32종 |
| 지원 3건 미만 제외 (`MIN_SUPPORT=3`) | **26종 / 900건** |

**상위 분포**: 사업화 253 / 연구개발 109 / 컨설팅 100 / 판로 87 / **융자 49** / 설비 47 / 고용보조 36 / 교육훈련 36 / 기타지원 36 …

- 입력: `text_for_model` = 사업명 + ①목적 + ②내용 + ③대상 (메타 줄 제외, 3장 참조)
- 벡터화: `char_wb` 2~4 n-gram TF-IDF

### 5.2 결과 (지원성격 26클래스, 900건)

| 모델 | Accuracy | Macro F1 | Weighted F1 |
|---|---:|---:|---:|
| **TF-IDF + LinearSVM** | 0.7567 | **0.6428** | 0.7500 |
| TF-IDF + LogisticRegression | 0.7444 | 0.5866 | 0.7333 |
| SVD + XGBoost | 0.6644 | 0.3998 | 0.6321 |
| SVD + CatBoost | 0.6567 | 0.3662 | 0.6210 |
| SVD + LightGBM | 0.6322 | 0.3128 | 0.5998 |
| SVD + RandomForest | 0.5867 | 0.2979 | 0.5418 |
| Majority (하한선) | 0.2811 | 0.0169 | 0.1234 |

61클래스(중분류 원본, Macro F1 0.513) → 26클래스(0.643)로 재그룹화만으로 성능이 올랐다. 클래스가 커지면서 클래스당 표본이 늘어난 결과다.

### 5.3 핵심 클래스 성능 — 융자 vs 연구개발

| 클래스 | Precision | Recall | F1 | 표본 |
|---|---:|---:|---:|---:|
| **융자** | 0.849 | 0.918 | **0.882** | 49 |
| **연구개발** | 0.759 | 0.927 | **0.835** | 109 |
| 사업화 | 0.854 | 0.763 | 0.806 | 253 |
| 판로 | 0.757 | 0.897 | 0.821 | 87 |
| 고용보조 | 0.821 | 0.889 | 0.853 | 36 |
| 종합지원 | 0.000 | 0.000 | 0.000 | 4 |
| 판로지원 | 0.000 | 0.000 | 0.000 | 5 |

**융자와 연구개발 둘 다 F1 0.83 이상.** 혼동행렬상 두 클래스가 서로 오분류되는 사례는 1~4건뿐으로, 상호 혼동 없이 구분된다. 반면 표본이 3~5건인 꼬리 클래스는 F1 0.0으로 전혀 못 맞춘다 — 26클래스에서도 꼬리는 여전히 길다.

### 5.4 채택 근거

**LinearSVM 채택.** GBDT 3종이 뒤진 주된 원인은 **SVD**다. TF-IDF 6만 차원을 150차원으로 압축하면서 정보가 크게 깎이는데, GBDT는 모두 그 압축본을 입력으로 받는다. 시계열·회귀에서 CatBoost가 1위였던 것과 정반대 결과라, **데이터 성격에 따라 승자가 갈린다**는 근거가 된다.

### 5.5 겪은 문제

**LightGBM 설정 붕괴.** 초기 측정(중분류 49클래스 단계)에서 LightGBM이 Macro F1 0.0081로 Majority보다도 낮았다. 클래스당 표본이 약 14개인데 `min_child_samples=5`가 분할을 막고 있었다. `min_child_samples=1`로 완화하니 0.2338로 회복 — 모델 성질이 아니라 설정 문제였다.

**CatBoostClassifier shape 버그.** `predict()`가 `(n,1)` 형태를 반환해 인덱싱 오류가 났다(m04, m06 두 곳에서 재발). `.ravel().astype(int)`로 평탄화해 해결.

GBDT 예산도 조정했다. 부스팅은 다중분류에서 **반복 1회당 클래스 수만큼 트리**를 만든다. 26~49클래스 × 400 iterations는 fold당 최대 19,600그루로 비현실적이어서, 세 모델 **모두 동일하게** 150~300으로 낮춰 공정 비교를 유지했다.

## 6-B. 모델 2 — STL 시계열 EDA (설계서 v3 10장)

설계서 v3에서 정식 단계로 추가됐다. STL은 예측 모델이 아니라 **시계열 구조를 진단해 이후 모델 선택을 정당화하는 EDA**다. 시각화만으로 "좋다/나쁘다"를 말하지 않고 정량 지표를 낸다.

```
Y(t) = Trend(t) + Seasonal(t) + Residual(t)

Trend Strength     F_T = max(0, 1 - Var(R)/Var(T+R))
Seasonal Strength  F_S = max(0, 1 - Var(R)/Var(S+R))
잔차 자기상관       Ljung-Box(lag 12), p<0.05 면 시간 의존성 잔존
```

### 6-B.2 이 표가 답하는 세 가지

**① Seasonal Naive를 baseline으로 쓰는 근거가 성립한다.** 계절성 강도 ≥0.5인 분야가 **8개 중 6개**다. 설계서 v3 12.1이 "STL에서 연간 계절성이 확인되면 Seasonal Naive를 핵심 baseline으로 둔다"고 한 조건이 충족된다.

6.2절에서 Seasonal Naive(MAE 22.75)가 XGBoost·SARIMA·RandomForest를 모두 이긴 것이 **우연이 아니라 데이터 구조상 당연한 결과**였음이 확인된다. ACF lag12가 0.62~0.75로 lag1과 맞먹는다.

**② 예측 난도가 분야별로 갈린다.** 설계서 v3 10.1 목적 5번이 요구한 구분이다.

- 예측 유리: 내수·경영·창업 (추세·계절성 모두 강함, 잔차 10~19%)
- **예측 불리: 기타** (추세 0.16 / 계절성 0.10 / **잔차 78%**) — 구조로 설명되는 부분이 거의 없다. 월평균 13.6건으로 규모도 작아 노이즈가 지배한다
- 애매: 인력 (잔차 55%)

설계서 v3 18장이 지원규모에 세운 "조건 미충족 시 예측값을 억지로 만들지 않는다"는 정책을, **공고량에서도 '기타' 분야에 적용할 근거**가 된다.

**③ 잔차에 시간 의존성이 남는 분야가 4개**(경영·수출·인력·창업)다. STL로 추세·계절성을 걷어내도 자기상관이 남는다는 뜻이라, AR 계열(SARIMA)이나 lag feature가 추가로 기여할 여지가 있다.

### 6-B.3 STL과 누수 (설계서 v3 10.5)

이 절의 STL은 **EDA 용도**이므로 전체 기간을 써도 된다. 다만 STL 성분을 예측 모델의 **Feature로 쓸 경우 반드시 fold 내부에서만 fit**해야 한다. 전체 기간 STL을 먼저 계산하고 나중에 train/val을 자르면 미래 정보가 들어간다.

## 6-A. 모델 1의 실전 적용 — 라벨 없는 데이터에 추론

지원성격 라벨은 2023 엑셀 909건에만 있고, Open API 1,570건에는 없다. 이걸 채우는 두 가지 방법을 검토했다.

| 방식 | 내용 |
|---|---|
| **A안 (채택)** | 2023 엑셀로 학습한 모델을 Open API 원문에 **그대로 적용** (추론만, 새 라벨 학습 없음) |
| B안 (미채택) | A안 예측 중 확신도 높은 것만 새 학습 라벨로 채택해 재학습 (의사라벨링, 사람 검수 필요) |

A안이 실제 서비스가 할 일과 동일하다 — 신규 사업계획서는 애초에 라벨이 없다. B안은 모델이 낸 라벨로 모델을 다시 학습시키는 구조라 편향이 강화될 위험이 있어 보류했다.

### 규칙 기반 라벨링은 기각

원문에 명시적 신호가 있는지 먼저 확인했다. 원문 906건에 지원성격 키워드(융자/연구개발/사업화/컨설팅/판로/설비 등)를 매칭한 결과:

| 항목 | 결과 |
|---|---:|
| 키워드가 하나라도 매칭 | 836/906 (92.3%) |
| **2개 이상 카테고리가 동시에 매칭** | **670/906 (74.0%)** |
| "지원방식:" 처럼 명시적으로 적힌 문서 | 38/906 (**4.2%**) |

74%가 중의적이라 규칙으로 라벨을 만들면 오히려 잘못된 라벨을 대량 생산할 위험이 크다고 판단, 모델 확률 예측을 그대로 쓰기로 했다.

### 1차 시도 실패 — 임계값 0.4, 94.1% 판단보류

배포 모델(2023 엑셀 전량 909건으로 재학습, LogisticRegression)을 원문에 적용했더니 **94.1%가 확신도 0.4 미만**으로 판단보류가 됐다. 원인을 세 단계로 추적했다.

**① 길이 불일치**

| | 길이(중앙값) |
|---|---:|
| 학습 텍스트 (`text_for_model`) | 180자 |
| 적용 대상 원문 | **4,810자** (27배) |
| 적용 대상 요약 대체 | 262자 |

원문 앞부분만 잘라(300~4000자) 재측정해도 평균 확신도가 0.19~0.21 사이에서 거의 안 바뀌었다.

**② 내용 구조 불일치**

원문 앞부분은 "OO기관 공고 제2026-XX호" 같은 관인·공고번호 상투구다. "사업목적/추진배경" 마커를 찾아 그 뒤부터 발췌해도(마커 검출률 67.3%) 확신도 개선은 미미했다(0.20).

**③ 근본 원인 — 임계값 자체가 잘못됐다**

도메인 내부(2023 엑셀 자체, 5-fold CV)에서도 평균 확신도가 **0.32**뿐이었다. 900건 26클래스 모델은 원래 이렇게 확률이 퍼진다. 0.4는 데이터 특성상 애초에 도달하기 어려운 기준이었다.

다만 확신도는 신호로는 유효했다.

|---|---:|
| 맞춘 예측 | 0.356 |

### 입력 전처리와 원문 품질 — 무엇이 기여했나 (M08)

원문을 개선하면(E02) 분류도 좋아질 것으로 예상했으나, **두 변경을 동시에 넣으면 원인을 알 수 없어** 4개 조건을 같은 모델·같은 임계값으로 나란히 측정했다.

전처리는 관인부(`OO기관 공고 제2026-XX호`)·서명줄·페이지번호를 제거하고 `사업개요` 마커부터 `신청방법` 직전까지만 발췌하는 것이다.

| 조건 | 원문 보유 | 평균 확신도 | 신뢰 | 참고용 | 판단보류 | 사용가능 |
|---|---:|---:|---:|---:|---:|---:|
| A. E01 + 전처리없음 *(=M07)* | 906 | 0.2080 | 145 | 256 | 1,169 | 401 |
| **B. E01 + 전처리** ← 채택 | 906 | **0.2160** | **182** | **281** | **1,107** | **463** |
| C. E02 + 전처리없음 | **1,411** | 0.1961 | 98 | 229 | 1,243 | 327 |
| D. E02 + 전처리 | **1,411** | 0.2084 | 171 | 240 | 1,159 | 411 |

**예상과 반대 결과가 나왔다.** E02는 원문 보유를 906 → 1,411건(+56%)으로 늘렸는데 사용가능 예측은 오히려 줄었다(401 → 327건).

원인은 **새로 읽히기 시작한 505건이 전부 HWP**라는 데 있다. E01에서는 LibreOffice 부재로 아예 못 읽던 것들인데, HWP 공고문은 PDF보다 서식·표 비중이 높아 학습 텍스트(정제된 요약문 180자)와 더 멀어진다. 원문이 많아진 것이 분류에는 불리하게 작용했다.

**진짜 기여한 것은 전처리다.** E01 기준 +15%(401→463), E02 기준 +26%(327→411)로 두 경우 모두 개선됐다.

> **같은 원문이 과제에 따라 정반대로 작용한다.** E02는 지원규모 추출에서는 관측치를 +95% 늘렸지만(7-A장), 텍스트 분류에서는 불리했다. 표와 서식이 살아날수록 금액은 잘 잡히지만 문체는 학습 데이터에서 멀어지기 때문이다.

## 7. 모델 3 — 지원규모 (탐색 실험, 최종 채택 아님)

> **설계서 v3 14장에 따라 이 장의 실험은 최종 서비스 모델에서 제외한다.**
>
> 3등급 분류는 "이 공고의 지원금이 어느 등급인가"에 답한다. 그러나 프로젝트에 실제로 필요한 질문은 **"분야·지원성격·시기별 지원규모가 어떻게 변해왔고 앞으로 어떻게 변할 것인가"**다. 문제 정의가 다르다.
>
> 따라서 아래 7.1~7.6은 **탐색 결과로 보존**하고(원문 확보량이 부족할 때 쓰는 대체 표현 방식), 최종 산출물은 7-A·7-B장의 **지원규모 시계열**로 간다.

- 의미가 `unknown`인 금액은 **타깃에서 제외**. 기업당인지 총사업비인지 모르는 값을 섞으면 설계서 6.3이 경고한 오류가 된다

**A안 — 등급 분류**

## 7-A. 모델 3 재정의 — 지원규모 시계열 (설계서 v3 14~16장)

최종 문제 정의는 단일 classifier가 아니라 **정보추출 + 시계열 분석 파이프라인**이다.

```
공고문 원문 → 지원규모 추출 → 의미 유형별 정규화
           → 월 × 대분류 × 금액의미 집계 → 시계열 → STL → 조건부 예측
```

### 7-A.1 관측 테이블 — E02 재추출 효과

도구 교체(1.3절) 후 지원규모 관측치를 다시 뽑았다.

| 금액 의미 | E01 기준 | **E02 기준** | 증가 |
|---|---:|---:|---:|
| `per_company` (기업당) | 710 | **1,226** | +73% |
| **`total_budget`** (총사업비) | 219 | **611** | **+179%** |
| `periodic` (월/연) | 222 | 408 | +84% |
| `per_project` (과제당) | 105 | 219 | +109% |
| `unknown` | 682 | 1,322 | — |
| **합계** | **1,938** | **3,786** | **+95%** |

`total_budget`이 거의 3배가 됐다. **총사업비는 본문 문장이 아니라 표 안에 있는 경우가 많아서**, 표 구조 보존 효과가 여기에 집중됐다.

### 7-A.2 연도별 분포 — 시계열이 성립하게 됐다

```
2019  221    2023  265
2020  263    2024  286
2021  244    2025  294
2022  249    2026  642
```

이전에는 HWP 미처리로 앞 구간이 비어 있었다(2019년 1건, 2020~2022년 60~68건). 목록 표본(2019~2025)이 채워지면서 **7년치가 연 220~290건으로 고르게** 분포한다. Open API만 있을 때는 2026년 단일 연도라 시계열 자체가 성립하지 않았다.

### 7-A.3 집계 단위와 지표 (설계서 v3 15·16장)

**절대 섞지 않는다** — 집계 키에 `amount_type`을 반드시 포함한다(설계서 v3 24장 규칙 8). `per_company`와 `total_budget`을 같은 평균에 넣으면 무의미한 값이 나온다.

```
1차 MVP : 월 × 대분류 × 금액의미
2차     : 월 × 대분류 × 지원성격 × 금액의미  (모델 1 신뢰등급 충분 시)
```

지원규모는 이상치가 강해 **평균만 쓰지 않고** median·p25·p75를 함께 낸다.

### 7-A.4 시계열 가용성 판정 (설계서 v3 18장 조건 1·3)

기준: 개월수 ≥24 **AND** 월평균 관측 ≥3

| 금액 의미 | 관측수 | 개월수 | 월평균 | 판정 |
|---|---:|---:|---:|---|
| `per_company` | 1,226 | 85 | 14.4 | **가능** |

E01 기준으로는 `per_project`가 월 2.4건으로 미달이었으나, 재추출 후 **4종 모두 통과**했다.

## 7-B. 지원규모 STL EDA와 조건부 예측 판정 (설계서 v3 17·18장)

### 7-B.1 STL 결과 — 공고량과 정반대다

지원규모는 이상치가 강해 **median**을 주 지표로, 금액 자릿수 범위가 넓어 **log10 스케일**에서 분해했다. 결측월은 시간 보간하되 보간 비율을 함께 기록했다.

| 금액 의미 | 월수 | 결측 | 보간비 | 중앙값 | 추세강도 | 계절성강도 | 추세변화 | **조건4** |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **`per_company`** | 92 | 7 | 0.08 | 1,925만 | 0.2878 | **0.4410** | 감소 −30% | **충족** |
| `total_budget` | 92 | 8 | 0.09 | 14,250만 | 0.0842 | 0.0221 | 증가 +20% | 미충족 |
| `periodic` | 92 | 10 | 0.11 | 200만 | **0.0000** | 0.1362 | 감소 −29% | 미충족 |
| `per_project` | 92 | 20 | 0.22 | 3,177만 | 0.0872 | 0.1746 | 감소 −88% | 미충족 |

| | 공고량 (6-B장) | 지원규모 (이 절) |
|---|---:|---:|
| 추세강도 | 0.83 (전체) | **0.08~0.29** |
| 계절성강도 | 0.78 (전체) | **0.02~0.44** |

**"몇 건 나오는가"는 강한 시간 구조를 갖지만 "얼마를 주는가"는 거의 없다.** `periodic`의 추세강도가 정확히 0.0000인 것은 월 200만원 같은 **정액 지원의 성격상 자연스럽다** — 오히려 데이터가 맞다는 방증이다.

대분류별 `per_company`는 8개 중 4개(기타·내수·인력·창업)가 결측 42~58개월로 분해 자체가 불가능했다. **금융만 계절성 0.498 / +46%**로 뚜렷하다.

### 7-B.2 조건5 판정 — walk-forward 예측 (per_company)

조건4를 통과한 `per_company`만 대상으로 예측을 돌렸다. 공고량 예측과 같은 프로토콜(walk-forward, shift(1) 피처, fold train에만 scaler fit)을 쓰되, 관측이 92개월로 짧아 fold를 2개 뒀다.

| 모델 | MAE_log10 | 배수오차 | 2배 이내 |
|---|---:|---:|---:|
| **Last Value** *(baseline)* | **0.2904** | **2.61배** | **54.2%** |
| Moving Average(3) *(baseline)* | 0.4021 | 3.25배 | 50.0% |
| LightGBM | 0.7423 | 14.99배 | 35.4% |
| XGBoost | 0.7504 | 14.88배 | 35.4% |
| RandomForest | 0.7591 | 15.05배 | 35.4% |
| CatBoost | 0.7632 | 15.07배 | 35.4% |
| Ensemble | 0.7996 | 13.33배 | 29.2% |
| Ridge | 0.8874 | 25.48배 | 43.8% |
| Seasonal Naive | 1.0063 | 16.93배 | 16.7% |

**ML 모델 전부가 baseline에 크게 뒤진다.** fold1의 train이 60개월인데 피처가 15개로, 공고량 예측(768~960행)의 1/13 규모라 트리 모델이 노이즈를 학습한다.

**Seasonal Naive가 꼴찌인 것이 중요하다.** STL에서 계절성 0.441로 4종 중 가장 높았는데도 실제 예측에서는 "작년 같은 달 값"이 전혀 통하지 않는다. 공고량에서 Seasonal Naive가 강력한 baseline이었던 것과 정반대다. **STL이 잡아낸 계절성이 예측에 쓸 수준은 아니었다.**

## 8. 결론 세 가지

1. **데이터 성격에 따라 승자가 갈린다.** 텍스트 분류는 희소 TF-IDF + 선형 모델(LinearSVM), 범주형 표 형태는 CatBoost, 시계열은 이질적 앙상블이 이겼다. 한 모델이 전부를 이기지 않았다.

2. **베이스라인이 강하다.** 시계열에서 Seasonal Naive가 단일 ML 모델 대부분을 이겼다. 모델을 늘리는 것보다 베이스라인 대비 개선 여부를 보이는 게 중요하다.

3. **누수를 통제하지 않으면 성능표가 무의미하다.** 라벨 누수만으로 Macro F1이 0.14~0.26 부풀려졌다.

4. **모델의 자체 확신도를 그대로 믿으면 안 된다.** 지원성격 모델을 라벨 없는 데이터에 적용할 때 임계값 0.4를 썼더니 94.1%가 판단보류였다. 원인은 도메인 차이가 아니라 **도메인 내부에서도 평균 확신도가 0.32**였다는 점 — 900건 26클래스 모델은 원래 그렇게 퍼진다. 임계값은 항상 실측(CV 정밀도 곡선)으로 재보정해야 한다.

5. **좋은 데이터가 모든 과제에 좋은 것은 아니다.** 도구 교체로 원문 품질이 크게 올랐고(표 보존, HWP 처리), 지원규모 추출에서는 관측치가 **+95%** 늘었다. 그러나 같은 원문이 **텍스트 분류에서는 오히려 불리**했다(사용가능 401 → 327건). 새로 읽힌 HWP가 학습 텍스트와 문체가 멀기 때문이다. 개선을 도입할 때는 **과제별로 따로 측정**해야 한다.

6. **STL이 잡은 구조가 예측력을 보장하지 않는다.** `per_company`는 계절성 강도 0.441로 4종 중 가장 높았지만, 실제 walk-forward에서 Seasonal Naive가 **꼴찌**였다. 반대로 공고량은 계절성 0.78에 Seasonal Naive가 강력한 baseline이었다. STL은 baseline 선택의 **근거를 만드는 단계**지 결론이 아니다.
