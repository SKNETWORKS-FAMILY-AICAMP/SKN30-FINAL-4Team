### 1.2 공고문 원문 취득

세 원천 모두 요약문만 담고 있어 지원규모 정보가 빈약했다. 실제 공고문 파일을 받는 경로를 실측으로 규명했다.

| | 목록 97,794건 | Open API 1,570건 |
|---|---|---|
| 출발점 | `상세URL` (302 → 상세페이지) | `printFlpthNm` |
| 파일 URL | 페이지 HTML 안의 `/cmm/fms/fileDown.do?atchFileId=…` | **이미 CSV에 있음** |
| 요청 수 | 2회 (페이지 → 파일) | 1회 |

- 인증 조건: `JSESSIONID` 쿠키 + `Referer` 헤더가 없으면 **403**
- 페이지의 뷰어 경로(`DG_viewer/…&viewerSelect=image`)는 원본을 **이미지로 렌더링**하므로 사용하지 않음

**다운로드 실적**

| 대상 | 결과 |

## 3. 발견한 누수 3종

이 프로젝트에서 성능표를 무의미하게 만들 수 있었던 문제들이다.

### 3.1 라벨 누수 ① — 2023 엑셀 `사업개요`

첫 줄에 정답이 그대로 적혀 있다.

```
【공고이름】 2023년 개인정보 보호·활용 기술개발 스타트업챌린지 지원
【사업개요】 경영 / 사업화(SW·서비스) / 중소기업(ICT·SW(보안)) / 개인정보보호위원회(...) / 4월
 ① 목적: ...
```

**노출률: 대분류 100.0% / 중분류 99.9% / 업종 45.9%**

→ `text_for_model`에서 메타 줄을 제외하고 본문(①목적/②내용/③대상)만 사용.

**실측 효과** (같은 5-fold, 메타 줄 포함 여부만 다름)

| 타깃 | 모델 | 누수 포함 | 누수 제거 | 차이 |
|---|---|---:|---:|---:|
| 중분류 | LinearSVM | 0.7762 | 0.5129 | **−0.2633** |
| 중분류 | LogisticRegression | 0.6760 | 0.4494 | −0.2266 |
| 업종 | LinearSVM | 0.8721 | 0.7030 | **−0.1691** |
| 업종 | LogisticRegression | 0.7853 | 0.6414 | −0.1439 |

메타 줄을 안 지웠다면 Macro F1 0.87짜리 모델을 보고했겠지만 실제로는 0.70이다.

### 3.2 라벨 누수 ② — Open API `hashtags`

첫 토큰이 분야 라벨과 동일하다(`경영,경기,2026,...`). **노출률 100.0%**
→ 분야명과 겹치는 토큰을 제거한 `hashtags_safe` 생성.

### 3.3 시간 누수 — 시계열 피처

`rolling_mean_12`를 전체 시리즈에 걸어놓고 나중에 자르면, 2022년 검증 샘플의 피처에 이미 2023년 값이 들어가 있다.
→ **모든 lag/rolling을 `shift(1)` 이후에 계산.** 시점 t의 피처는 t−1 이전 정보만 담는다.

## 4. 검증 설계 (핵심)

### 4.1 모델별 분할 방식

| | 모델 1 분류 | 모델 2 시계열 | 모델 3 지원규모 |
|---|---|---|---|
| **방식** | Stratified 5-Fold | **Walk-forward** 3-Fold | **GroupKFold** 5-Fold |
| **분할 단위** | 행 (층 = 클래스) | 시간 | 그룹 = 사업명 |
| **데이터** | 896 / 900행 | 1,072행 | 361행 |
| **train : val** | **80 : 20** (고정) | 89~91 : 9~11 (가변) | **80 : 20** (고정) |
| **전 데이터 검증 사용** | 100% | **26.9%** | 100% |
| **K-Fold 교차검증인가** | ✅ | ❌ | ✅ |

### 4.2 fold별 실제 행수

**모델 1 — Stratified 5-Fold (중분류 896행)**

| fold | train | val |
|---|---:|---:|
| 1 | 716 (79.9%) | 180 (20.1%) |
| 2~5 | 717 (80.0%) | 179 (20.0%) |

896행 전부가 검증에 **정확히 1회씩** 사용된다.

**모델 2 — Walk-forward 3-Fold (1,072행)**

| fold | train | val |
|---|---:|---:|
| 1 | ~2021-12 · 768행 (88.9%) | 2022년 · 96행 (11.1%) |
| 2 | ~2022-12 · 864행 (90.0%) | 2023년 · 96행 (10.0%) |
| 3 | ~2023-12 · 960행 (90.9%) | 2024년 · 96행 (9.1%) |

**이것은 K-Fold 교차검증이 아니다.** 두 가지가 다르다.

1. 비율이 fold마다 달라진다(train이 계속 커지는 expanding window)
2. 1,072행 중 검증에 쓰인 건 **288행(26.9%)뿐**이고 나머지 784행(2014~2021)은 train 전용이다

K-Fold였다면 2014년 데이터도 검증에 쓰여야 하는데, 그러면 **2020년 데이터로 학습해 2014년을 예측**하게 된다. 시계열에서는 미래로 과거를 맞추는 누수다(설계서 13장 규칙 2).
문헌에서는 *time series cross-validation* / *rolling-origin evaluation*이라 부르지만, 산출물에는 **walk-forward validation**으로 표기하는 것이 정확하다.

2025년은 3/27까지의 부분 연도라 평가에서 제외했다.

**모델 3 — GroupKFold 5-Fold (361행 / 그룹 350개)**

| fold | train | val |
|---|---:|---:|
| 1 | 288 (79.8%) | 73 (20.2%) |
| 2~5 | 289 (80.1%) | 72 (19.9%) |

그룹은 **연도·지역 태그를 지운 사업명**이다. 같은 사업이 해마다 재공고되므로(`2025년 X사업` / `2026년 X사업`) 단순 KFold면 같은 사업이 train·test에 나뉘어 담겨 성능이 부풀려진다.

### 4.3 fold 내부에서 통제한 누수

**fold 밖에서 미리 계산하면 안 되는 것들**이다.

| 대상 | 잘못된 방식 | 적용한 방식 |
|---|---|---|
| TF-IDF 어휘 | 전체 데이터에 fit | **Pipeline으로 fold train에만 fit** |
| TruncatedSVD | 전체에 fit | fold train에만 fit |
| StandardScaler | 전체에 fit | fold train에만 fit |
| 결측 대치값(중앙값) | 전체 중앙값 | **fold train의 중앙값** |
| lag·rolling 피처 | 전체 시리즈에 rolling | **shift(1) 이후 계산** |
| SARIMA / Prophet | 전체 시리즈 1회 적합 | **fold마다 재적합** |
| 분야별 중앙값 베이스라인 | 전체 중앙값 | fold train에서 산출 |

**예외**: 사전학습 문장 임베딩(SBERT)은 우리 라벨을 전혀 보지 않으므로 전체에 대해 한 번 계산해도 누수가 아니다.

### 4.4 알려진 제약

- 중분류의 가장 작은 클래스가 **2건**이라 5-fold에서 fold 5개 중 2개에만 검증 표본이 들어간다. Macro F1이 낮게 나오는 원인 중 하나다.
- 단일 표본 클래스(중분류 13종 / 업종 9종)는 층화가 불가능해 제외했다. 커버리지는 98.6% / 99.0%로 손실은 작다.
- **고정 홀드아웃 테스트셋이 없다.** 데이터가 작아 전량을 교차검증에 쓴다. 설계서 18장 5순위가 요구한 "실제 서비스 입력과 동일한 형태의 별도 테스트셋"은 미구성 상태다.

## 5. 모델 1 — 중분류 / 업종 분류

### 5.1 문제 정의

대분류(8분야)는 기업마당이 이미 부여하므로 제외. 중분류·업종은 **2023 중앙부처 엑셀에만 있는 라벨**이라 예측 대상으로 남는다.

- 입력: `text_for_model` = 사업명 + ①목적 + ②내용 + ③대상 (메타 줄 제외)
- 타깃: 중분류 49클래스(896행), 업종 56클래스(900행)
- 벡터화: `char_wb` 2~4 n-gram TF-IDF (한국어는 형태소 분석기 없이도 문자 n-gram이 강함)

### 5.2 중분류 49클래스

| 모델 | Accuracy | Macro F1 | Weighted F1 | 시간 |
|---|---:|---:|---:|---:|
| **TF-IDF + LinearSVM** | 0.6361 | **0.5129** | 0.6223 | **4s** |
| TF-IDF + LogisticRegression | 0.6328 | 0.4494 | 0.6041 | 23s |
| SVD + CatBoost | 0.5525 | 0.3048 | 0.4900 | 203s |
| SVD + XGBoost | 0.5257 | 0.3007 | 0.4746 | 63s |
| SVD + RandomForest | 0.4755 | 0.2352 | 0.4036 | 26s |
| SVD + LightGBM | 0.4889 | 0.2338 | 0.4399 | 50s |
| Majority (하한선) | 0.1540 | 0.0059 | 0.0411 | 2s |

### 5.3 업종 56클래스

| 모델 | Accuracy | Macro F1 | Weighted F1 | 시간 |
|---|---:|---:|---:|---:|
| **TF-IDF + LinearSVM** | 0.7978 | **0.7030** | 0.7951 | **6s** |
| TF-IDF + LogisticRegression | 0.7711 | 0.6414 | 0.7626 | 28s |
| SVD + XGBoost | 0.6222 | 0.2042 | 0.5117 | 72s |
| SVD + LightGBM | 0.6022 | 0.1355 | 0.4875 | 86s |
| SVD + CatBoost | 0.5911 | 0.1443 | 0.4706 | 243s |
| SVD + RandomForest | 0.5478 | 0.0936 | 0.4090 | 42s |
| Majority (하한선) | 0.4978 | 0.0139 | 0.3309 | 2s |

### 5.4 채택 근거

**LinearSVM 채택.** 두 타깃 모두 1위이고 CatBoost보다 **40~50배 빠르다**(4~6초 vs 203~243초).

GBDT 3종이 뒤진 주된 원인은 **SVD**다. TF-IDF 6만 차원을 150차원으로 압축하면서 정보가 크게 깎이는데, GBDT는 모두 그 압축본을 입력으로 받는다. 시계열·회귀에서 CatBoost가 1위였던 것과 정반대 결과라, **데이터 성격에 따라 승자가 갈린다**는 근거가 된다.

**업종의 Accuracy는 함정이다.** Majority가 이미 0.4978인데 `전업종`이 전체의 절반이라서다. RandomForest(0.5478)·CatBoost(0.5911)는 Accuracy로는 Majority를 넘지만 Macro F1이 0.09~0.14로, 소수 클래스를 거의 못 맞추고 다수 클래스만 찍고 있다. 설계서 7.5가 *"Accuracy 하나만으로 평가하지 않는다"*고 한 이유가 이 표에 그대로 나타난다.

### 5.5 겪은 문제 — LightGBM 붕괴

초기 측정에서 LightGBM이 **Macro F1 0.0081**로 Majority보다도 낮게 나왔다. 설정을 바꿔 재측정한 결과:

| 설정 | Macro F1 |
|---|---:|
| `num_leaves=15, min_child_samples=5` | 0.0081 |
| `num_leaves=7, min_child_samples=1` | 0.2023 |
| `num_leaves=15, min_child_samples=1, n_est=300` | **0.2338** |

클래스당 표본이 약 14개뿐이라 `min_child_samples=5`가 분할을 막고 있었다. **모델의 성질이 아니라 설정 문제**였으므로 수정 후 값을 채택했다.

GBDT 예산도 조정했다. 부스팅은 다중분류에서 **반복 1회당 클래스 수만큼 트리**를 만든다. 49클래스 × 400 iterations = fold당 19,600그루로 비현실적이어서, 세 모델 **모두 동일하게** 150~300으로 낮춰 공정 비교를 유지했다.

## 6. 모델 2 — 월별 공고량 예측

### 6.1 문제 정의

- 단위: 월 × 분야 (8분야 × 147개월)
- 타깃: 시점 t의 `announcement_count` (1개월 ahead)
- 피처: `lag_1/2/3/6/12`, `rolling_mean_3/6/12`, `rolling_std_12`, `yoy_diff`, `month`, `quarter`, `month_sin`, `month_cos`, 분야(원핫)

### 6.2 결과 (walk-forward 3 fold 평균)

### 6.3 채택 근거

**단일 ML 모델은 Seasonal Naive를 의미 있게 이기지 못했다.** CatBoost만 0.15 앞섰고 XGBoost·LightGBM·SARIMA·RandomForest·LinearRegression은 모두 베이스라인에 뒤졌다. "작년 같은 달 값을 그대로 쓴다"는 규칙 하나가 GBDT보다 낫다는 뜻이다.

베이스라인을 넘은 것은 **이질적 앙상블**뿐이며 개선폭은 **+5.7%**다. 트리 계열끼리만 묶었다면 예측이 서로 너무 닮아 이 이득은 나오지 않았을 것이다.

설계서 8.4가 *"모델 개수 자체보다 Baseline 대비 실제 성능 개선 여부를 보여주는 것이 중요하다"*고 한 대목에 대한 답이다.

### 6.4 겪은 문제 — 한국어 Windows에서 Prophet 백엔드 실패

Prophet이 `'Prophet' object has no attribute 'stan_backend'`로 죽었다. 실제 원인은 다른 데 있었다.

cmdstanpy 1.3.0이 `where.exe tbb.dll`을 실행하고 출력을 UTF-8로 디코딩하는데, DLL을 못 찾으면 Windows가 **CP949 한글 오류 메시지**를 뱉는다. 이때 `UnicodeDecodeError`가 나고 Prophet이 이를 삼켜 엉뚱한 오류로 바꾼다.

→ `tbb.dll` 경로를 `PATH`에 추가하는 우회를 스크립트에 넣었다(`m02_forecast.py::_ensure_tbb_on_path`).

**이전 두 번의 Prophet 측정(MAE 41.93)은 전부 평균 대체값이라 무효였다.** 위 표는 수정 후 실측값이다(실패 0건).

### 7.3 2차 시도: A안·B안 병렬 검증 (M04)

**A안 — 등급 분류**

| 등급 체계 | 최고 모델 | Accuracy | Macro F1 | 인접 포함 |
|---|---|---:|---:|---:|
| **고정 3등급** | RandomForest | 0.6427 | **0.6339** | **0.9501** |

3등급이 5등급을 압도한다. 고정·분위 경계는 사실상 동률이라(0.6339 vs 0.6332) 실무에서 읽기 쉬운 **고정 경계(1천만/1억)**를 택했다.
순서형이므로 **인접 등급 포함 정확도**를 함께 측정했다. "1천만~1억"을 "1억 이상"으로 틀린 것과 "1천만 미만"으로 틀린 것은 실무 심각도가 다르다.

## 8. 결론 세 가지

1. **데이터 성격에 따라 승자가 갈린다.** 텍스트 분류는 희소 TF-IDF + 선형 모델(LinearSVM), 범주형 표 형태는 CatBoost, 시계열은 이질적 앙상블이 이겼다. 한 모델이 전부를 이기지 않았다.

2. **베이스라인이 강하다.** 시계열에서 Seasonal Naive가 단일 ML 모델 대부분을 이겼다. 모델을 늘리는 것보다 베이스라인 대비 개선 여부를 보이는 게 중요하다.

3. **누수를 통제하지 않으면 성능표가 무의미하다.** 라벨 누수만으로 Macro F1이 0.14~0.26 부풀려졌다.
