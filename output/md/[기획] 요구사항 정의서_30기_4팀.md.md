# 0. v0.1.1 → v0.1.2 변경 요약

## 0.1 핵심 변경

1. 시스템의 실제 입력 단위를 `사업기획안`에서 **사전협의 요청자료**로 정밀화
2. 핵심 입력문서를 **사전협의 요청서 + 사업계획서 또는 예산 설명자료**로 명시
3. `사업기획안`은 신규·변경 사업기획 전체를 뜻하는 상위 개념으로 재정의
4. 전체 기능 흐름을 `사전협의 요청자료 입력 → 신규·변경 사업정보 구조화`로 변경
5. INP 요구사항을 실제 요청자료 입력·업로드 기준으로 수정
6. STR 요구사항에 요청사유·신설/변경 구분·신설·변경 필요성·기대효과 등 공식 업무 필드를 반영
7. CPL 요구사항의 기준을 사전협의 요청서 및 제출자료 자체점검 Reference와 연결
8. DR-PRJ를 요청·식별 / 타당성 / 적합성 / 보조정보 구조로 확장
9. MVP M1~M3 및 요구사항 추적표 명칭을 요청자료 중심으로 정렬
10. `DEC-INP-002`를 신설하여 MVP 입력문서 조합과 자체점검표 취급을 별도 결정사항으로 관리
11. 기존 Top-5 / Top-3 / Type 1·2 / Evidence Trace / 최종판정 금지 / 우선순위 원칙은 유지

# 1. 요구사항 정의 기준

## 1.1 기준선

본 요구사항정의서는 다음 기획상 확정사항을 변경하지 않는다.

- 1차 사용자는 신규·변경 중소기업 지원사업을 기획하고 사전협의를 준비하는 신청기관 사업기획 담당자다.
- MVP는 실제 SIMS 신청·접수·검토결과·재협의 기능을 구현하지 않는다.
- 서비스는 최종 중복·타당성·정책판단을 수행하지 않는다.
- 기본 비교축은 `사업목적 / 지원대상 / 지원내용`이다.
- `지원규모 / 지원방식 / 중복수혜·참여제한 / 수행체계`는 데이터가 충분한 경우에만 비교한다.
- 관련사업 후보는 기본 Top-5 이내로 노출한다.
- 핵심 검토쟁점은 기본 Top-3 이내로 노출하며 억지로 3건을 채우지 않는다.
- 근거가 부족하면 `판단 불가` 또는 `추가 자료 필요`로 표시한다.
- 사용자는 검토쟁점을 `수용 / 보류 / 기각` 상태로 처리할 수 있다.
- 대화형 기능은 분석결과 Drill-down, 조건 변경, 재비교, 근거 확인에 한정한다.
- 최종 산출물은 On-demand `Pre-review 검토요약서`다.

## 1.2 용어 기준선

| 용어 | 요구사항 정의 | 사용 원칙 |
|---|---|---|
| **사업기획안** | 신규·변경 중소기업 지원사업을 구체화하는 전체 사업기획 내용 | 상위 개념으로만 사용하며 시스템의 직접 입력문서명으로 사용하지 않음 |
| **사전협의 요청자료** | 사전협의 신청을 위해 준비·제출하는 문서 묶음 | MVP의 실제 분석 입력 단위 |
| **사전협의 요청서** | 공식 서식에 따른 협의요청 문서 | 핵심 입력문서 |
| **제출자료 자체 점검표** | 제출자료의 주요 항목 포함 여부를 점검하는 서식 | Completeness Reference; MVP 입력 필수 여부는 DEC-INP-002 |
| **사업계획서 또는 예산 설명자료** | 사업의 대상·목적·내용·전달체계·근거·성과·예산 등을 상세히 설명하는 자료 | 핵심 분석 원문 |
| **사업안** | 구조화된 신규·변경 사업정보를 편의상 지칭하는 내부 용어 | 기능 내부 표현에 한정 |

## 1.3 사용자 역할

| 역할 | 정의 | MVP |
|---|---|---|
| 사업기획 담당자 | 신규·변경 사업의 사전협의 요청자료를 입력하고 Pre-review 결과를 검토·보완하는 1차 사용자 | 포함 |
| 시스템 | 사전협의 요청자료 구조화, 기존사업 탐색·비교, 쟁점·근거 제시, 검토요약 생성 | 포함 |
| 사전협의 검토자 | 제출 후 구조화 정보·비교근거를 재사용하는 향후 사용자 | Won’t |
| 시스템 관리자 | 기관·권한·운영설정 관리 | Won’t |
| 외부 전문가 | 최종 전문판단·정책판단 수행 | 서비스 외부 |

### MVP 권한 원칙

MVP에서는 기관 단위 권한관리나 실제 SIMS 계정체계를 구현하지 않는다.

## 1.4 요구사항 ID 규칙

| 유형 | 형식 |
|---|---|
| 기능 요구사항 | `FR-[영역]-NNN` |
| 비기능 요구사항 | `NFR-[영역]-NNN` |
| 데이터 요구사항 | `DR-[영역]-NNN` |
| 외부 인터페이스 | `IF-[대상]-NNN` |
| 미확정 의사결정 | `DEC-[영역]-NNN` |

기존 ID는 다른 의미로 재사용하지 않는다.

## 1.5 우선순위

| 우선순위 | 의미 |
|---|---|
| Must | MVP 성립에 반드시 필요 |
| Should | 중요하지만 일정·데이터 조건에 따라 조정 가능 |
| Could | 핵심 서비스 성립에는 직접 영향이 적은 선택 기능 |
| Won’t | 현재 MVP에서 제외 |

## 1.6 정의 상태

| 상태 | 의미 |
|---|---|
| 확정 | 기획 기준선에서 요구사항으로 확정 |
| 기획 방향 | 기능 방향은 확정됐으나 세부 정책 정의 필요 |
| 조건부 | 데이터·성능·일정 조건에 따라 동작 범위가 달라짐 |
| 확인 필요 | 팀 의사결정 또는 추가 검증 필요 |
| 후속 범위 | MVP 이후 |
| 제외 | 서비스 범위 밖 |

> 사용자 화면의 상태 라벨과 요구사항 문서의 `정의 상태`는 구분한다.  
> 사용자 화면에서 `확인 필요`라는 문자열은 사용하지 않는다.

```text
[사전협의 요청자료 입력/업로드]

          ↓

          ↓

          ↓

          ↓

          ↓

          ↓
```

# 8. MVP 우선순위

## 8.1 Must

MVP Must는 다음 핵심 Capability에 집중한다.

1. 텍스트 입력
2. 최소 1개 문서형식 업로드
3. 사전협의 요청자료 핵심필드 구조화
4. 핵심필드 원문근거
5. 누락 점검
6. 목적↔대상 / 목적↔내용 정합성 점검
7. 정의된 MVP 모집단에서 관련사업 Retrieval
8. Top-5 기본 노출
9. 목적·대상·내용 기본 비교
10. 중복수혜 조건 비교(데이터 존재 시)
11. 비교축 데이터 충분성 상태
12. Issue Taxonomy 기반 Type 1·2 쟁점 생성
13. Top-3 / 미충족 허용
14. Evidence Trace
15. 수용 / 보류 / 기각
16. 결과 기반 대화
17. 수정안 기준 재실행
18. On-demand 검토요약
19. 최종판정 방지
20. 근거 없는 생성 방지
21. 표준 상태 라벨
22. 평가 가능한 수용기준

## 8.2 Should / Could

### Should
- 추가 문서형식 지원
- 모호성 자동판정
- 추가 후보 보기
- 검색조건 직접 재실행
- 지원규모·지원방식·수행체계 상세비교
- 목적↔성과목표 점검
- 재실행 히스토리
- 파일형식 검토요약 내보내기
- 사용자 메모
- 외부 데이터 장애 제한모드

### Could
- 분석 전 입력원문 별도 확인 UI
- 분석 전 입력 교체 편의기능
- 기타 비핵심 내비게이션·편의기능

## 8.3 Won’t — 현재 MVP 제외

다음은 기획서 Should 또는 확장항목이지만 7주 MVP 일정과 1차 사용자 집중을 위해 현재 MVP에서 제외한다.

- 검토자 전용 View
- 연계 가능성 후보 기능의 별도 전용 모듈
- 복수사업 상세 동시 비교
- 협업·코멘트 워크스페이스
- 과거 사전협의 사례 자동추천
- 실제 SIMS 신청·접수·검토결과·재협의 연동
- 기관 단위 관리자·권한관리
- 공식 정책판정
- 전문가 자동대체
- 전체 과거 사전협의 결과 DB 구축

> 위 4개 기획서 Should 항목(연계 가능성 후보 / 복수사업 상세 비교 / 협업·코멘트 / 과거 사전협의 사례 추천)은 **기획서에서 삭제된 것이 아니라 MVP 범위 밖으로 명시적 이관**한다.

# 9. 수용 시나리오

기존 AC-01~AC-10은 유지한다.

## AC-11 완전성 점검

**Given** 지원대상이 `관내 중소기업` 수준으로만 기재된 사업안이 있고  
**When** 완전성·모호성 점검을 실행하면  
**Then** DEC-CPL-001의 판정기준을 충족하는 경우 해당 항목을 `구체화 필요`로 표시하고 사유를 제시해야 한다.

## AC-12 입력 실패

**Given** 텍스트를 추출할 수 없는 문서를 업로드했고  
**When** 분석을 실행하면  
**Then** 분석을 진행하지 않고 실패 원인과 텍스트 직접입력 등 대체 입력방법을 안내해야 한다.

## AC-13 수정안 재실행

**Given** 사용자가 구조화 필드를 수정했거나 보완된 사전협의 요청자료를 입력했고  
**When** Pre-review를 재실행하면  
**Then** 수정값이 반영된 새 결과가 생성되고 최소한 직전 결과와 구분할 수 있어야 한다.
