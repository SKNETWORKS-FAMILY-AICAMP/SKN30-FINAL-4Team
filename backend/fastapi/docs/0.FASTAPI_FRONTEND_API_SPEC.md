# 프론트엔드 FastAPI API 명세서

이 문서는 현재 구현된 프론트엔드 공개 API의 기준이다. 브라우저는 Supabase Auth,
Database API, Storage, Realtime, Edge Function을 직접 호출하지 않는다.

```text
Frontend (Cookie 포함 요청)
  → FastAPI /api/v1/*
       ├─ Supabase Auth
       ├─ Supabase Postgres / pgvector / private Storage
       └─ PostgreSQL polling worker
```

분석 상태는 REST polling으로 조회한다. SSE, WebSocket, Realtime 구독은 현재
공개 계약에 포함되지 않는다.

## 공통 규칙

- Base URL: `/api/v1`
- 프론트 요청: `credentials: 'include'`
- 업무 API 인증: HttpOnly Cookie. `Authorization` bearer token을 보내지 않는다.
- 성공 본문에 access/refresh token을 넣지 않는다.
- 서버가 검증한 Supabase user UUID만 소유권 판단에 사용한다.
- `user_id`, 역할, 권한을 요청 본문이나 query로 보내도 신뢰하지 않는다.

오류 형식:

```json
{ "code": "UNSUPPORTED_FILE_FORMAT", "message": "Request upload accepts .hwp and .hwpx" }
```

주요 상태 코드는 `401`(인증 실패), `404`(없음 또는 타 사용자 소유),
`409`(활성 분석 중복), `413`(50 MiB 초과), `415`(형식/MIME 불일치),
`422`(요청 검증), `503`(내부 의존성 미설정·일시 불가)다.

FastAPI Swagger UI(`/docs`)는 현재 route, path/query/form parameter와 인증 경계를
확인하는 용도로 사용한다. 분석 결과·후보·세션·이력의 고정 필드는 named OpenAPI schema로
제공한다. 단, CPL/FIT의 `detail`과 후보의 축별 `axes.*`는 판정 계약에 따라 확장되는
JSON object다. 필드 의미와 예시는 이 문서의 결과 조회 절과
[FASTAPI_RESPONSE_CONTRACT.json](FASTAPI_RESPONSE_CONTRACT.json)을 함께 기준으로 구현한다.

## 인증

### `POST /auth/sign-in`

```json
{ "email": "user@example.com", "password": "password" }
```

FastAPI가 Supabase password grant를 호출하고 `pre_review_access`,
`pre_review_refresh` HttpOnly Cookie를 설정한다. 성공 본문에는 user ID와 email만
반환한다.

### `POST /auth/sign-up`

`email`, `password`로 Supabase 가입 API를 호출한다. 이메일 확인이 설정되어 있으면
확인 안내만 반환한다.

### `POST /auth/refresh`, `POST /auth/sign-out`

refresh는 refresh Cookie로 Supabase 세션을 갱신하고 두 Cookie를 다시 설정한다.
sign-out은 Supabase 세션 종료를 시도한 뒤 로컬 Cookie를 삭제한다. 정상 완료는 `204`다.
Auth provider가 일시적으로 불가하면 `503`을 반환하면서도 Cookie는 삭제한다. refresh
Cookie가 없거나 유효하지 않으면 Cookie를 삭제하고 `401`을 반환한다.

### `POST /auth/password-reset`, `POST /auth/update-password`, `GET /auth/me`

비밀번호 재설정 메일 발송, **이미 검증된 Cookie 세션**의 비밀번호 변경, 현재 Cookie
세션 검증을 각각 수행한다. reset 요청은 계정 존재 여부를 노출하지 않는다. 다만 reset
메일의 token/PKCE를 HttpOnly Cookie 세션으로 교환하는 callback은 아직 공개 API가
아니다. 따라서 비밀번호를 잊은 사용자의 완결된 reset UX는 아직 구현 범위 밖이다.

Cookie는 `HttpOnly`, `SameSite=Lax`, `Path=/`다. 운영 HTTPS에서는 `Secure=true`를
쓴다. `POST /auth/*`와 `POST /analysis-runs`는 설정된 정확한 `Origin`만 허용한다.
이 Origin 검사는 Cookie 인증의 CSRF 경계이며, 현재 별도의 `X-CSRF-Token` 교환 API는
없다.

## 분석 실행

### `POST /analysis-runs`

`multipart/form-data`의 `file`에 HWP 또는 HWPX를 보낸다.

| 항목 | 현재 동작 |
|---|---|
| 파일 | `.hwp` / `.hwpx`, MIME·내용 검사, 최대 50 MiB |
| 저장 | FastAPI가 private `request-temp`에 서버 권한으로 업로드 |
| DB | `workspace.analysis_run`, `workspace.analysis_run_dispatch`, 원본 `workspace.source_artifact` 생성 |
| 큐 | 상태 `queued`; worker가 PostgreSQL polling으로 claim |
| 성공 | `202 Accepted` |

```json
{ "analysis_run_id": "uuid", "status": "queued" }
```

업로드 뒤 DB 생성이 실패하면 FastAPI는 방금 올린 Storage 객체를 보상 삭제한다.

### `GET /analysis-runs/{analysis_run_id}`

프론트는 이 endpoint를 주기적으로 호출한다. 응답 예시는 다음과 같다.

```json
{
  "analysis_run_id": "uuid",
  "status": "running",
  "analysis_case_id": null,
  "error_code": null,
  "error_message": null
}
```

`succeeded`이면 `analysis_case_id`로 결과를 조회하고, `failed`이면
`error_code`/안전한 `error_message`를 표시한다. `queued`와 `running`에서는 같은
endpoint를 polling한다. `/events` SSE endpoint는 현재 없다.

## 결과 조회

다음 endpoint는 모두 Cookie 소유권을 확인하며, 다른 사용자의 UUID도 `404`로
응답해 존재 여부를 숨긴다.

- `GET /analysis-cases/{analysis_case_id}`: CPL/FIT/SIM/ML 참고정보, 근거, report/session 스냅샷
- `GET /sim-candidates/{sim_candidate_id}`: 후보 공고의 축별 비교 상세
- `GET /analysis-sessions/active`: 현재 활성 세션. 없으면 `204`
- `GET /analysis-history`: 현재 사용자 이력

결과의 배열/필드 형태는
[FASTAPI_RESPONSE_CONTRACT.json](FASTAPI_RESPONSE_CONTRACT.json)을 따른다.
결과·이력·후보 상세는 retention window가 살아 있는 경우에만 조회된다. 후보 상세에는
후보에 연결된 evidence snapshot 배열도 포함된다.

`analysis_result.ml`은 세 모델의 참고정보이며 각각 `message` 한 필드만 내려간다.
이 문구는 모델이 준 자유 문장이 아니라 서버가 검증된 구조값으로 조립한 한국어
문장이고, `status`가 무엇이든 항상 채워진다 — 성공이면 조립한 문장, 실패면 사유
문구다. 그래서 프론트는 분기 없이 그대로 출력하면 된다.

`support_type`·`anomaly_level`·`predicted_amount_won`·`cause_axes`와 `status`·
`reason_code`는 저장 payload와 챗봇 컨텍스트에는 남아 있으나 이 공개 경계를 넘지
않는다. 확률·신뢰도·점수·백분위와 `internal` 값도 마찬가지다. 뱃지·필터처럼 구조값이
필요해지면 그때 해당 필드를 공개 표면에 추가한다.

`analysis_result.session.can_chat`이 `true`이면 아래 채팅 API를 사용할 수 있다.
질문 등록과 재시도는 Cookie 인증과 trusted Origin 검사를 모두 통과해야 한다.

## 분석 결과 채팅

- `POST /analysis-cases/{analysis_case_id}/messages`
  - body: `{ "content": "지원규모가 높은 편이야?" }`
  - `202 Accepted`: user/assistant message ID와 assistant `generating` 상태 반환
- `GET /analysis-cases/{analysis_case_id}/messages?limit=50&updated_since=<RFC3339>`
  - `limit` 범위는 1~100이며 `sequence_no` 순으로 반환
  - assistant가 생성 중이면 `content`는 `null`
  - `updated_since`는 폴링용 델타 커서다. 직전 응답에서 가장 큰 `updated_at`을
    그대로 넣으면 그 시각 이후에 생기거나 바뀐 메시지만 돌아온다. 생략하면 전체다.
  - 경계가 `>=`라 직전 마지막 메시지가 한 건 다시 오므로 `message_id`로 병합한다.
  - **`sequence_no` 커서를 쓰면 안 된다.** `generating` 답변이 `completed`로 바뀔 때
    `sequence_no`는 그대로여서, 프론트가 이미 받은 행의 완료를 영영 놓친다.
- `POST /analysis-cases/{analysis_case_id}/messages/{assistant_message_id}/retry`
  - 실패한 assistant 메시지만 재시도하며 `202 Accepted` 반환

답변은 해당 분석 건에 저장된 CPL/FIT/SIM/ML 공개 결과와 Evidence만 근거로 생성한다.
질문 접수와 assistant `generating` 행, durable queue 등록은 한 트랜잭션이며 실제 답변은
별도 Chat worker가 처리한다. 프론트는 POST 응답의 `assistant_message_id`를 보관하고 GET을
polling해 `completed` 또는 `failed` 상태를 확인한다. 다른 사용자, 보관기간 만료 건,
비활성 세션은 존재 여부를 구분하지 않는 `404`로 처리된다. 수동 재시도는 최대 2회이고
5초 cooldown이 적용된다.

## 아직 공개 API가 아닌 기능

다음은 데이터 모델 또는 이전 초안은 있으나 현재 FastAPI router에 구현·노출하지
않았다.

- 분석 세션 touch/close
- PDF signed URL 발급·재생성
- SSE/WebSocket/Realtime 상태 push
- 기존 공고 ZIP import HTTP API (현재는 trusted importer 스크립트)

프론트는 위 기능을 호출하면 안 된다. 추가 시 이 문서와 response contract를 함께
갱신한다.
