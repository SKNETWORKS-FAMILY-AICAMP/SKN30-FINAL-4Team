# 프론트엔드 FastAPI API 명세서

이 문서는 현재 구현된 프론트엔드 공개 API의 기준이다. 브라우저는 Supabase Auth,
Database API, Storage, Realtime, Edge Function을 직접 호출하지 않는다.

```text
Frontend (Cookie 포함 요청)
  → FastAPI /api/v1/*
       ├─ Supabase Auth
       ├─ Supabase Postgres / pgvector / private Storage
       └─ PostgreSQL polling worker
```

분석 상태는 REST polling으로 조회한다. SSE, WebSocket, Realtime 구독은 현재
공개 계약에 포함되지 않는다.

## 공통 규칙

- Base URL: `/api/v1`
- 프론트 요청: `credentials: 'include'`
- 업무 API 인증: HttpOnly Cookie. `Authorization` bearer token을 보내지 않는다.
- 성공 본문에 access/refresh token을 넣지 않는다.
- 서버가 검증한 Supabase user UUID만 소유권 판단에 사용한다.
- `user_id`, 역할, 권한을 요청 본문이나 query로 보내도 신뢰하지 않는다.

오류 형식:

```json
{ "code": "UNSUPPORTED_FILE_FORMAT", "message": "Request upload accepts .hwp and .hwpx" }
```

주요 상태 코드는 `401`(인증 실패), `404`(없음 또는 타 사용자 소유),
`409`(활성 분석 중복), `413`(전체 HTTP body 또는 파일 상한 초과),
`415`(형식/MIME 불일치), `422`(요청 검증), `503`(내부 의존성 미설정·일시 불가 또는
전역 queue cap 초과)다.

FastAPI Swagger UI(`/docs`)는 현재 route, path/query/form parameter와 인증 경계를
확인하는 용도로 사용한다. 분석 결과·후보·세션·이력과 CPL/FIT/SIM detail은 모두 named
OpenAPI schema의 strict typed DTO다. 정의하지 않은 raw/internal key를 browser 응답에
추가하지 않는다. 필드 의미와 예시는 이 문서의 결과 조회 절과
[FASTAPI_RESPONSE_CONTRACT.json](FASTAPI_RESPONSE_CONTRACT.json)을 함께 기준으로 구현한다.

## 인증

### `POST /auth/sign-in`

```json
{ "email": "user@example.com", "password": "password" }
```

FastAPI가 Supabase password grant를 호출하고 `pre_review_access`,
`pre_review_refresh` HttpOnly Cookie를 설정한다. 성공 본문에는 user ID, email,
`display_name`만 반환한다.

### `POST /auth/sign-up`

`email`, `password`, `display_name`으로 Supabase 가입 API를 호출한다. `display_name`은
1~100자의 필수 표시 이름이다. 이메일 확인이 설정되어 있으면 `user`가 `null`일 수 있고
확인 안내만 반환한다.

### `POST /auth/refresh`, `POST /auth/sign-out`

refresh는 refresh Cookie로 Supabase 세션을 갱신하고 두 Cookie를 다시 설정한다.
sign-out은 Supabase 세션 종료를 시도한 뒤 로컬 Cookie를 삭제한다. 정상 완료는 `204`다.
Auth provider의 transport/5xx 같은 일시 장애는 `503`을 반환하면서 기존 Cookie를
그대로 보존한다. 이 규칙은 refresh뿐 아니라 `GET /auth/me`와 Cookie 인증 업무 API에도
적용된다. sign-out은 provider 장애가 `503`이어도 로컬 Cookie를 항상 삭제한다. refresh
Cookie가 없거나 provider가 credential을 invalid/expired로 판정하면 Cookie를 삭제하고
`401`을 반환한다.

### `POST /auth/password-reset`, `POST /auth/update-password`, `GET /auth/me`

비밀번호 재설정 메일 발송, **이미 검증된 Cookie 세션**의 비밀번호 변경, 현재 Cookie
세션 검증을 각각 수행한다. reset 요청은 계정 존재 여부를 노출하지 않는다. 다만 reset
메일의 token/PKCE를 HttpOnly Cookie 세션으로 교환하는 callback은 아직 공개 API가
아니다. 따라서 비밀번호를 잊은 사용자의 완결된 reset UX는 아직 구현 범위 밖이다.

두 Cookie 모두 `HttpOnly`, `SameSite=Lax`다. access Cookie는 `Path=/`, refresh Cookie는
`Path=/api/v1/auth`로 scope를 좁힌다. 운영 HTTPS에서는 `Secure=true`를 쓴다.
`POST /auth/*`와 `POST /analysis-runs`는 설정된 정확한 `Origin`만 허용한다.
이 Origin 검사는 Cookie 인증의 CSRF 경계이며, 현재 별도의 `X-CSRF-Token` 교환 API는
없다.

## 분석 실행

### `POST /analysis-runs`

`multipart/form-data`의 `file`에 HWP 또는 HWPX를 보낸다. 프론트는 요청마다 UUID v4를
하나 생성해 `Idempotency-Key` 헤더에 넣고, 네트워크 오류로 같은 업로드를 재시도할 때는
반드시 같은 UUID를 다시 보낸다. 새 분석을 시작할 때만 새 UUID를 만든다.

| 항목 | 현재 동작 |
|---|---|
| 파일 | `.hwp` / `.hwpx`, MIME·내용 검사, `PREREVIEW_UPLOAD_MAX_BYTES`(기본 50 MiB) |
| HTTP body | `PREREVIEW_HTTP_MAX_BODY_BYTES`(기본 51 MiB): multipart boundary/header와 모든 part를 포함한 전체 요청 상한 |
| 헤더 | `Idempotency-Key: <UUID v4>` 필수; 같은 작업 재시도에서는 동일 값 사용 |
| 예약 | DB에 `uploading` run과 정확한 Storage 경로·SHA-256을 먼저 commit |
| 저장 | FastAPI가 private `request-temp`에 서버 권한으로 업로드 |
| 확정 | 원본 `source_artifact` 등록과 `queued` 전환을 한 DB transaction으로 commit |
| 큐 | 상태 `queued`; worker가 PostgreSQL polling으로 claim |
| 성공 | `202 Accepted` |

FastAPI는 `workspace.reserve_analysis_upload_v2`의 유일한 run ID allocator를 호출한다.
Storage object key는 호출 전에 owner와 `Idempotency-Key`로 결정적으로 만들며, 호출 전
생성한 임시 UUID를 run ID로 취급하지 않는다. 새 예약과 정확한 replay 모두 RPC가 돌려준
`analysis_run_id`를 source artifact 등록, queued 전이, 202 응답, 이후 status 조회에 그대로
threading한다. `replayed=true`이면 그 반환 ID에 이미 연결된 reservation을 재사용하며 새
run·object key·queue row를 만들지 않는다.

```json
{ "analysis_run_id": "uuid", "status": "queued" }
```

같은 사용자가 같은 `Idempotency-Key`와 동일 파일을 다시 보내면 기존 작업을 반환하고
Storage에 중복 업로드하지 않는다. 같은 사용자가 그 키를 다른 파일에 재사용하면 `409`다.
키 namespace는 사용자별이므로 다른 사용자의 우연한 UUID 충돌과 상태를 노출하지 않는다.

예약만 남은 `uploading` 작업은 같은 키·파일 재시도로 이어서 처리한다. Storage POST의
응답이 유실되거나 중복 응답이 오면 서버가 같은 private object를 다시 GET해 byte
SHA-256·길이·MIME이 모두 일치할 때만 성공으로 간주한다. 확인할 수 없는 경우에는
reservation과 객체를 보존하고 `503`을 반환하므로, 프론트는 새 UUID를 만들지 말고 같은
요청을 재시도해야 한다.

Storage 실패는 DB에 `cleanup_pending`으로 먼저 기록한 뒤 정확한 예약 객체만 삭제한다.
`queued` 확정 commit의 성공 여부가 불명확하면 원본을 삭제하지 않고 DB read-back 결과를
따른다. 15분이 지난 `uploading` 예약과 실패한 삭제는 다음 업로드 시 제한된 batch로 다시
정리한다.

새 analysis upload나 chat create/retry가 migration 37의 공유 전역 queue cap에 도달하면
`503 SERVICE_UNAVAILABLE`을 반환한다. 같은 Idempotency-Key의 정확한 replay는 기존 작업을
돌려주므로 새 작업이 아닐 때는 cap에 막히지 않는다. `PREREVIEW_GLOBAL_QUEUE_MAX`는
모든 API replica에서 같은 값으로 설정해야 한다.

### `GET /analysis-runs/{analysis_run_id}`

프론트는 이 endpoint를 주기적으로 호출한다. 응답 예시는 다음과 같다.

```json
{
  "analysis_run_id": "uuid",
  "status": "running",
  "analysis_case_id": null,
  "error_code": null,
  "error_message": null
}
```

`succeeded`이면 `analysis_case_id`로 결과를 조회하고, `failed`이면
`error_code`/안전한 `error_message`를 표시한다. `queued`와 `running`에서는 같은
endpoint를 polling한다. `/events` SSE endpoint는 현재 없다.

### `GET /analysis/current`

분석 화면의 초기/복귀 polling에는 이 endpoint를 사용한다. DB가 stale upload/run을 먼저
reconcile한 하나의 snapshot으로 다음 셋 중 하나를 돌려준다.

```json
{
  "state": "processing",
  "run": {
    "analysis_run_id": "uuid",
    "status": "queued",
    "original_filename": "request.hwpx",
    "created_at": "2026-09-14T03:00:00Z",
    "updated_at": "2026-09-14T03:00:00Z"
  },
  "session": null
}
```

- `processing`: `run`이 있고 `status`는 `uploading`, `queued`, `running` 중 하나다.
- `ready`: `run`은 `null`, `session`에 active 결과 session/case가 있다.
- `idle`: `run`, `session` 모두 `null`이다.

업로드 직후의 run ID를 알고 있으면 기존 `GET /analysis-runs/{analysis_run_id}` 단건 polling도
계속 사용할 수 있다.

## 결과 조회

다음 endpoint는 모두 Cookie 소유권을 확인하며, 다른 사용자의 UUID도 `404`로
응답해 존재 여부를 숨긴다.

- `GET /analysis-cases/{analysis_case_id}`: CPL/FIT/SIM/ML 참고정보, 근거, report/session 스냅샷
- `GET /sim-candidates/{sim_candidate_id}`: 후보 공고의 축별 비교 상세
- `GET /analysis-sessions/active`: 호환용 현재 활성 세션. 없으면 `204`
- `POST /analysis-sessions/{analysis_session_id}/close`: 지정한 소유자 session 종료. 성공은 빈 `204`
- `GET /analysis-history?cursor=<opaque>`: 현재 사용자 이력. 정확히 5개씩 signed snapshot cursor page

결과의 배열/필드 형태는
[FASTAPI_RESPONSE_CONTRACT.json](FASTAPI_RESPONSE_CONTRACT.json)을 따른다.
결과·이력·후보 상세는 retention window가 살아 있는 경우에만 조회된다. 후보 상세에는
후보에 연결된 evidence snapshot 배열도 포함된다.

`analysis-history`의 응답은 배열이 아니라 `{ "items": [...], "next_cursor": string|null }`다.
`next_cursor`는 URL-safe opaque 값이며 수정하지 않고 다음 `cursor`에 그대로 넣는다. history와
conversation history는 API의 `PREREVIEW_CURSOR_SIGNING_SECRET`이 비어 있으면 `503`으로
fail-closed한다. secret을 교체하면 기존 cursor는 무효가 된다.

### CPL 상태 표시 계약

`analysis_result.cpl.items[].status`는 다음 네 값 중 하나다. 모두
**소문자이며 대소문자를 구분**한다. 프론트는 이 값을 점수로 환산하지
않고 배지와 안내 문구에만 매핑한다.

| `status` | 표시 | 의미 |
|---|---|---|
| `confirmed` | 확인됨 | 값과 원문 근거가 확인됨 |
| `needs_confirmation` | 확인 필요 | 일부 값·근거가 불충분하거나 구조화 확인이 필요함 |
| `no_content` | 내용 없음 | 적용 대상 항목이지만 원문에서 내용을 찾지 못함 |
| `not_applicable` | 해당 없음 | 이 요청 유형에는 항목 자체가 적용되지 않음 |

`needs_confirmation`을 `not_applicable`로 표시하면 추가 확인이 필요한 결과가
“해당 없음”으로 오표시되므로, 알 수 없는 값은 별도 fallback 배지로 처리한다.

`analysis_result.ml`은 세 모델의 참고정보이며 각각 `message` 한 필드만 내려간다.
이 문구는 모델이 준 자유 문장이 아니라 서버가 검증된 구조값으로 조립한 한국어
문장이고, `status`가 무엇이든 항상 채워진다 — 성공이면 조립한 문장, 실패면 사유
문구다. 그래서 프론트는 분기 없이 그대로 출력하면 된다.

`support_type`·`anomaly_level`·`predicted_amount_won`·`cause_axes`와 `status`·
`reason_code`는 저장 payload와 챗봇 컨텍스트에는 남아 있으나 이 공개 경계를 넘지
않는다. 확률·신뢰도·점수·백분위와 `internal` 값도 마찬가지다. 뱃지·필터처럼 구조값이
필요해지면 그때 해당 필드를 공개 표면에 추가한다.

`analysis_result.session.can_chat`이 `true`이면 아래 채팅 API를 사용할 수 있다.
질문 등록과 재시도는 Cookie 인증과 trusted Origin 검사를 모두 통과해야 한다.

## 분석 결과 채팅

- `POST /analysis-cases/{analysis_case_id}/messages`
  - body: `{ "content": "지원규모가 높은 편이야?" }`
  - `202 Accepted`: user/assistant message ID와 assistant `generating` 상태 반환
- `GET /analysis-cases/{analysis_case_id}/messages/{assistant_message_id}`
  - POST/retry가 돌려준 assistant ID를 주기적으로 조회하는 polling endpoint다.
  - `generating`이면 `content`는 `null`, 이후 `completed` 또는 `failed`가 된다.
- `GET /analysis-cases/{analysis_case_id}/messages?limit=50&cursor=<opaque>`
  - `limit` 범위는 1~100이며 본문은 `{ "items": [...], "next_cursor": string|null }`다.
  - 각 page는 시간순(`sequence_no` 오름차순)이고 `next_cursor`는 더 과거 page를 위한
    signed keyset cursor다. 값을 수정하지 않고 그대로 다음 요청에 전달한다.
- `POST /analysis-cases/{analysis_case_id}/messages/{assistant_message_id}/retry`
  - 실패한 assistant 메시지만 재시도하며 새 UUID v4 `Idempotency-Key`와 함께 `202 Accepted` 반환

답변은 해당 분석 건에 저장된 CPL/FIT/SIM/ML 공개 결과와 Evidence만 근거로 생성한다.
질문 접수와 assistant `generating` 행, durable queue 등록은 한 트랜잭션이며 실제 답변은
별도 Chat worker가 처리한다. create와 retry는 각각 UUID v4 `Idempotency-Key`가 필수다.
프론트는 POST 응답의 `assistant_message_id`를 보관하고 단건 GET을 polling해 `completed` 또는
`failed` 상태를 확인한다. 다른 사용자, 보관기간 만료 건,
비활성 세션은 존재 여부를 구분하지 않는 `404`로 처리된다. `retry_count`는 worker 자동
재시도와 수동 재시도의 **합계**다. 자동은 최대 1회, 수동은 최대 2회이므로 공개 total은
최대 3이다. 수동 재시도에는 5초 cooldown이 적용된다. 같은 retry `Idempotency-Key`의
동일 재전송은 현재 total(3 포함)을 그대로 `202`로 반환한다.

## 아직 공개 API가 아닌 기능

다음은 데이터 모델 또는 이전 초안은 있으나 현재 FastAPI router에 구현·노출하지
않았다.

- PDF signed URL 발급·재생성
- SSE/WebSocket/Realtime 상태 push
- 기존 공고 ZIP import HTTP API (현재는 trusted importer 스크립트)

프론트는 위 기능을 호출하면 안 된다. 추가 시 이 문서와 response contract를 함께
갱신한다.
